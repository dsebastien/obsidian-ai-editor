### Decisions

- **Buffered-only transport for now**: adapters advertise streaming capabilities and the SSE decoder exists, but no per-provider stream decoder is wired; the executor does one fetch → one result event. Renderer `fetch` (not `requestUrl`) is the deliberate transport (streaming-capable later; `requestUrl` cannot stream); `requestUrl` fallback for CORS-blocked providers is a marked seam.
- **Edit forwarding from the focused view only**: linked panes replay the same edit as separate transactions; forwarding all would double-apply changes to the anchor store. A missed remap from a programmatic background edit cannot corrupt an apply (Accept precondition, BR #3).
- **Binding rules**: not applied yet — all enabled review-capable editors run (SEAM M6 marked in review-service).
- Skips are always reported (Notice + panel), never silent.

## Adversarial review round 2 — confirmed blocker/major fixes (same day)

## Concurrency limiter — behavior.maxConcurrentRequests enforced (plan §0 seam #3)

Settings exposed `behavior.maxConcurrentRequests` (1-10, default 3) but every editor executor stream started immediately. Enforced in commit `29bf5e5`:

- **Pure semaphore** `src/app/services/orchestration/semaphore.ts` (9 specs, dependency-free): FIFO admission; dynamic limit read via `getLimit()` at EVERY admission decision (each acquire and each release) — a settings change applies to subsequent acquisitions, permits already held are never revoked; abort-aware `acquire(signal)` — an aborted waiter leaves the queue immediately and rejects with the signal's reason, consuming nothing; idempotent per-permit release (double release frees exactly one slot); limits below 1 clamp to 1 so a bad value can never deadlock.
- **Gate placement**: `RunController` owns ONE `Semaphore` sized by an injected `getMaxConcurrentRequests` provider (default unlimited for headless/test callers) and passes it to every `ReviewRunHandle` — the gate is plugin-wide, so at most N backend requests are in flight across ALL concurrent runs, not per run. `ReviewRunHandle.consume` acquires BEFORE calling `spec.execute` (the stream — and thus the backend request — cannot start without a permit) and releases in a `finally` covering every exit (done, error, cancel, thrown stream).
- **Truthful UI state**: while queued the editor keeps its initial `'pending'` status (verified — `'running'` is only set after admission), so rail/panel show not-yet-started honestly.
- **Cancellation**: `cancelRun` aborts the shared signal → a queued waiter is ejected synchronously and settles as `'cancelled'` without its executor ever being called; no zombie waiters, no leaked permits (spec: a fresh run acquires immediately after). Cancelling a queued run leaves an in-flight run on another file untouched.
- **Wiring**: `plugin.ts` constructs `new RunController(() => this.settings.behavior.maxConcurrentRequests)` — live view, no reload needed. CLI-triggered reviews flow through the same controller, so they share the same gate.
- **Specs**: 5 new `RunController` concurrency specs (N+1 editors with limit N → one pending; release admits FIFO; gate shared across runs on different files; cancel-while-queued ejects + no leak; limit raised between runs applies to the next run). One pre-existing timing-sensitive cancel spec widened from 2 to 5 microtask turns (the acquire await adds one turn before the stream starts).

- **Concurrency permit released at terminal state** (`run-controller.ts`): the plugin-wide `maxConcurrentRequests` permit was only freed in the consume loop's `finally`, i.e. when the editor stream's iterator ended. After `cancelRun` (or a terminal event) the loop keeps draining discarded events (`continue`), so an executor that ignores its AbortSignal — the `RunEditorSpec` seam where future CLI backends plug in — held its permit indefinitely: with limit N, N such streams deadlocked every future review plugin-wide (editors stuck `pending`) until plugin reload, and cancelling could not reclaim them. Fix: the release function is stored on the editor state and fired the moment the editor goes terminal (`terminate` and `cancelRun`); release is idempotent (semaphore guarantee) and the `finally` stays as backstop. 2 new specs: cancel reclaims the permit from an abort-ignoring executor (a fresh run acquires immediately); a terminal `result` frees the permit while the stream is still draining (queued editor completes even though the first stream never closes).
- **Ask-editor submit refuses a switched note** (`review-controller.ts`): `openAskEditorModal`'s submit called `startReview(view, …)`, which resolves `view.file` at submit time — if the leaf switched notes while the modal was open (programmatic `openFile`, another plugin, workspace restore), the instruction dispatched as a whole-note review of the WRONG note. The note path is now captured at modal-open time; a mismatched submit aborts with a Notice ("The note changed while the dialog was open — ask cancelled.").
- **Ask dispatch scope is `whole-note`, not `auto`** (`review-controller.ts`): the collapsed-capture case (`requested === undefined`) dispatched scope `auto`, so a selection made during the modal's arbitrarily long gap silently narrowed the run — violating design §1's rule that selection scope flows EXCLUSIVELY through the `requestedSelection` capture contract. `whole-note` is safe unconditionally: a valid captured selection overrides the snapshot scope explicitly, and the invalid-selection fallback already strips to whole-note.
- **Docs corrected**: the "Ask an editor" history entry claimed "Specs: 27 new (ask-editor-model 10, …)" — actual delta is 13 (697 → 710; ask-editor-model 6, reviewCapableEditors 2, augmentSystemPrompt 3, instruction pipeline 2), now stated correctly. Design doc drift closed: §3 command table gained the shipped `ask-editor` row (editorCheckCallback, same gate as Review selection), §1 item 3 no longer reads "M4; ships as a hidden item until the modal exists" — annotated as shipped (commit `991fbcd`).

Gates: `bun run format`, `bun run validate` (tsc + eslint + 712 tests), `bun run build` all green.

Open: standing live checks unchanged; new live check — cancel a run against an unresponsive backend (e.g. hung Ollama) with limit 1 and confirm a fresh review starts immediately.

## Slow & thinking models — piece 1: per-editor retry

Final slice of the increment (plan §0, decisions locked): an editor whose attempt ended `error` or `cancelled` can be re-run alone, inside the existing run (commits `4810a5b` core, `3343271` UI).

- **Core** (`RunHandle.retryEditor(editorId, freshText)`): legal only for terminal-with-failure editors (`done`, pending/running, and mid-retry all refuse with a typed result). The retry REPLACES the editor's previous findings — `FindingStore.removeMany` drops them (any status; an accepted edit stays in the document, only the record goes) so two generations of critique never mix. Other editors' findings are untouched.
- **Anchoring is the crux** (BR #3/#4): the run-level `appliedChanges` replay history became a per-editor anchor base — each attempt anchors findings against ITS base text (run snapshot initially, the CURRENT buffer captured at retry time) and replays only edit batches applied since that attempt started. Recording stops per editor at terminal (strictly better than the old stop-after-settle gating) and restarts from the retry snapshot. The retried request also SENDS the fresh text to the backend — the model must review the text its quotes anchor against; a selection scope only rides along while the attempt text is still the snapshot text (offsets into changed text are meaningless).
- **Cancel composition**: retries run on a fresh per-retry `AbortController` plus a fresh per-editor runId. After `cancelRun` the shared run signal is permanently aborted — composing with it would kill any retry instantly — so the retry's own controller is the only signal; `cancelRun` lost its early-return and now aborts in-flight retry controllers too. The new runId doubles as the attempt guard: late events from a previous attempt's still-draining stream fail the runId match, and a stale consume loop can never terminate a newer attempt. The concurrency permit (`maxConcurrentRequests`) is acquired exactly like a first attempt — a retry queues as 'pending' behind the limit.
- **Settle semantics**: `isSettled()` is now derived from live editor state, so an active retry flips the run back to in-progress everywhere — rail spinner + Cancel button, `Cancel review` command gate, side panel; CLI `ai-editor:status` already derived `settled` from editor states. The `settled` promise keeps first-settle semantics (a promise cannot un-resolve; the CLI awaits it for one-shot output) — documented on the interface.
- **UI**: rail dots became chips — `RailEditorStatus` gained `'cancelled'` (previously folded into `'idle'`, which would have hidden the affordance) and failed/cancelled editors show a retry icon-button ('Retry <name>'); the side-panel section header mirrors it (`rotate-ccw`, same label) via `SidePanelBinding.retryEditor`. Both call the single `ReviewController.retryEditor(filePath, editorId)`: current buffer text read synchronously from the canonical view in the same block as the retry start (no keystroke can interleave; edit forwarding is already live since the run stays bound after settle), vault-read fallback for runs without an open view (run-identity guarded across the await). Refusals → Notice.
- **Specs** (+10, 747 total): fresh-text anchoring with repeated-text occurrence disambiguation against the NEW text, retry-after-cancel on a fresh signal, permit queueing, illegal retries (done / in-flight / mid-retry / unknown), `isSettled` flip, edits-during-retry remap + accept, cancel of an in-flight retry, `removeMany` semantics, rail retry affordance + cancelled labels.

Gates: `bun run format`, `bun run validate` (tsc + eslint + 747 tests), `bun run build` all green.

Open: live checks — fail an editor (kill Ollama), retry from the rail chip and from the panel header, confirm old findings vanish and new ones anchor on the edited buffer; cancel a run, retry one editor, cancel again mid-retry; retry while another run holds all permits (chip shows waiting). The whole "Slow & thinking models" row is now code-complete.

## Slow & thinking models — fix pass (adversarial review)

Adversarial review of the increment surfaced 5 findings (1 major, 4 minor); all verified against the code and current Anthropic API docs, all real, all fixed (commits `c34472f` backends, `df633f8` CLI).

- **Anthropic thinking was wired to a dead API mode (major)**: 'on' sent manual extended thinking (`thinking: {type: 'enabled', budget_tokens}`), which is deprecated on Claude 4.6 and rejected with HTTP 400 on every current model (4.7+, Opus 5, Sonnet 5, Fable 5) — and because the transport never reads error bodies (BR #12), the only symptom was an opaque `Provider request failed (HTTP 400)`. `thinking: 'on'` now sends **adaptive thinking** (`{type: 'adaptive'}`), which also supports forced tool use — `tool_choice: {type: 'tool'}` stays forced, restoring the structural output guarantee for the thinking path (the text-JSON parser fallback remains as defense). `max_tokens` rises to 32k in adaptive mode because thinking spend counts against it (every adaptive-capable model allows ≥64k output).
- **Legacy budget mode preserved explicitly**: the schema `thinking` enum grew to `'off' | 'on' | 'budget'` (no-users policy — changed freely, salvage covers it element-wise). `'budget'` sends the legacy manual block for Claude 4.5-and-earlier models; the backend modal's Thinking dropdown (Off / Adaptive / Budget (legacy)) documents which generation each mode fits, and the budget int field shows only in budget mode. Ollama treats any non-'off' value as `think: true`.
- **Budget overflow clamped**: `MAX_OUTPUT_TOKENS (8192) + budget` could reach 40,192 while the legacy models that accept manual thinking cap `max_tokens` at 32k — every request with a budget above ~23.8k failed API validation with HTTP 400. Budget mode now clamps the sum to 32,000 and the budget to `max_tokens − 1024` (result headroom), keeping `budget_tokens < max_tokens` for every schema-legal value (spec: budget 32,000 → max_tokens 32,000, budget_tokens 30,976).
- **openai-compatible reasoning progress**: `createOpenAiAccumulator` only inspected `delta.content`/`delta.refusal`, so a reasoning model behind a compatible endpoint (thinking enabled via `extraBodyJson` — the field's own use case) produced zero progress events for the whole reasoning phase: minutes of apparent hang, the exact failure mode this increment exists to eliminate. Non-empty `delta.reasoning_content` (DeepSeek) and `delta.reasoning` (OpenRouter) now count as progress without ever entering the payload, mirroring the Anthropic `thinking_delta` handling. Spec pins progress during a reasoning-only phase and the reasoning text staying out of the result.
- **CLI one-shot output vs mid-run retry**: `ai-editor:review` awaits `run.settled`, which keeps FIRST-settle semantics — a per-editor retry started from the rail/panel of an open note flips that editor back to pending/running, and `shapeRunOutput` silently dropped it from findings, summaryByEditor AND skips; with no other completed editor it falsely reported 'The run was cancelled before any editor completed'. Non-terminal editors now surface as a distinct `retrying` skip reason, and the nothing-completed message names the in-flight retry and points at `ai-editor:status` (which already derives terminal state correctly). One-shot semantics deliberately kept — blocking the CLI call on user-driven retries could hang it indefinitely.

## Daemon mode — fix pass (adversarial review)

Adversarial review of the daemon increment (`93229af..a9c45e3`) surfaced 6 findings (4 code minors + 2 report-accuracy notes); all verified against the code, code fixes in commit `c1b84e1`.

- **`abortWhen` survives a mid-flight daemon disable (cost)**: the guard only checked for an unsettled run, so toggling `behavior.daemonMode` off while a fired dispatch sat inside `startReview`'s context-assembly awaits still reached `startRun` and billed the configured backends after the cost kill-switch was flipped (`settingsChanged` clears timers and scheduler state but cannot stop an already-fired async dispatch). The guard now also returns true when the setting is off.
- **`abortWhen` survives plugin unload (teardown race)**: same gap for `dispose()` — `onunload` clears timers and `cancelAll()` SETTLES runs, so the run-in-flight check passed and a dispatch mid-await started a fresh run whose backend fetches were never aborted (requests outliving the plugin). Unlike the analogous command-path race, daemon dispatches fire unattended, so racing plugin-disable is realistic. The guard now also returns true on `disposed`; the `plugin.ts` `onunload` comment ("no dispatch can start mid-teardown") was reworded to the guarantee that actually holds (no new timer fires; mid-flight dispatches abort via `abortWhen` before `startRun`).

- **Reduced motion (WCAG 2.3.3)**: `.ai-editor-rail-daemon` pulses for the entire idle window — up to 600 s per `daemonIdleSeconds` — on every open note being edited, with no `prefers-reduced-motion` guard. - **Report-accuracy (no repo change)**: the increment's chat report claimed "+5 service specs" — the actual delta in `review-service.spec.ts` is 4 new `it()` blocks (editorIds pool restriction, editorIds no-editors, abortWhen aborts, abortWhen proceeds); plan/history made no numeric claim and were already accurate.
