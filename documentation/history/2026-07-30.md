## Theming, reduced motion and accessibility sweep (v1 sweep stage I, slice 1 — M9)

The first M9 slice. Five code commits plus this docs commit: `866244d` (the stylesheet), `110ba42` (finding highlights), `a62e058` (the side panel), `fd6f044` (the settings tab bar), `fdae37a` (the colour swatch).

Specs 2098 → **2124** (+26: +0 / +12 / +6 / +8 / +0, measured per commit by checking each one out in a clean worktree and running the suite).

### Theming — audited against the real variable set, not from memory

Obsidian's `app.css` was extracted from the installed `obsidian.asar` and every custom property this plugin uses was checked against it, then against the three community themes installed in the vault (Border, Minimal, Omarchy). All 34 are real core tokens. Nothing was renamed.

Two things were actually wrong:

- **Corners did not follow the theme.** 27 rules got their radius from Tailwind's `@apply rounded` — a hardcoded `0.25rem`. It happens to equal Obsidian's default `--radius-s`, so the default look is byte-identical, but Border redefines the radius tokens 27 times and Minimal 6, and this plugin's cards, chips, buttons and dialogs ignored all of it while every Obsidian surface around them changed shape. They now read `var(--radius-s)`. `rounded-full` was left alone: a dot is geometry, not a theme decision.
- **One hand-mixed shadow.** The margin card carried `rgb(0 0 0 / 12%)`. A light-on-dark theme needs a different elevation colour than a dark-on-light one, and the floating finding card already took `--shadow-s` — the card beside it now does too.

`--text-warning` was the one token no theme redefines; it is core-defined (`var(--color-orange)`), and the single site using it without a fallback was made consistent with the other four rather than left as the odd one out.

### Reduced motion — a blanket, because the allow-list said so itself

Every animation in the stylesheet WAS covered, by three separate `prefers-reduced-motion` blocks listing selectors by hand. The comment above one of them stated the problem in its own words: "that list is explicit, so a new animation is silently exempt unless it is added there". Nothing in the build could catch an omission, and the cost of forgetting falls on the user who asked their operating system not to animate things.

The three lists are replaced by ONE block at the foot of the file, scoped by attribute to elements carrying this plugin's class prefix — so Obsidian's animations and the theme's are untouched — collapsing `animation-duration`, `animation-iteration-count`, `transition-duration` and `scroll-behavior`. Specificity 0,1,0 and last in the file, so it wins over every animated rule above without an `!important` (which the repo's CSS rules forbid). Durations are collapsed rather than removed so an animation that ends on a different style than it starts still lands on its final frame.

Verified in the built `dist/styles.css`: the block is the last rule emitted.

Nothing depends on motion to convey state, which is what makes the blanket safe: the pulsing rail dot is also dimmed, the review spinner sits next to the word "Reviewing…", the chip-click emphasis keeps its stronger static tint, and the margin cards were already documented as deliberately un-transitioned.

### The finding highlight was pure colour

The headline defect the milestone names. A highlight in the document carried exactly ONE signal — the persona tint. With three editors on a note that tint was the only thing separating three overlapping opinions, and it is invisible to a red/green deficiency, to a monochrome display, and to a screen reader.

Two additions, deliberately independent:

- A `title`: `<Editor> — <severity>`, plus `member of <Panel> (panel)` when the editor reviewed as a member, plus a sentence when the finding has gone stale. The PARTS ride the decoration spec rather than a finished string, so a mark that goes stale in place (`markStaleEffect`, no rebuild) re-derives a sentence that says so — spec-pinned.
- A per-editor bottom-edge STYLE (`ai-editor-finding-edge-<n>`): dotted, dashed, double, from the editor's index in settings, so the order matches the rail's chips and is stable for the life of the vault. Only the style varies — width and colour stay put, so no persona's highlight is louder than another's. Slot 0 is the plain solid edge and emits no class at all, so a one-editor vault renders exactly as before. `.ai-editor-finding-stale` still drops the edge entirely.

**`aria-label` was rejected, with the reason written into `finding-identity.ts`.** A CM6 mark renders as a `<span>` inside the editor's contenteditable, i.e. `role=generic` — which ARIA forbids naming, the same rule that moved the margin card's composed sentence onto a `role=group` in the stage H fix pass. Rendering the mark as `<mark>` would earn a nameable role and was rejected too: Obsidian styles `.markdown-rendered mark` at a specificity a single class cannot beat, so every finding would inherit the theme's `==highlight==` look inside Live Preview and the plugin would fight it with doubled selectors forever. The authoritative NAMED surfaces for a finding are unchanged and already correct — the side-panel row, the review card (`role=dialog`), the rail chip. A highlight is a pointer into those.

### What the side panel was not saying

- **A solo editor's section had no accessible name.** Only a panel member's did, which read as a deliberate distinction and was not one: it left the commonest case — two or three editors on a note — as unnamed regions, so a screen-reader user landing on a finding heard the critique with no way to ask whose it was. `memberSectionName` names every section and adds the panel when there is one.
- **Severity reached assistive tech not at all.** It is a coloured Lucide glyph; the shape keeps it off colour alone, but `setIcon` emits an SVG with no text, so info and warning were indistinguishable. The span is `role=img` named with the severity.
- **A scorecard row read into the next one** — a stack of unrelated spans announced as one unpunctuated run. `role=group` plus `scorecardMemberName`, which leads with the member and spells out "not weighed by the panel" and "reviewed, but not named in the scorecard" instead of leaving them to a pill's colour.

### The settings tab bar promised a pattern it did not implement

`role="tablist"` with `role="tab"` buttons and none of the behaviour. A screen reader announces "tab, 3 of 7", its user reaches for the arrow keys, and nothing happened — declaring the role made the bar HARDER to operate than seven plain buttons would have been. And because `renderAll` empties the container, activating a tab destroyed the element the user was standing on and dropped focus to the document: one keystroke and the bar was gone.

Now the whole pattern: roving `tabindex` (one stop for the bar, Tab moves past it into the settings themselves), Arrow Left/Right with wrap plus Home/End, `aria-controls` onto a real `role="tabpanel"` that is `aria-labelledby` its tab, and focus put back on the tab the user moved to — only when the re-render was caused by their action, so the load-time re-render cannot steal focus from wherever they had got to. Selection follows focus (the pattern's default for cheap panels): one gesture moves and activates, and the panel under the tab is always the one being announced. The key → index decision is the one piece of pure logic and is pinned in `tab-keyboard.spec.ts`.

### Focus rings, and the one place they were missing

Obsidian's ONLY focus indicator for a button is `button:focus-visible { box-shadow: 0 0 0 3px var(--background-modifier-border-focus) }` — verified against the extracted `app.css`. Every control in this plugin that is a real `<button>` inherits it, and the `box-shadow: none` in our base rules sits at 0,1,0 and loses to that 0,1,1 selector, so nothing was being suppressed. That was worth checking rather than assuming, because the base rules look like they suppress it.

What Obsidian cannot cover is the four elements that are focusable without being buttons: the clickable side-panel finding row (`role=button tabindex=0`), the transform preview widget, the "what will be sent" prompt block and the push-back thread list. Each had a background or border tint indistinguishable from hover, which is WCAG 2.4.7 and 2.4.11. They now get the same ring as the native one. The transform preview also stopped suppressing the outline on plain `:focus` (it now only styles `:focus-visible`).

### The colour swatch

A row of buttons whose only content is a hue, where the selected one was marked by — another hue. `aria-pressed` states it, a white check inside a dark halo shows it (a glyph and not a token: the background is a user-picked colour, not a theme surface, so no theme variable is guaranteed to contrast with it), and the newly selected swatch takes focus back after the row rebuilds.

## Stage H review fix pass

External review of the M8 comment slices surfaced 19 findings. Every one was verified against the code first: 18 were real and are fixed, 1 was declined with reasons (below). Three code commits plus this docs commit: `a63b848` (the durable store), `e6506a6` (dispatch + refresh), `a16c534` (the column).

### The store had four ways to lose comments and two ways to lose them at startup

- **An interrupted write could take the whole vault's comments with it** (`a63b848`). `writeStoreFile` stages the payload in `comments.json.tmp` and, when the adapter refuses to rename over an existing file, does `remove` then `rename`. Between those two calls the temp file is the ONLY copy — and nothing ever read it: `load()` read the store path, got `null`, reported `missing`, and `commentStoreLoadNotice` renders `missing` as _no notice at all_. Every durable comment gone, silently, presented as a first run. Load is the recovery point now: a missing store with a readable temp beside it is an interrupted write, adopted and reported as `recovered`. A temp that is not readable is preserved like any other corruption rather than swallowed.
- **Every write was a blind overwrite** (`a63b848`). The module doc already anticipates sync ("Obsidian Sync, Syncthing and iCloud all conflict-copy per file") but the code read the file exactly once, at load. Device A opens the vault, device B parks comments and syncs the file in, A's next debounced write reverts them wholesale with nothing said. Writes now re-read first and compare against the exact bytes this session last saw; anything else is another writer, and the two sides are **unioned by comment id** — this session wins a shared id, everything only the other side has is adopted. Deliberately a union: propagating the other side's deletions would let a sync round-trip erase a question, and deleting is one click away anyway. Comparing bytes rather than adding a `stat` to the storage seam is the declined half of a review finding (see below). A foreign file that can be neither parsed nor preserved stops the writes instead of clobbering it.
- **A rename merging onto an occupied path dropped the overflow silently** (`a63b848`). `noteRenamed` returns the dropped count and the glue Notices it — Business Rules #13 forbids the silent case specifically.
- **`flush()` did not wait for the write in flight** (`a63b848`), so its contract ("writes immediately if anything is pending") was false in exactly the case that matters: the 2 s debounce firing moments before quit. It awaits the running write, whose own loop already picks up whatever queued behind it. Bounded to that one write — a failing adapter must not spin the unload path.
- **A failed write scheduled no retry** (`a63b848`). It set `dirty` and waited for the next mutation, so one locked file turned into "nothing is written for the rest of the session" for any session where the user stopped commenting. Failures re-arm with an exponential backoff (capped) and, after three in a row, tell the user — the console is not a user surface.
- **Vault hooks were registered before the store finished loading** (`a63b848`). Obsidian replays renames and deletes made while it was closed, so a rename landing during `load()`'s two async reads hit an empty map and was then _undone_ by the load, which restored the comments under the OLD path — a key nothing can reach again. Load first; `load()` also merges into the map instead of setting over it, as a second line of defence.
- **A deleted note left its runs going** (`a63b848`). `CommentRunController.cancelForNote` existed and was spec-covered but had no caller: the request ran to completion, held a permit from the plugin-wide budget (so it could still delay a foreground review) and its terminal event landed on a comment nothing tracks. `CommentJobRegistry.noteDeleted` cancels first and then removes, the same order `delete()` uses, and `cancelForNote` follows a folder prefix like every other vault handler here.

### The margin only appeared to work

- **Nothing refreshed the column on a job transition** (`e6506a6`). The registry subscription was the only thing wired to job notifications — including the once-a-second ticker — and it called `updatePanels()` alone, which never touches `refreshMargin`. So a parked comment sat on "Queued" with no timer and no answer until an unrelated scroll, `layout-change` or pane resize happened to schedule a refresh. The Notice promises the opposite in so many words. The subscription drives both surfaces now; `scheduleRefresh` is coalesced and `MarginColumn.render` is a no-op on an unchanged model, so the 1 Hz tick costs a reposition pass. Retry got the same treatment (it announced nothing and refreshed nothing).
- **Typing never repositioned the cards** (`e6506a6`). `handleEditorUpdate` returns early for a note with no run, and again when nothing went stale — the common cases — so cards stayed at pixel offsets measured before the edit while their lines moved, and a comment whose quote had just been deleted still rendered as anchored with a live Reveal button. It schedules a coalesced refresh when the note actually has comments, so an ordinary note pays nothing.
- **A refused retry stranded the comment** (`e6506a6`). `prepareRetry` ran BEFORE the gate chain: status → `submitted`, findings cleared, error dropped, persisted — and then `dispatch` could still refuse (excluded, rule-disabled, needs-confirmation, no-editor, note-full, already-running). The result is a dead end: `submitted` offers no Retry, offers a Cancel that cancels nothing, and the failure message is already gone until a restart normalizes it to `interrupted`. Worst of all, the oversized-note copy tells the user to "re-ask" — the affordance that had just disappeared. The restart is now the last thing before the launch, and the start-path gate specs have retry mirrors.
- **The comment dialog could park a question about the wrong text** (`e6506a6`). The offsets were captured at modal-open time and the note read fresh at dispatch, so anything that changed the note while the modal was open (Sync, another pane, another plugin) had `spanHints` derive a quote from unrelated text. The span's text is captured with the offsets and re-checked at dispatch — the precondition shape the "Ask an editor" flow already used.
- **A read-only store accepted comments all day and lost every one** (`e6506a6`). `isReadOnly()` had no consumer in `src`: with writes disabled after unpreservable corruption, the modal still opened, the request still went out, and the Notice still promised an answer in the margin. One startup Notice is not informed consent. Parking and retrying refuse, and say why.

### The column, its focus and its names

- **The render key included the elapsed timer** (`a16c534`), so `marginModelKey` changed once a second while any job ran and `render` answered with `replaceChildren()` on the whole column — destroying whatever the keyboard user had focused, every second, and contradicting the class's own contract about scroll frames. Latent only because of the missing subscription refresh above; fixing that would have turned it into per-second focus theft. The timer and the card's announced sentence are live text, written in place through `marginCardStatusText` / `marginRenderedCards`.
- **The orphan box ate the anchored cards** (`a16c534`). It was `shrink-0` above a `flex-1` groups box in a fixed-height `overflow-hidden` column — and that groups box is the coordinate space every anchored card is positioned and clipped in (`groupsBox()`). Expanding a few orphan cards drove its height toward zero, so comments whose lines were plainly visible silently vanished as "off-screen"; past that the orphan cards themselves were clipped by a column that is `pointer-events-none` and therefore unscrollable. The orphan box is an overlay now (capped at half the column, scrollable) and the groups box always spans the pane, so anchors are measured against the pane rather than against a box another element's height controls.
- **The announced sentence was dropped on exactly the cards that needed it** (`a16c534`). It rode on `aria-label` attached to a plain `div` on the non-revealable path, and ARIA forbids naming `role=generic` — which is the orphan case: status line `aria-hidden`, a dashed border as the only other cue, and nothing announced but the question. The card is a `role=group` carrying the name; the reveal button keeps its visible text as its name (WCAG 2.5.3, label in name). The side panel's comment row had the identical defect.
- **`MarginColumnModel.empty` was deleted** (`a16c534`) rather than consumed. Its only plausible consumer would drop the reserve when nothing is in view — which is precisely the reflow-on-scroll the column exists to avoid. A field advertising an invariant nothing can enforce invites a caller to act on it.

### Declined, with the reason

The review asked for mtime/size (or hash) stat-based conflict detection, re-statted immediately before the rename. The storage seam is deliberately five calls and has no `stat`; adding one buys nothing over comparing the bytes this session last saw, which is what shipped and which also covers an adapter whose mtime granularity is coarse. The _effect_ the finding asked for — preserve, merge, surface, never silently win the race — is implemented.

Specs: +18 (2080 → 2098; +13 / +2 / +3 per commit): temp-file recovery incl. the still-a-first-run and unreadable-temp cases, external-change merge + the no-resurrection guarantee + the refuse-to-clobber case, backoff and escalation, flush-awaits-in-flight, rename overflow reporting, registry delete-cancels-runs (note and folder), the four retry-refusal gates leaving the stored status untouched, the render key's insensitivity to the timer, the live-text helpers.

Gates: `bun run format`, `bun run validate` (tsc + eslint --max-warnings 0 + 2098 tests), `bun run build` all green after each commit. Nothing pushed.

## The margin column, and a way to ask for a comment at all (v1 sweep stage H, slice 3)

M8's last UI item. Four code commits plus this docs commit: `95d1711` (pure geometry + card model), `f31acdb` (the column DOM + styles), `bec3414` (controller wiring), `c08ab87` (the "Ask for comments" entry point).

The headline is not the column. It is that `startCommentJob` **had no caller**: slices 1 and 2 built a durable store, a background orchestration shape, a starvation policy and a side-panel section for a feature no surface could create. Three surfaces now can.

### Not a CM6 gutter — the same answer the rail gave

CM6 gutters are left-side, line-oriented strips inside the scroller. A right-hand comment column is none of those things: its items are taller than a line, the user reads them in parallel with the text, and it has to coexist with Obsidian's own gutters (line numbers, fold) rather than compete for their slot. So the column is a positioned overlay owned by the markdown view — `rail.ts` review finding #19, applied a second time — created through the view's own `Document` (popouts), Obsidian-free, no `innerHTML`, text glyphs.

### Coexistence with the editor width — decided, not inherited

Three placements, and the reasoning is the decision:

- **`overlay`** — with **Readable line length** on (Obsidian's default) the text is centered and the pane already has a wide empty right margin. The column drops into it and the note's layout **does not move at all**.
- **`reserve`** — with it off, the text runs the full pane width and there is no free margin. Floating cards over prose would hide the very sentences they comment on, so the column pads the editor scroller instead. The text reflows exactly twice per note: when the first comment appears and when the last one goes, both explicit user actions.
- **`hidden`** — below ~700px of pane. The rail survives a narrow pane because it is 16px chips; 220px of prose does not. This is the number that supersedes the M4 row's superseded ~900px three-column figure.

The measurement feeds back on itself and that had to be handled: padding the scroller by `P` moves a full-width block left by `P` but a centered one by `P/2`, so the placement subtracts what it applied — regime-aware — before deciding. Without it, reserve widens the margin, the wider margin says overlay, dropping the reserve narrows it again. `MARGIN_MODE_HYSTERESIS` covers the boundary the same way `nextLayoutMode` does; a missing readable-width class falls back to the full correction, which under-reports free space and therefore stays in `reserve` rather than flapping.

### Stacking, and what is deliberately not rendered

`stackMarginSlots` pushes groups DOWN from their anchors (a run of comments on consecutive lines stays readable) and then pulls the tail back UP off the bottom edge, never above the column's top. A card may sit above its line — that is still the nearest legible position — but never off-screen.

Comments whose line is **not in view are omitted**, not clamped: clamping fifty comments into the viewport piles forty-nine on the one the user is reading. But the column itself stays mounted while the note has any comment at all, so scrolling never adds or removes the reserved space — a reflow triggered by scrolling would be the single worst thing this feature could do.

Several comments on one line collapse into an **"N comments"** chip. A single comment never collapses: a chip that expands to one card is a click that buys nothing.

Orphans (quote no longer resolves) go into ONE collapsed group pinned at the top, **with their quote**, so the user can find the text themselves. Never dropped (Business Rules #13), never guessed into a position (#4), and never offered Retry — `retryCommentJob` refuses an orphan, so a button offering it would be a lie.

### Resolve is not Delete

Two different promises, and now one vocabulary across the margin and the side panel:

- **Resolve** closes the comment and KEEPS the record (store status `dismissed`) so nothing re-asks it.
- **Delete** removes it for good, behind a confirmation dialog. Business Rules #13 forbids deleting a comment _silently_; never deleting one at all would be a different and worse rule — the user wrote the question, and an orphan they no longer care about would otherwise be unremovable. The rule text now says so.

The side panel's "Dismiss" became "Resolve" and gained "Delete" (no users, so the copy changed outright).

### Render, measure, position

Three phases, because a card's height is only knowable once rendered and its position depends on every other card's. `marginModelKey` deliberately excludes anchor positions: scrolling changes every anchor on every frame, and rebuilding there would throw away keyboard focus, re-collapse expanded answers and flicker. Scroll frames reposition; they never re-render. Heights are re-measured only when the DOM was rebuilt or the column width changed (measuring forces a layout).

The scroll listener is a CAPTURE-phase listener on the view's content element: `scroll` does not bubble, CodeMirror's scroller does not exist when the glue mounts, and a capture listener on an ancestor catches it from whichever descendant actually scrolls.

Re-anchoring runs `matchQuote` over the whole note once per comment and the refresh cycle fires on every edit batch — so it is memoized against the CM document's identity (immutable, so a new object IS a changed document) plus the stored comments' revisions.

### "Ask for comments"

Editor context menu (last item — it is the only one that produces nothing to watch), an `Ask for comments` command, and a button beside the panel's Review. A **selection is required** and the refusal says so: a margin comment is anchored to a span, and a whole-note comment would have no line to sit next to and no quote to re-anchor against after an edit. `Review current note` is already the whole-note surface.

One dialog serves "Ask an editor" and "Ask for comments" — the interaction is identical (pick an editor, type a question, send) and two would have drifted apart on keyboard handling, enablement and the single-editor case. They differ in copy and in the default editor, which is what finally makes `behavior.defaultCommentEditorId` real (plan §4 "Comment routing"): the picker opens on it, reroutes per comment, and falls back silently when that editor can no longer run — a picker whose initial value is empty makes the primary button look broken.

The size guard round-trips through the same confirmation modal reviews use, with copy that says what confirming buys. Success speaks a Notice on purpose: the column may be hidden (narrow pane, toggle off) and a background job with no acknowledgement looks like a click that did nothing.

- `Cycle severity filter` (or the panel button): info findings disappear from the highlights AND the panel, the hidden count matches, `Next finding` walks only the visible ones, and `Accept all` counts drop accordingly. Cycling back to "All severities" restores everything (nothing was mutated).
- Filter + triage: with the ringed finding hidden by a filter change, the ring disappears and the next step resumes from that position.

- **No new operation needed**: `thread-turn` already existed in the contract (request: findingId, quote, critique, history, message). Decision: a hold updates critique and suggestion **in place** — it is the same observation, refined — rather than superseding; `supersede` stays for the refine-proposal flow that mints a NEW finding. Updating in place re-derives the accept precondition for free: the anchor and `anchoredText` are untouched, so a span that went stale mid-turn keeps the revised suggestion display-only, and a finding sitting in `preview` whose suggestion CHANGED falls back to `open` (the diff on screen is no longer the proposal). A concede dismisses and flags `conceded` — but never undoes an accept that landed while the turn was in flight (the exchange is still recorded).
- **Threads live on the run handle** (`RunHandle.startThreadTurn`), because the run owns the findings they hang off: a replaced or discarded run kills its turns for free, and `cancelRun` aborts them AND marks their findings failed immediately (same rationale as reclaiming editor permits: an executor that ignores its signal must not leave a card spinning forever). Same event protocol as reviews (runId match, exactly-once terminal, post-terminal discard, wrong result kind / stream-end-without-terminal = failures), same plugin-wide permit, same redaction seam. A turn deliberately does NOT participate in `settled`/`isSettled()` — the review is over, a thread is a side conversation. Aborts are per-turn rather than composed with the run signal, so pushing back on a CANCELLED run's findings still works (cancel keeps findings inspectable).
- **Cancellation contract**: closing the card cancels nothing (the reply lands in the store and shows when reopened, plus a Notice); `Cancel review` does cancel.
- **Dispatch** (`services/thread-service.ts`): shaped like `startReview` / `startAction` — exclusions fail closed before anything is read (BR #7), only the editor that PRODUCED the finding may answer (typed skip when it is missing, disabled, review-incapable, or has no usable API backend), the persona prompt is assembled fresh (the vault IS the config), the span text is resolved BEFORE any await, refusals are typed results. Deliberate omission: no size guard — a thread-turn request carries the quote, critique, prior turns and the message, never the note text (the note only counts against the context budget), and the review that produced the finding already passed the guard. Asking again inside a card would be noise.

Re-rendering would eat what the user is typing, so the reply drafts, keyboard focus and caret are carried across the rebuild; drafts live and die with the card.
- **Notices**: every completed turn reports once (withdrew / revised / replied / failed) because the card is usually closed by the time the answer arrives. `cancelled` and `discarded` stay silent — cancelling is a user action with its own feedback, and a discarded turn means the finding is gone.

## Binding rules actually filter, and note types are real (v1 sweep stage E, slice 1)

The `SEAM M6` marker in `review-service.ts` is gone. `settings.rules` had been modelled since M1 and consumed by nothing; it now governs both of plan §4b's effects. Five code commits plus this docs commit: `5a926f7` pure engine, `2251df5` vault seam + OSK adapter, `d0710ed` dispatch, `adf6bdd` UI suppression, `3d419a2` Rules tab.

### Evaluation order — decided, not inherited

Two phases, and the reasoning matters more than the code:

1. **A matching `disabled` rule wins from ANY position in the list.** The alternative — plain first-match-wins across both effects, which is what the tab's old copy promised — lets an unrelated `assign` rule ordered above a kill switch silently re-enable the plugin on the notes the user fenced off, with no visible cause. A kill switch is a safety control; being shadowed by an ordering accident is a bug class, not a preference.
2. **Among `assign` rules, the FIRST match in list order wins.** Sorting by match specificity (note-type > frontmatter > tag > folder) was considered and rejected: the tab exposes explicit move-up/move-down, so list order IS the user's priority statement, and a hidden sort would make the visible order a lie. Any specificity the user wants is expressible by moving a rule up.

Assignments are **not** unioned across matching rules. A rule saying "only the Humanizer touches this folder" has to be able to mean exactly that; accumulating with a broader rule's target makes narrowing inexpressible.

No match → the pre-rules behavior, every enabled review-capable editor. The tab says so, including in its empty state.

### Cold metadata cache fails in opposite directions per effect

Obsidian's metadata cache resolves asynchronously, so tag / frontmatter / note-type facts can be missing right after startup. `disabled` rules then fail **closed** (treated as matching) and `assign` rules fail **open** (treated as not matching). Same trade-off `isExcluded` already makes for privacy, applied where it belongs: a warm-up window in which the plugin wakes up on the notes the user switched it off for is the one outcome a kill switch may not produce, while an assignment failing open lands on the documented default pool, not on a leak. Folder matching needs no metadata and is always evaluated — so a folder-scoped kill switch is exact even during warm-up.

### Note-type identity is a SET, and the OSK plugin stays optional

The Starter Kit names a type `Personal Notes` and tags it `type/personal`. There is no reliable transformation between those, so a note's identity is the union of both spellings, normalized (`personal-notes`, `personal`), and a rule matches **any** of them. A rule written against the canonical name works with the plugin installed; a rule written against the tag works either way. The alternative — guessing a singular/plural mapping — would silently mismatch on types like `Personal Notes` / `type/personal`, where the stem itself differs.

`recognizeNoteType` was deliberately **not** ported from `starter-kit.service.ts`: it is asynchronous, and every consumer here is a synchronous decision (context-menu construction, command gate, rail render) that cannot await a cross-plugin call. Its inputs — the type list and the note's tags/path — are synchronous, so recognition is done locally in `domain/rules/note-type.ts` by matching each type's own enabled tag / folder / filename-regex mappings. `formula` mappings are not evaluable outside the Starter Kit and recognize nothing; a user-authored regex that fails to compile recognizes nothing rather than taking down a menu build.

`ui/osk-note-types.ts` is the entire dependency on that plugin: feature-detected, `ApiResult`-envelope tolerant, every field defensively normalized, `[]` on anything unexpected or thrown. Nothing else in the plugin knows the Starter Kit exists.

`domain/rules/matchers.ts` now owns the folder/tag primitives and `context/exclusions.ts` imports them. A user who excludes `Private` and disables the plugin for `Private` must get the same set of notes both times; that is now true by construction rather than by two implementations agreeing.

### Cost of asking

Rule evaluation runs on every menu open, command gate and refresh cycle, so the fact gathering reads only what the configured rules can use: no rules or folder-only rules never touch the metadata cache, and only a rule matching on note types triggers the registry call. The counting fake in `note-rules.spec.ts` pins that — the common vault pays nothing.

### `rule-disabled` is not `excluded`

A new typed refusal on `ReviewStart`, `ActionStart` and `ThreadStart`, plus the matching CLI error code. Keeping it separate is the point: `excluded` means "this content never leaves the vault" and the fix is in the Behavior tab, `rule-disabled` means "AI Editor does not operate here" and the fix is in the Rules tab. The message names the rule (its name, or its match expression when unnamed). It is checked **before** the size guard, so a switched-off note never pops a confirmation dialog on its way to being refused.

Only the kill switch applies to actions and threads. An `assign` rule picks who REVIEWS a note; a bound action already names its own target editor, and a push-back can only be answered by the editor that produced the finding.

### Participant pools, unified

`startReview`'s pool precedence is now explicit: a per-run `instruction` (ask-an-editor, a bound review verb) > a daemon's `editorIds` re-dispatch > a matching `assign` rule > every editor. Rules supply the DEFAULT pool only — when the user or the daemon named editors, that choice wins.

The two pool kinds that NAME editors (instruction, rule) share one code path and report every named editor that cannot run, disabled and deleted included, instead of silently shrinking. The daemon's re-dispatch pool keeps its old silence about disabled editors: the user turned them off on purpose and an automatic refresh must not nag. A rule pointing at a deleted panel refuses with a new `rule-target-missing` skip rather than quietly reviewing with everyone the rule was meant to replace — referential integrity reports the same dangling reference in the settings.

### The kill switch reaches every surface

`isReviewable` now takes the vault reader instead of a pre-read metadata value (rules need note-type facts too) and folds the kill switch in, so every surface already gated on it — the review commands, the file menu, the CLI, the daemon's fire-time probe — refused a switched-off note with no further wiring.

Where the exclusion path stopped short, this slice went further:

- `isNoteExcluded` became `isPluginEnabledFor` (exclusion AND kill switch), because both produce the same UI outcome: nothing offered. `EditorMenuState.excluded` became `blocked` with an explicit "nothing at all" early return, so the contract is local to the pure model instead of inferred from a caller that happens to build consistent state.
- **The rail is now hidden and the highlights cleared** for a blocked note. Previously the rail stayed up on excluded notes, offering a Review button whose only possible outcome was a refusal Notice.
- `runContextFor` became the single choke point for every ambient triage surface (next/previous finding, accept/dismiss current, bulk accept/dismiss, severity filter): a blocked note reports no run, so none of those commands is available and none can mutate it. `activeRunContext` delegates to it. The side-panel binding and the finding-card lookup refuse the same way; a card open when the rule lands is closed once, on the transition.
- **`Cancel review` stays available on purpose.** Stopping an in-flight backend request is never the wrong outcome, and gating it would leave a run nothing could stop.
- A hidden run stays **bound** to its glue. Edit forwarding keeps its anchors remapping, so removing the rule restores a coherent run instead of a set of stale offsets (Business Rules #3/#4).

### Rules tab

The UI could already create, edit, reorder and delete rules, so this was polish only: copy that matches the engine, the obsolete "OSK auto-discovery lands in a later milestone, rules using it stay inert" paragraph replaced by a live Starter-Kit-detected / not-detected line telling the user which spelling to match, and `ruleSummary` upgraded to say what a rule RESOLVES to (`folder "Blog" → reviewed by panel Pre-publish (Hater, Humanizer)`) and to say so when it does nothing: no target yet, deleted editor, deleted panel, panel with no members left. ## The context budget is a policy, and the plugin will show you what it sends (v1 sweep stage E, slice 2)

Plan M5's two remaining context items — the budget across every source, and the "what will be sent" preview. Three code commits plus this docs commit: `094f41b` budget policy, `5d05749` one prompt-build entry point + preview service, `64bdfd3` modal / command / settings button.

### What was already there, and stayed there

The task list asked to "check whether context assembly honors `includeLinkedNotes` / `maxLinkedNotes`". It does, fully, and has since the follow-links work: `assembleContext` attaches the reviewed note's outgoing links as `linked-note` attachments — links AND embeds (`ObsidianVaultReader.getOutgoingLinks` merges `cache.links` with `cache.embeds`), markdown only, depth 1, deduplicated against everything already attached under an earlier reason, capped at `maxLinkedNotes`, budget-aware, and with excluded notes never inlined _and_ never consuming the cap. All of it spec-covered. So this slice verified it instead of rebuilding it; the only change on that path is that attachment blocks now carry a `role`.

That `role` is the one thing the labeling was missing. Every block used to read `<context-note path="…">`, whatever it was. A note the persona references is instruction material; a note linked from the document under review is subject matter; a model that cannot tell them apart will happily critique the reference material. The `role` value is the attachment reason, so the prompt, the preview and the budget all name the same thing with the same word.

### The budget had no owner and no honesty

`contextBudgetChars` was four lines of arithmetic inlined in the assembler, and the two fields meant to explain it — `preview` and `truncated` — had **no production consumer at all**. They were produced on every run and read only by their own tests. Worse, `truncated` held both the note that got a prefix and the notes that got nothing, which is the distinction a user needs most.

`services/context/context-budget.ts` now owns the policy: the send/priority order, the allocation, the labels. The assembler collects candidates and applies it. Splitting them is what makes the whole policy pure and spec-pinnable without a vault, and gives the preview one place to read it from.

**Priority order, decided rather than inherited:**

1. The **system prompt** — voice text + persona text + memory text as one string. Never truncated: half a persona silently produces a different editor.
2. The **reviewed note** — never truncated. Findings must quote the submitted snapshot verbatim and anchors resolve against it (Business Rules #3/#4), so a trimmed note would make anchoring lie. The assembler could not trim it even if it wanted to: the note text travels in the operation payload (`operation.text`), not in the system prompt. The budget only ACCOUNTS for it.
3. **Attachments** in assembly order: `prompt-ref` → `wikilink-ref` → `followed-link` → `linked-note`.

Because the first two are never truncated, the ordered truncatable region IS the attachment list — so ONE list serves as both the send order and the priority order. That coupling is deliberate. Two orders would let the preview show notes in an order that does not explain which of them got dropped, and explaining that is the entire point of the preview.

Inside `prompt-ref`, voice-profile notes precede persona notes, mirroring the system prompt's text order (the assembler's documented invariant). So the global voice profile outranks a persona's own reference notes. Considered and rejected: hoisting persona refs above it because "the persona IS the editor" — the persona's _text_ is never truncated at all, and the voice profile is one small globally-configured note set while persona refs are per-editor and typically the larger group. Dropping the persona's fifth reference before the single voice-profile note is the better failure, and anyone who disagrees can express it by turning `injectVoiceProfile` off for that editor.

Two reporting decisions follow from wanting the preview to be honest rather than reassuring:

- **Truncated is not dropped.** An attachment allocated zero characters is `dropped`. "Truncated" promises a prefix arrives, and an empty prefix is no content at all. Blurring them would make the preview's most actionable row meaningless.
- **Every candidate reports its REAL source size**, even when dropped. That means reading notes the budget will not send — deliberate cost: the number that tells a user whether to raise the budget or cut a reference is how big the dropped note was. A note that cannot be read at all is not a section; reporting it as dropped would blame the budget for a missing file.
- **Over budget is reported, not absorbed.** When the never-truncated sections alone exceed the budget, every attachment is dropped and `overBudgetChars` says by how much. The run still goes out — refusing to review a long note would be worse — and the preview says so in words, without implying a fix that does not exist.

### One prompt-build entry point, which is what makes the preview trustworthy

Reviews, transforms/generations and push-back threads each had their own `assembleContext` + `composeSystemPrompt` pair. The preview would have made it four, and the fourth would eventually have disagreed with the other three. A trust surface that drifts is worse than no trust surface.

`buildEditorPrompt` is now the only way a system prompt gets built, and all four callers go through it. The spec that matters is in `context-preview-service.spec.ts`: it runs a REAL `startReview` against a capturing `fetch`, pulls the `system` field out of the request body, and asserts the preview's string equals it. Drift is now a test failure instead of a discovered lie.

### The preview surface

`previewEditorContext` resolves everything the modal shows: the exact system prompt, one section row per accounted part with what the budget did to it, the resolved backend (or the reason the editor cannot run — a prompt the user approves that no backend can carry is still a run that will not happen), and the two refusals as their own statuses. `excluded` names the Behavior tab, `rule-disabled` names the Rules tab and the rule; keeping them apart matters because the fixes are in different places, and "nothing would be sent" is the most important sentence a preview can produce.

It takes the editor as a **value**, not an id. That is what lets the editor settings dialog preview its unsaved draft — previewing the persona you are currently writing is the whole point of the button there.

Two entry points, deliberately different, both documented in code:

- **`preview-context`** (palette: "Preview what will be sent") reads the **live editor buffer**. Unsaved edits are what a review would send, so a preview reading vault state would describe a different request.
- The **Preview** button in the editor dialog reads the **vault** but previews the **unsaved draft**. The settings dialog covers the editor, so there is no focused markdown view to read a buffer from.

The modal re-resolves on every picker change rather than caching: each editor has its own persona, voice-profile opt-in and linked-note policy, so there is nothing shared to cache, and a stale panel here would be exactly the lie this surface exists to prevent. A `renderToken` guard drops an out-of-order resolve. The system prompt renders into a `<pre>` via `text` (no `innerHTML`), keyboard-reachable with an accessible name that says whose prompt it is, since the picker above it changes that. The modal sends nothing — its only injected dependency is `previewEditorContext`.

Copy updated where it was now wrong or thin: the Behavior tab's context-budget field states the spend order and points at the command; the editor dialog's "Include linked notes" toggle says links _and embeds_, one hop, that excluded notes are never attached, and that the budget applies.

## Custom actions grow up, and settings become portable (v1 sweep stage E, slice 3)

Plan M5's last two feature items (§4e). Five code commits plus this docs commit: `8b2b589` schema + verb registry + resolution, `7ab0c51` dispatch, `b83c530` Actions tab, `50fd566` the transfer module, `cd34766` the dialogs.

### A custom action was a rewrite, whatever its instruction said

`actionBindingSchema` already carried `customName` and `customInstruction`, and `action-resolution.ts` hardcoded `verbClass: 'transform'` for anything that was not a registry verb. So a custom action called "Check the numbers", with the instruction "flag every unsupported number", replaced the selected text with the answer. The instruction and the effect were unrelated.

`customVerbClass` (`transform` | `generate` | `review`) fixes that, and it is **required with no default**. That was the decision worth making: a Zod default of `'transform'` would have satisfied "class required" on paper while keeping exactly the bug above for every action whose author did not think about the dropdown. So a custom action with no class resolves to a new typed reason, `custom-class-missing`, and is offered nowhere — the same treatment a blank name or a blank instruction already received, surfaced the same way in the tab.

### One verb interface, because two would drift

`resolveActionVerb(actionId, custom?)` in the verb registry is now the only way a dispatch path turns an action id into the verb it runs: the registry entry for a built-in id, the custom action's own `ActionVerb` (label + class + already-resolved instruction) otherwise. Built-ins win over a supplied custom verb — a persisted binding must not be able to redefine what "Humanize" does behind the shared label.

The consequence in the controller is the interesting part. `startBoundAction` used to split on `verbClass` FIRST and then, on the transform branch only, resolve a custom instruction from the vault. A review-class custom action had nowhere to put its instruction, which is precisely why custom actions could not be review-class. Verb resolution now happens ahead of the split (`resolveBoundVerb`), so all three routes receive the same resolved verb — and a review-class custom action can bind a panel, because the panel rule was already written in terms of the class rather than in terms of "is it built-in".

Two asymmetries kept on purpose: the review branch reuses the already-resolved instruction across the size-confirmation round trip (the instruction rides inside `RunInstruction`), while the transform branch re-enters at the top and re-resolves. And an action whose instruction resolves to nothing still refuses with a Notice rather than dispatching — billing a backend to ask for nothing is worse than a refusal.

### `followLinks` on an instruction now means what it means everywhere else

The custom-instruction UI needed the note-refs control, and that control ships a "Follow links" toggle. Rendering the toggle and ignoring the flag would have been a lie, so `resolveCustomInstruction` now expands it with the SAME semantics as context assembly: depth 1, embeds count, deterministic link order, `FOLLOWED_LINKS_CAP` per referenced note, exclusions decided before any content is read, each note inlined once. Excluded notes are never followed either (Business Rules #7).

The instruction cap (`CUSTOM_INSTRUCTION_MAX_CHARS`) makes this safe: the direct text is serialized first, so the cap can only ever cut reference material, never the directive itself.

### Export and import: the key rule runs in both directions

`domain/settings/settings-transfer.ts` is pure and owns the whole contract; `settings/transfer-model.ts` owns every string the user reads; `settings/transfer-modals.ts` is glue that wires checkboxes and writes one file. Entry points live under Behavior → Import & export.

**API keys never travel.** Stripping happens inside `exportSettings`, the only function that produces an export, so no call site can forget. The import clears the field too — even when the file carries a key. That second half matters more than it looks: a `data.json` copied from another vault is a legitimate import source, and accepting its key would silently bill its owner's account. Both dialogs state the rule on screen, because "my keys are in this file" is the one wrong assumption a user could act on by sharing it. The advanced `extraBodyJson` field travels as-is; it is functional request configuration, and blanking it would break the backend it configures.

**Imports add.** Every imported entity gets a fresh id, and references inside the import are remapped onto the new ones. `resolveIdCollisions`' load-time semantics — keep-first, references untouched — were considered and deliberately not reused: there a duplicated id means "the same entity twice after a sync merge", so keeping references pointing at the survivor is right; here it means "a different entity from another vault", and keeping the reference would point an imported panel at the user's own editor. A reference to something OUTSIDE the import survives only when that id exists in the current settings, which is what makes re-importing panels back into the vault their member editors still live in do the obvious thing; otherwise it is cleared and reported as a typed adjustment.

`voiceProfile` is the exception: a single value cannot be added, so it replaces, and the summary says so in capitals before anything is written.

**Nothing is silent.** Elements are validated one by one, so a hand-edited entity never drops its siblings. Everything that cannot come in is a typed rejection with a reason the dialog spells out: invalid for this version, a panel none of whose member editors exist here, a built-in verb already bound (two bindings for one verb would give it two menu entries and make every lookup depend on array order), or a section already at its schema maximum. That last one is enforced while PLANNING rather than at save time, because the facade rejects a schema-invalid update wholesale and "could not save" names nothing; the cap constants mirror the schema and a spec pins the mirror against `pluginSettingsSchema` itself.

The format marker is not required on import — a foreign `data.json` has none. An object with no recognizable section is the error case, because that is when the user picked the wrong file.

## The panel can start a review (GitHub issue #16)

Two commits: `e749cf2` the pure gate + button state, `e0d85ab` the panel header and the dispatch.

### One gate, and it says why

`isReviewable` answered a yes/no. The panel button needs the same answer plus the REASON, because the whole point of the control is that it adapts to the bound note: an excluded note and a kill-switched note are both "no", and their fixes are in different settings tabs.

So `reviewGate` is now the single evaluation and returns `excluded` / `rule-disabled` (with the rule label) / `no-editor` / `ok`, with `isReviewable` and `isPluginEnabledForNote` as projections of it. A spec pins the projection in every case, which is the actual guarantee: an explanation cannot drift from the decision it explains, because there is only one decision.

The note-level half (`noteGate`) is split out so `isPluginEnabledForNote` never pays for the editor/backend scan it does not care about — it runs on every rail refresh of every open pane.

### The panel gained a header, not a button

`SidePanelBinding` requires a run. A Review button that only exists once a run exists is useless: a note with no findings yet is exactly when you want to start one. So the binding became the optional half of a `SidePanelState` whose other half is the review target, and the header (bound note name + button) renders regardless.

`setBinding` became `setPanelState`. The rename is not cosmetic — `setState` collides with Obsidian's `View.setState`, and the collision is a compile error rather than a silent shadow only because `noImplicitOverride` is on (AGENTS.md's reserved-name hazard, caught by tsc on the first run).

### Refusing, not cancel-replacing

`RunController.startRun` cancels the previous run for the same file. The rail's button turns into Cancel while running, which is right there — the rail sits in the editor, on the text. In the panel it would be wrong twice over: the panel is DISPLAYING that run's findings, and a click on a button that looks like "Review" would destroy them.

So the panel button refuses while a run or retry is in flight, gated on `canCancelRun` — the same predicate the `Cancel review or action` command uses. That is not a coincidence to be tidied away later: "a run is in flight" has exactly one definition, and the button refuses exactly when cancelling is possible. The check is re-done on click rather than trusted from the rendered state, because a run can start between the last render and the click.

A transform/generate run deliberately does NOT count as busy. `startReview` never replaces a transform run, so nothing is lost by dispatching alongside one, and the shared concurrency gate queues the request. The rail shows both as running because it has one button for both; the panel button is about reviews.

Busy is read through a THUNK, not captured as a boolean. The panel re-renders on run notifications without any push from the controller, so a captured value would leave the spinner turning after the run settled. The spinner itself is `aria-hidden` decoration — the label and the accessible name already say "Reviewing…", so announcing it twice would be noise — and it is static under `prefers-reduced-motion`, because a slow local model can legitimately spin for minutes (WCAG 2.2.2).

### A kill-switched note gets a disabled button, not a hidden one

Plan §4b says a matching `disabled` rule removes the plugin's chrome from a note, and the panel binding is indeed gone. Following that literally would hide the button too — and leave the user staring at a blank leaf they opened on purpose, with no way to learn that a rule emptied it.

The kill switch's promise is that nothing dispatches. A disabled button dispatches nothing. It also names the rule and the tab to find it in, which is the difference between an explained panel and a mysteriously empty one.

## The setup wizard, and M5 is feature-complete

Plan §4f. Two code commits — `540b2c0` the pure core, `592a464` the modal, its copy, the command and the first-run trigger — plus this docs commit.

### Nothing is written until Finish

The task allowed committing per step or at the end. Per-step commits sound safer and are not: they require every step to be independently valid, and the backend step is not. A label with no model is a backend that exists and cannot run — persisting it mid-wizard is precisely the "broken settings" the requirement was about.

So the wizard accumulates a draft and `applySetupWizard` turns it into ONE settings update. Cancelling at any step cannot leave a half-configured plugin because there is no sequence of partial writes to interrupt. The apply is a pure whole-value function, which is what makes "everything the wizard did not touch comes back identical" a spec rather than a hope.

### Empty is allowed; half-filled is not

Every step except the backend is optional by nature — which editors, which voice notes, which mode all have defaults. The backend step is optional too, and that matters: a user who wants to look around before pasting a key must not be trapped on step 2. But it refuses to advance with an incomplete backend, because that is the one input where some of it is worse than none of it.

The refusal reuses the Backends tab's rule rather than restating it. `domain/settings/backend-validation.ts` now owns what makes a backend usable, messages included, and the tab's dialog calls it instead of carrying its own copy of the checks. The messages live with the rule on purpose: each one IS the rule stated in words ("OpenAI-compatible backends need a base URL"), and splitting them into a copy module is how two surfaces end up enforcing the same requirement while explaining it differently.

### `onboarded` means "the wizard has had its chance"

The schema field already said it: "True once the setup wizard completed **or was skipped**." So any exit sets it — Finish, Cancel, Escape, the X. The alternative (only Finish sets it) turns an accidental dismissal into a modal that greets you on every launch, and the flow is re-runnable from a command and a Behavior → Setup button, so "seen" is never a one-way door.

Re-runs are edits, not resets: the draft seeds from the current settings. One deliberate exception — the wizard never edits an EXISTING backend. It adds one. Silently rewriting a configured backend from a flow called "setup" would be a surprise, and the Backends tab is where editing lives.

### The default-backend wiring is the difference between working and looking like it works

Editors inherit their backend. A wizard that added a backend without also making it the global default would end with a configured backend, six enabled editors, and nothing that runs — the exact state the wizard exists to prevent, presented as success. So a wizard-added backend becomes the default when there is none. When one already exists it is never repointed: a re-run must not silently redirect a working setup.

The same instinct drives the last step. It reports "nothing will run yet" from `hasReviewCapableEditor` over the settings about to be written — the predicate that knows about disabled backends, dangling references, missing models and per-editor overrides. Re-deriving an approximation of it inside the wizard is how a "you're all set" screen starts lying, so `setupOutcome` deliberately does not carry that field at all.

### Test connection tests the thing that matters

The cheap ways to test a connection answer a question nobody asked. A models-list GET or a bare chat completion goes green for an endpoint that authenticates perfectly and then fails every review, because the model will not produce the structured output the operation contract requires.

So the health check sends a real `review` operation over a one-sentence document through `createApiEditorExecutor` — the same path a review takes. A pass means "reviews will work here".

That produces **three** outcomes rather than two, and the third is the useful one: an endpoint that answers but whose payload the plugin cannot parse is `unusable`, not `failed`. Credentials and connectivity are fine; the model is not. Different sentence, different color, different fix.

Its timeout is 60 s, deliberately NOT `behavior.requestTimeoutSeconds` (ten minutes by default): a connection test that can hang for ten minutes is not a test. And because 60 s genuinely is not always enough for Ollama to load a cold model, the timeout message says a real run may still succeed with a higher request timeout — so a slow local model is never reported as a broken one.

### Two small implementation truths

Field edits skip the re-render, because text inputs must keep focus. That has a consequence the obvious code gets wrong: the Test connection handler must read the backend at CLICK time (a draft captured at render time would test the model as it read one keystroke ago), and its in-flight guard must key on the backend's **id** rather than object identity (every keystroke replaces the draft object, so identity comparison would discard the verdict for anyone who kept typing while the request was out).

And the keyboard: the forward button is focused on every step, so the defaults path is Enter, Enter, Enter through native button activation. A modal-wide Enter binding was written and then removed — with the CTA focused it fires alongside the button's own activation and advances two steps at once.

### Deviation worth recording

The last step's pointers name the command palette, the review command, the rail, the panel and the send preview, but **no documentation URL**. `docs/` is still the template stub (`docs/README.md` says "TODO: Add a brief description"), and shipping a first-run flow that sends new users to a placeholder page is worse than not mentioning it. Add the pointer when M9 fills in the docs content.

## Stage E review fix pass

External review of stage E (binding rules, context budget + send preview, custom actions + settings transfer, the panel Review button, the setup wizard) returned 17 findings. Every one was verified against the code before touching it; all 17 were real, and all 17 are fixed. Five code commits, privacy first: `06be0ff`, `47dd1f1`, `7de8c4c`, `ba85644`, `b42ba2c`, plus this docs commit.

### An imported backend is a destination, and the confirmation never showed it

The blocker. `planImport` cleared `apiKey` and kept everything else verbatim, and `importSummaryLines` reported counts — never a URL, never that an imported editor joins every review.

The stripped key is no protection. `resolveApiBackend` never checks for a key; Ollama's request builder needs only a model and a base URL; the OpenAI adapter requires a key for `openai`/`openrouter` and nothing else. Imported editors arrive enabled with `capabilities.review` on, and with no `assign` rule matching, `startReview` runs every enabled review-capable editor. So a foreign settings file — the documented import source, since a bare `data.json` with no format marker is accepted on purpose — could silently add a review participant that ships note text plus every linked-note attachment to a host the user never saw.

Two changes, and the second is the one that matters. API-family backends now arrive **disabled**, with a typed `backend-disabled` adjustment: enabling one means opening the Backends tab, which is where its URL is. And the confirmation now lists, per imported backend, its kind, the host it would send to (or "<kind> default" when it has no base URL — never a blank), and whether it carries a custom request body; plus a line stating how many imported editors would take part in every review of every note.

The equivalent honesty problem runs the other way on export. `EXPORT_KEY_NOTICE` asserted "API keys are never exported" and the dialog called the file "safe to share", but `exportSettings` strips only `apiKey`: `baseUrl` and `extraBodyJson` travel verbatim, because they configure the request and blanking them would break the backend. A gateway URL of the form `https://gw.example/v1?api-key=SECRET`, a `https://user:pass@host/v1`, or an `extraBodyJson` holding the token for a host that takes it in the body all end up in a file the dialog said was safe to hand over. Rather than redact functional configuration, the export DECLARES it: `exportSecretRisks` names the backends concerned and the dialog says why, and the notice now says the key **field** is never exported.

Deliberately broad detection (`@`, or a query key containing `key`/`token`/`secret`/`password`/`auth`/`sig`): a false positive costs one sentence, a false negative costs a live token.

### A cap that runs after remapping orphans every reference into it

`capSection` trimmed sections AFTER cross-references had been rewritten, so an entity dropped by a cap left survivors pointing at an id that would never exist — and no adjustment reported it, contradicting the module's own rule that every cleared reference is a typed adjustment. Reproduced: 199 existing editors plus an import of 2 editors and a panel over both yields `additions.panels[0].memberEditorIds = [gen-0, gen-1]` with `gen-1` never added, and `adjustments: []`.

The fix is ordering, not patching. Each section's survivors are settled first, in dependency order (backends → editors → panels → actions → rules), and only then are ids generated and references rewritten. A capped-out entity is therefore indistinguishable, to everything that referenced it, from an entity that was never in the file: the reference goes through the same `remap` path and comes out cleared and reported. Salvaged entities now carry their source index through every filtering pass, so a rejection names the position in the file rather than a position in an intermediate array — and the member pass still runs before the panel cap, so room freed by a memberless panel goes to the next one.

### `..` in the export path was resolved by the adapter, not by us

`normalizeExportPath` stripped leading slashes and appended `.json` and never looked at `..`. The result went to `vault.create`, whose adapter joins it onto the vault base path and resolves the traversal — writing outside the vault, past Obsidian's sandbox and past the dialog's `getAbstractFileByPath` existence check, which only ever sees in-vault paths and therefore skipped the overwrite confirmation for exactly the files least safe to overwrite silently. It now returns a typed refusal; backslashes are folded first so `..\escape.json` cannot slip through.

### The trust surface could not show what a custom action sends

`previewEditorContext` called `buildEditorPrompt` with no instruction and had no entry point that took a verb — yet `resolveCustomInstruction` inlines referenced vault notes into the dispatched instruction, up to `CUSTOM_INSTRUCTION_MAX_CHARS` (10 000). So up to 10 KB of vault content left the vault on every custom-action run without appearing in the one surface whose module doc promises that the prompt shown IS the string the adapter receives, and whose modal claims to show exactly the assembled context.

The preview now takes an optional action binding. `resolveBoundActionVerb` moved out of the controller into `action-resolution.ts` and both callers use it, so preview and dispatch cannot resolve different instructions — that shared function is the fix, the picker is just how it is reached. A review-class instruction is appended to the system prompt exactly as `startReview` appends it, so the byte-for-byte spec still holds with an action selected. A transform/generate instruction rides the operation payload instead, so it gets its own summary line with its own size and an explicit statement that it is not in the prompt and not in the budget — folding it into the budget report would have been a second lie, since the instruction obeys its own cap, not `contextBudgetChars`. The clipboard payload carries it too, for the payload case only: repeating a review-class instruction would misrepresent the request as sending it twice.

An action that no longer resolves is a refusal, matching the dispatch. The editor dialog's Preview button gets no picker on purpose — its question is about the draft persona.

### A regex from another plugin's settings ran unbounded on the UI thread

`mappingMatches` compiled and executed an OSK note-type `regex` mapping inside synchronous decisions that fire on every rail refresh, menu build and command gate. The `try/catch` covers `SyntaxError`; it does not cover catastrophic backtracking, and a hung renderer takes down the settings tab the user would need to reach to fix the pattern.

Patterns are now compiled once and cached (bounded, cleared wholesale when full), refused above 200 characters, refused when they carry a nested quantifier, and matched against a bounded slice of the base name. Refusing the shape is coarse and that is the right trade: a refused mapping recognizes one note type less, a pathological one freezes Obsidian. A spec runs `(a+)+$` against a 40-character non-matching name and asserts the elapsed time.

### One note-scoped answer to "who would review this note"

Two findings, one divergence.

## A panel run becomes one run (v1 sweep stage F, slice 1 — plan M6)

A panel used to be a fan-out: an action bound to a panel, or a rule assigning one, resolved the panel to its member ids and started N ordinary reviews that happened to begin together. Nothing downstream knew a panel had convened. This slice makes a panel run a first-class run — the members AND the aggregation step that follows them — and settles the partial-failure policy M6 required.

Three code commits: `6ffdb22` (charter seam), `ef41d84` (run + aggregation lifecycle), `89e8583` (dispatch), plus this docs commit.

### The charter is a shared brief, not a script for the chairperson

Plan §4 called `charterSource` "aggregation instructions", and the starter panel's charter was written to match: _"You are the chairperson of the Pre-publish Review panel. Four editors have each reviewed the same document… Produce: 1. A verdict per member…"_.

Two things are wrong with that once the charter has to reach the members. Read in a member's prompt it is nonsense — a member is not the chairperson and produces findings, not verdicts. And it re-specifies output the `aggregate-panel` operation prompt already dictates, in a contract-shaped way the user cannot change anyway (`kindRules` in `providers/prompt.ts` already says: never invent findings, record real disagreement in `dissent`, list failed members in `missingMembers`, rank `topFixes` by impact).

So the charter is now the panel's shared brief — what this panel is for and how it weighs things — and it plays both roles: appended to every member's system prompt, and used as the system prompt of the aggregation call. One user-authored field, no place for the two halves of one panel to disagree about what the panel is for. A second field ("brief for members" plus "instructions for the chairperson") was considered and rejected for exactly that reason.

The starter charter was rewritten accordingly: the publication bar, the four failure modes the panel exists to catch, the weighting rule (one load-bearing objection outweighs several shrugs), and an explicit instruction that every member keeps its own mandate. That last line matters — a panel that homogenized its members would be four copies of one editor, which is the opposite of why panels exist.

### It rides the existing seam, through the one prompt-build entry point

`augmentPanelCharter` sits next to `augmentSystemPrompt` and is applied inside `buildEditorPrompt`. Order: persona + context, then the charter, then the per-run instruction — the last block is the most salient, and the instruction is what the user asked for THIS time while the charter is standing context for every run of that panel. Because it goes through `buildEditorPrompt`, the "what will be sent" preview keeps showing the exact string the adapter receives.

Charter resolution needed the same `PromptSource` machinery a custom action's instruction already had: resolve fresh at dispatch time, never read an excluded note, never FOLLOW into one, inline each note at most once, cap the followed links, cap the total. That is four privacy/config guarantees in one loop and it was about to exist twice, so it came out as `resolvePromptSourceText` (services/context) parameterized by block tag and cap. `resolveCustomInstruction` delegates to it; `resolvePanelCharter` is the second caller. The persona/voice-profile path deliberately does NOT route through it — that produces budgeted `ContextAttachment`s with a reported drop list, a different shape with a different failure mode.

### Members are ordinary editor streams, on purpose

`StartRunInput.panel` adds the aggregation step and nothing else. Members go through the same anchoring, the same `FindingStore`, and the same plugin-wide `Semaphore` — so a four-member panel under `maxConcurrentRequests: 2` cannot starve another note's run (a spec pins the FIFO interleaving), and every finding keeps the `editorId` of the member that reported it. A panel weighs its members; it does not merge them, and nothing re-attributes a finding to the panel.

### Partial-failure policy — decided

`domain/panels/panel-aggregation.ts`, pure and spec-covered:

**The panel completes with the members that succeeded.** A member that failed is reported as failed, stays individually retryable inside the run, and travels to the chairperson with `failed: true` so the scorecard can state what it did not see. Aggregation runs as soon as at least ONE member succeeded; with none it reports `skipped` rather than billing a backend to synthesize emptiness.

The alternative — fail the whole panel when any member fails — was rejected. One member timing out on a laptop-hosted model is common enough that all-or-nothing would mean "usually nothing", and three honest reviews plus a named gap is strictly more useful than a refusal.

Two smaller decisions inside it. A member that finished with zero findings SUCCEEDED: a clean read is a real verdict, not a failure. And the failed members still travel in the request, because sending only the survivors would let the chairperson write a confident scorecard over a partial panel without ever knowing it was partial — the exact failure `missingMembers` exists to prevent.

Verified explicitly, since M6 asked: the stage-A per-editor retry machinery works inside a panel run. Retrying a member replaces its findings as usual, AND re-opens the panel — the scorecard that named it missing is about to be wrong, so it is discarded and re-derived when the run settles again. An attempt epoch guards it, mirroring the per-editor `runId` attempt check: a late aggregation settle carrying an older epoch belongs to a scorecard the run has already thrown away.

### Cancellation reaches the scorecard

`cancelRun` cancels every in-flight member and the pending or in-flight aggregation — the scorecard is a statement about a run the user just stopped. An already-produced scorecard is left alone, exactly like the findings of the members that did finish: cancelling stops work, it does not erase results.

### Dispatch: one path, so no surface can convene half a panel

`startReview` takes a `panel`, but the interesting case needs no caller at all: the rule outcome is resolved inside `startReview`, so a binding rule assigning an ENABLED panel makes the run a panel run for the command, the rail, the panel Review button, the CLI and the daemon at once. A DISABLED panel still supplies its members — the flag governs the panel as an aggregation entity, so turning it off drops the charter and the scorecard, not the reviewers. That is the promise `resolveRuleEditorPool`'s own header already made before M6 existed; it is now true rather than aspirational, and `RuleEditorPool` carries `panelId` to say so.

A review verb bound to a panel dispatches ONE panel run with its instruction on top of the charter. A daemon refresh carries the panel identity of the run it refreshes — dropping it would silently downgrade the note to loose editors.

`panel-unavailable` (missing / disabled) is its own refusal rather than falling through to `no-editors`: the members may be perfectly healthy, and the fix is in the Panels tab. Conversely, a panel whose aggregation backend does not resolve still RUNS — the members' reviews are the bulk of the value, and the scorecard reports `unavailable` instead of the whole run being refused over a settings mistake the user can fix after reading the reviews.

One tidy-up fell out: `resolveApiBackend` is now a thin call over a new `resolveBackendRef`, which the panel's aggregation backend uses. Two implementations of "inherit the default backend" would have drifted.

The scorecard UI (side panel + rail), the Panels settings tab CRUD, the editors-vs-panels visual distinction (Business Rules #11), CLI shaping of a panel run, and "Generate more" / `InsertAt`. Slice 2.

Specs: 1434 → **1472** (+38), per commit +11 / +19 / +8 — verified by running the suite at each commit, not by arithmetic on the diff.

Gates: `bun run format`, `bun run validate` (tsc + eslint --max-warnings 0 + 1472 tests), `bun run build` green after each commit. Nothing pushed.

### Open / live checks (UI not self-verifiable)

- Add a binding rule assigning the Pre-publish Review panel to a folder, then review a note in it: four editors run in parallel, the rail shows four chips, and every finding keeps its member's colour and name.
- Run "Preview what will be sent" on that note: the panel charter appears in the shown prompt, after the persona and before any action instruction.

- Point the panel's aggregation backend at a deleted backend: the members still review and nothing crashes.

## The scorecard is typed, budgeted and on screen (v1 sweep stage F, slice 2 — plan M6)

Slice 1 made a panel run one run and settled the partial-failure policy. This slice makes its OUTPUT a first-class thing: a typed `PanelResult` the aggregation must produce, an input that fits a budget, and two surfaces that render it.

Four code commits: `cdb9e4e` (contract), `ffdb4f8` (aggregation compaction + budget), `6bb0efb` (side-panel scorecard), `35e1ba1` (rail panel entity), plus this docs commit.

### `topFixes: string[]` and `dissent: string` were the two weakest fields in the contract

Both were already there; both were the wrong shape for what the panel is for.

A top fix that reads _"tighten the opening paragraph"_ leaves the user to find the span themselves — even though the member that reported it quoted that span verbatim, two fields away. So `topFixes` is now `{ action, editorName?, quote? }`. The pointer is **optional and stays optional**: a legitimate top fix can be structural ("cut the second half") and anchor to no single span, and a pointer the model invented to fill a required field would be strictly worse than none.

`dissent` as one string invites the model to average four readings into one balanced sentence and lose which member held which position. That is the exact information a panel has and a single editor does not, so it is now `{ subject, positions: [{ editorName, stance }] }[]` — subject and positions in separate fields, so no surface downstream can merge them, and an empty array stays a valid "they agreed". The prompt rules say not to report a difference of emphasis as dissent, because a schema that rewards filling the field would get it filled.

Two smaller additions: `recommendation` gained a one-line `rationale` (a verdict token states a conclusion without stating why), and the aggregation request's members gained `omittedFindings`, filled by the budget below.

### The aggregation request had no budget, and would have been truncated by the model

A four-member review of a long note produces hundreds of findings, each carrying anchoring aids, evidence and a full replacement suggestion. Sent raw that request is several times the size of the note the members read — and the thing that then truncates it is the MODEL, silently, in the middle, with no record of what it dropped.

`domain/panels/panel-aggregation.ts` now does the dropping, and reports it.

**Compaction** is unconditional and per field. `prefix`, `suffix`, `occurrence`, `confidence`, `rationale` and `evidence` go: the chairperson weighs members — it never anchors a span, re-verifies a source or applies a replacement. `critique`, `suggestion` and `summary` are clipped to fixed caps. **Quotes are never truncated**, because a `PanelTopFix` points back at its finding BY QUOTE and a shortened quote comes back as a pointer that resolves to nothing or, worse, to the wrong span.

**The budget** is half of `contextBudgetChars`, minus the charter (which IS the aggregation call's system prompt, and is never truncated for the same reason a persona is not) and the member envelopes, with a floor so a user who set a small review budget still gets a usable panel.

**Fitting is round-robin**, one finding per member per pass. Filling member by member is the obvious implementation and the wrong one: a spec pins the exact case where sequential filling spends everything on A and B and leaves C — the last member of the panel — entirely unheard, while the scorecard claims to weigh it. Round-robin gives C a turn first.

A member whose next finding does not fit **leaves the rotation**; its remaining findings are omitted even when a later, smaller one would have fit. Skipping one and taking the next would present the member's list as something other than a prefix, and a prefix is exactly what `omittedFindings` promises — which is what lets the chairperson reason about what it did not see. Truncation is never per finding: half a critique changes what the member said, while a shorter list of complete findings is honest and countable.

### The scorecard renders above the member sections, never instead of them

`ui/panel-scorecard.ts` is a pure projection with its own specs; the side panel only turns it into DOM.

It produces a view for **every** aggregation status — waiting, running, failed, cancelled, skipped, no backend — and the member sections render underneath it in all of them. There is no branch anywhere that hides the run because the synthesis failed: an aggregation that dies costs the user a summary, never the four reviews they paid for, and the failure copy says exactly that ("the member reviews below are unaffected"), with the redacted backend message under it. `unavailable` names the setting that fixes it.

A member that failed is listed even when the chairperson never mentioned it, marked "No review — not weighed". Silence about a member that did not run is the failure `missingMembers` exists to prevent, and the prompt tells the model not to speak for it.

**Top-fix resolution** (`resolveTopFixFinding`) matches the fix's quote against the live findings: exact inside the credited member, then exact anywhere, then the same two passes on whitespace-and-case-normalized text. The normalized pass runs LAST so an exact match is never displaced by a fuzzy one (a spec pins the case where the credited member's finding only matches after normalization and another member's matches exactly — the exact one wins). No match means no pointer, and the row renders as plain text rather than a button: revealing the wrong span is worse than revealing none, because the user acts on it (Business Rules #4), and a control that cannot act must not look like one.

Dissent renders as structure — subject, then each member's position — never collapsed.

`verdictLabel` (All good / Needs work / Not ready) moved out of `side-panel.ts` into its own module. An editor's verdict and a panel's recommendation are the same vocabulary; two relabelings would eventually have disagreed about what `kill` is called.

### The rail shows the panel as one entity (Business Rules #11)

The rail rendered a panel run as N loose editor dots, indistinguishable from four unrelated editors that happened to start together.

A panel run is now ONE **hollow ringed** chip inside a bracketed group holding its member dots. Editors stay SOLID: the distinction is shape, so it survives at 16px and does not depend on colour. Editors that are not members keep their place outside the group — a panel weighs its members, it does not absorb them.

The chip projects the scorecard's lifecycle through the SAME mapper the side panel uses (`scorecardStatusKind`), so the two cannot disagree about where the aggregation stands, and the overall verdict rides it as a badge. `(panel)` is in the accessible NAME, not only in the shape — a ring is invisible to assistive tech, so #11 would otherwise hold only visually. Selecting it opens the side panel: a verdict, ranked fixes and dissent do not fit in a tooltip. The compact rail keeps the ring and drops the badge (no room at 12px); the tooltip carries it.

One pre-existing defect fixed on the way: `applyTooltip` wrote the tooltip into `aria-label`, clobbering the name the Review button set immediately before it — so the compact button's accessible name was the narrow-pane guidance rather than what the control is, which is precisely the split the stage-D fix pass introduced the two fields for. The name is now a parameter defaulting to the tooltip.

## Editors stop looking like panels, and an editor can be asked for more (v1 sweep stage F, slice 3 — plan M6)

### Business Rules #11 was being satisfied four times, in four wordings

The rule says editors and panels must be distinguishable in every surface. Four surfaces each had their own answer, and each was half an answer.

The rail wrote `(panel)` inline in the chip's accessible name. The settings dropdown wrote `◎ Name (panel)`. The scorecard header drew a ring and then printed the bare name. The context menu and the palette said **nothing at all** — an action bound to a four-member panel read exactly like one bound to a single editor, so the surface where the choice costs the most was the one surface that did not mention it.

`ui/entity-label.ts` is now the one author, with the two decisions stated in it rather than rediscovered per surface:

**The distinction is never carried by shape or colour alone.** A ring is invisible to a screen reader and unreadable at 12px to plenty of sighted users, so wherever a panel is named, the name says `(panel)`. The glyphs are an addition.

**Only panels are marked.** An editor is the unmarked default — it is what the rest of the plugin is already about — so tagging both kinds would turn the marker into noise and stop it standing out. That asymmetry is why `entityName` takes the kind rather than the caller picking a helper.

Applied to: the rail chip and the group holding its member dots, the target dropdowns, the scorecard header, the side-panel member sections (an indent plus an `aria-label` naming the panel they belong to — while keeping the editor's own name, because a panel weighs its members and does not absorb them), the editor context menu and the dynamic action commands.

A panel-bound verb now reads `Critique (panel: Pre-publish Review)`. The panel is NAMED rather than merely flagged: one press there is one request per member, so the user is choosing a cost, and "which panel" is what tells them how big it is. Menu **ordering** deliberately still sorts on the bare label — the marker is about which kind the action convenes, and letting it move `Critique` under `C (panel…)` would shuffle a menu people navigate by verb. `ResolvedAction` carries `panelName` for this: one lookup at resolution time rather than four surfaces each finding the name for themselves and eventually wording it differently.

### "Generate more" is the mirror image of Retry, and the difference is the whole feature

`RunHandle.continueEditor` asks one editor for MORE findings. Every respect in which it differs from `retryEditor` is deliberate:

- a retry REPLACES the editor's findings (they came from a failed attempt); a continuation KEEPS them and appends;
- a retry clears the dedupe keys (the new attempt may legitimately re-report); a continuation keeps them, so a literal repeat is dropped on arrival;
- a retry is for `error`/`cancelled`; a continuation is for `done` only. A failed editor has nothing to build on, and a running one is already working.

**Not repeating itself is handled twice, because either mechanism alone is weak.** The request carries `alreadyReported` — quote plus clipped critique, enough to recognize the ground covered without re-sending suggestions, evidence and anchoring aids the editor does not need in order to avoid itself — and the prompt reframes the pass as an additional one, forbidding repeats and rephrasings and _explicitly_ allowing an empty result, because a second pass is exactly the situation that invites padding. Whatever ignores all that still hits the retained dedupe keys. `alreadyReported` is ABSENT rather than empty on a first pass, so a backend can tell "nothing yet" from "found nothing".

### The failure policy is what makes the feature safe

A continuation that fails or is cancelled does **not** put the editor into `error`/`cancelled`. It restores `done` and records `continuationError` separately.

Marking it failed would be the obvious implementation and a data-loss bug: `error` and `cancelled` are exactly the statuses that offer **Retry**, and Retry replaces an editor's findings. One click, immediately after an optional extra pass timed out, would destroy the first pass's findings — the ones the user was in the middle of triaging, and the only reason they pressed the button in the first place. So the editor stays finished, the failure renders as a note beside the button, and Retry is not offered at the moment it would do the most damage.

The same reasoning governs summary and verdict: a continuation that reports neither leaves the first pass's standing. It was an _additional_ pass, so silence about the note as a whole means "nothing to add", never "withdraw what I said".

New findings anchor against the text passed in at call time — a fresh per-editor anchor base, exactly like a retry (Business Rules #3/#4) — so the extra round reads the note as it is now, which is also what the user is looking at. A member going back to work re-opens its panel's scorecard, which named which members it weighed and what they found and is about to be wrong; `reopenPanel` is now shared with `retryEditor` instead of duplicated.

### The count is in the button because the button costs money

`Generate more (n)` sits under each finished editor's bulk row — the opposite move to bulk triage, acting on the same list, which is why it belongs there. `n` is how many findings are already on the note.

A bare "Generate more" would read as a free refresh. With the count it reads as "add to these three", which is what it is, and the number changing after a round is the feedback that the round did something.

The button **disables rather than disappears** while its own round runs: a control must not vanish under the pointer that just pressed it, and that is also what makes one press one round — a double click cannot buy two. There is no auto-repeat and no "keep going" mode.

An editor sitting at `(0)` still gets the button. "I found nothing" is a real answer, and it is worth challenging once.

The count comes from the findings the section shows and is deliberately **not** the severity-filtered list: the lens hides findings from view, it does not un-report them, and telling an editor it found fewer than it did would invite it to repeat them.

`Generate more findings` in the palette does one round for every finished editor of the active note's run — the whole-note gesture, keyboard reachable. Still one round each.

### The starter charter had no opinion about ranking

Slice 2 made top fixes ranked and pointed at a span, dissent a structure of attributed positions, and the recommendation carry a rationale. The `aggregate-panel` operation prompt dictates all of that as FORMAT. Nothing supplied the judgment behind it, so the model was being asked to rank by nothing and to preserve a disagreement it had no reason not to average.

Two paragraphs added at charter level: rank by what unblocks publication (blocking first, then what visibly improves the document, polish last or not at all), prefer a concrete action tied to the exact passage over a description of the problem — a fix the author cannot locate is a fix they will not make; and keep disagreement as the positions actually held, attributed, rather than a middle nobody argued for, while a difference of emphasis stays not a disagreement.

Both read correctly in the charter's other role. It is appended to every member's prompt, and "name the blocking problem first, quote the passage, do not soften what you disagree with" is advice a single member can follow as written.

## Stage F review fix pass — and the CLI finally sees a panel (v1 sweep stage F — plan M6)

### "Settled" was answering the wrong question

`isSettled()` derives from the editor states, and `maybeAggregate()` only opens the aggregation once it is already true. So a panel run reported itself settled for the entire time its scorecard request was in flight — and every busy gate in the plugin keys on that predicate. Cancel disappeared from the palette at the one moment there was a single request left to cancel, `ai-editor cancel` answered `already-settled`, the rail swapped its spinner for Review, the side-panel Review button started a run that cancel-replaced the aggregation, and the daemon's probe read the note as free. `cancelRun`'s own documentation promises to cancel "the pending/in-flight aggregation"; that branch was unreachable from every user surface.

The fix is not to redefine `isSettled` — two consumers need it exactly as it is (`maybeAggregate` would deadlock on itself, and the CLI's `settled` promise is about the member streams). `isBusy()` is the new question: **is anything still running**, editors plus a waiting/running panel. Six surfaces ask it now; `isSettled` keeps its two callers and a doc comment saying which is which.

### A continuation does not invalidate what it adds to

`continueEditor` reused `reopenPanel()`, which nulls the scorecard. For a retry that is right — a retry REMOVES the editor's findings, so the top fixes point at spans that no longer exist. For a continuation it is backwards: the findings are all still there, so every member verdict still holds and every fix still resolves. Worse, the loss was unrecoverable: `cancelRun` moves a `waiting` panel to `cancelled` and never re-aggregates, so cancelling the extra round left the run with **no scorecard** while the editor sat back at `done` with its original findings — the exact asymmetry `terminate` and `cancelRun` already implement for `state.continuing`, missing from the panel half.

`reopenPanel({ keepResult })` states the difference in one word. A continuation keeps the result and marks it `resultStale`; the side panel says so in one line above the block ("From the previous round — a member is generating more, so this will be rewritten") rather than presenting it as current or hiding it. A re-aggregation that then fails or is cancelled leaves it alone — which is what `cancelRun` said all along.

### The scorecard is model text; it is now checked against the run

`memberVerdicts[].editorName` is a string the chairperson wrote. Nothing verified it, so a panel that invented a member — or merely misspelled one ("Beginner Reader" for "Beginner") — produced a row for an editor that never ran AND hid the real one, unless it happened to also be in `missingMembers`. `PanelRunState.memberNames` carries the roster; unknown names are dropped and every roster member the panel did not name is listed as `unnamed` (distinct from `missing`: one is the chairperson's silence, the other is the run's own record that no review exists). This is `resolveTopFixFinding`'s stated policy — "returns null rather than guessing" — applied to the function one screen above it that was guessing.

The same function had the mirror defect: its cross-member fallback is deliberate (a fix may quote a finding the credited member did not report), but the row still displayed the model's credit. A row reading "Hater" that reveals Beginner's finding asserts a provenance the click contradicts. `resolveTopFix` returns the candidate, and the credit follows the resolution; the model's name stands only when nothing resolved, which is the structural-fix case.

## The CLI security boundary (v1 sweep stage G, slice 1 — M7)

M7's first slice is the seam itself, built before any tool adapter so that no CLI backend can ever be wired up around it. Nothing is user-reachable yet: `review-service` still refuses `cli-backend-unsupported`, and the `SkipReason` stays until slice 2 has a tool speaking a protocol. Three commits: `988ee58` (the three checks before anything starts), `fff53ba` (process-tree kill), `c403c14` (the spawn itself). New folder: `src/app/services/backends/cli/`.

Business Rules #9 listed the properties; this is them, as code.

### Node access — the precedent, set once

Nothing in `src/` imported a Node module before today. The plugin is `isDesktopOnly: true` (BR #5), so the renderer is an Electron one with Node available, and `scripts/build.ts` already leaves `node:*` external (verified: a bundle including this folder emits `require("node:child_process" | "node:fs" | "node:fs/promises" | "node:os" | "node:path")` and inlines nothing). The imports are confined to **two** files — `node-fs.ts` (executable probe + throwaway directory) and `node-process.ts` (child creation + tree kill) — so the plugin's entire Node surface is two files a reviewer can read end to end, and everything else in the folder stays runtime-agnostic and spec-covered without a process.

### The executable is the user's path, and nothing else

`validateExecutablePath` requires an absolute path to an existing, executable regular file. This is a security rule, not a nicety: a bare name would be resolved through the PATH the renderer inherited from the user's login shell, so a writable directory ahead of the real one silently turns "review this note" into "run whatever is called `claude` today"; a relative path would resolve against the working directory, which the boundary deliberately keeps disposable. The child still GETS a `PATH` for its own sub-tools — documented as a trade-off, and never consulted for what we launch.

Windows scripts (`.bat`, `.cmd`, `.ps1`, `.vbs`, `.js`, `.wsf`) are refused by extension with their own reason, because running one means running `cmd.exe`/PowerShell, which re-introduces the command-line quoting rules this boundary exists to avoid — the same reason Node itself refuses them without `shell: true`. The check runs before the existence check, so a user pointed at `claude.cmd` is told what is actually wrong instead of being sent looking for a missing file. A NUL byte is refused before touching the filesystem: it truncates the path inside the OS call, so what runs would not be what was checked.

### The environment is built from empty

`process.env` in a desktop renderer carries tokens for unrelated services, an ssh-agent socket, proxy credentials, `NODE_OPTIONS`. `buildCliEnv` starts from `{}` and adds back three kinds of entry, each with a stated reason: what the tool cannot start without (`HOME` — where `claude`/`codex` keep the user's login; `SystemRoot` and friends on Windows), what it resolves its own sub-tools with (`PATH`, the one real trade-off), and what the user explicitly configured (API-key variable names). Explicit configuration is consent; a wildcard is not.

Two variables are SET rather than forwarded: `TMPDIR`/`TEMP`/`TMP` point into the run directory so an agent's scratch files share the run's lifetime, and `NO_COLOR`/`TERM=dumb` because ANSI escapes on stdout would corrupt the JSON protocol. A deny list refuses loader/runtime/shell-hook injection names (`LD_PRELOAD`, `DYLD_INSERT_LIBRARIES`, `NODE_OPTIONS`, `BASH_ENV`, `GIT_SSH_COMMAND`, the proxies, `PATH`, the temp variables) **even when explicitly configured**, matched case-insensitively — a user pasting one of those is confused or being socially engineered, and both end the same way. Refusal, not silent dropping: a user who asked for a variable and did not get it would debug the tool, not the setting.

### The sandbox the caller cannot widen

`spawnCliProcess` takes no `cwd`. It creates a `mkdtemp` directory (owner-only, unpredictable name) and removes it in a `finally`, so "an agent that writes files must not land them in the user's notes" is a property of the signature rather than a rule. Deliberately not the plugin's own data folder either — `.obsidian/plugins/ai-editor/` is inside the vault, so anything written there is a file the user's sync engine replicates and their vault search finds.

Likewise `createCliChild` is the only door into `node:child_process` in the plugin and its options type has no `shell` field, so `shell: false` is the only reachable state rather than an overridable default. Arguments cross as an array; no command line is ever assembled.

### Content on stdin, and only there

`stdin` is a separate input field from `args`, and arguments are capped at 4096 characters with a message that says where content belongs. The boundary cannot detect a note in argv, but it can make the mistake fail immediately instead of publishing the note to every process listing on the machine (argv is world-readable in `ps`).

### Bounded output, with different policies per stream

stdout is the protocol: a truncated JSON document is a corrupt answer, not a smaller one, so exceeding the cap (8 MiB) stops the capture, fails with `stdout-overflow`, and kills the tree. stderr is diagnostics: nothing downstream depends on it being complete, so exceeding its cap (64 KiB) drops the OLDEST bytes and keeps the tail — where the error is — with `truncated` set. **This is a deliberate deviation from "fail when exceeded" for stderr**, taken because the requirement's actual point (bounded memory) is met either way and a chatty tool should not lose its result over its own progress logging.

stderr comes back as `StderrDiagnostics`, whose `summary` is status-only ("The tool wrote 412 bytes to its error stream"), whose content sits behind a `reveal()` call, and whose `toString`/`toJSON` both return the summary. A CLI tool routinely echoes its own configuration, and its configuration routinely contains the key it was given (BR #12) — so interpolating this object into a Notice or serializing it into an error report cannot leak the transcript by accident. In product code `${diagnostics}` is additionally a lint error (`restrict-template-expressions`).

### Killing, verified rather than assumed

An agent is not one process. On POSIX the child is spawned into its own process group, so `kill(-pid)` reaches every descendant and `kill(-pid, 0)` answers "is anything in there still alive?" — that probe is why the group is worth having. On Windows, `taskkill /T /F` from an explicit `%SystemRoot%` path. Escalation is graceful → bounded grace → forced, and the result is a value: `already-gone` / `terminated` / `force-terminated` / `survived`. `survived` is the one outcome the boundary could not make safe, so the caller gets it instead of a silent leak. The liveness check runs BEFORE the first signal, because an exited pid can be recycled and a stale `-pid` is a live process group belonging to someone else; `killProcessTree` refuses pid ≤ 1 and our own pid outright.

### Lifecycle details that are races if you get them wrong

Listeners are subscribed synchronously with the spawn — a short-lived child can exit before the next microtask, and a handler registered after an `await` misses the event and hangs until the timeout (reproduced while probing, then designed out). `close` is preferred over `exit` because it means the pipes drained too, but a grandchild that inherited them can hold `close` open forever, so `exit` starts a bounded 1 s drain and settles regardless; the leftover tree is killed on the way out. A clean-looking exit with `child.exitCode === null` also triggers the kill, because that means only the pipes drained. `stdin` gets an error handler: a tool that exits without reading its input breaks the pipe, which is the tool's business and not a plugin crash. Nothing throws out of `spawnCliProcess` — the caller is a run that must end in exactly one terminal state.

### The conformance suite runs real processes

`spawn.spec.ts` spawns `process.execPath` on an inline script rather than mocking a spawn seam. The properties under test — an environment that really is empty, a working directory that really is the throwaway one, content that survives the pipe byte for byte, a sleeping grandchild that really dies — belong to the OS's view of the child, and a mock would assert none of them. Both runtimes (Bun in tests, Electron's Node in Obsidian) accept `-e`, so one fixture exercises one code path.

Covered: happy path; malformed JSON returned verbatim for the protocol layer; no output; slow output vs timeout (including partial stdout kept); huge output vs cap; runaway stderr truncated without failing the run; non-zero exit; signal death nobody asked for; cancel terminating a sleeping grandchild with **both pids probed until gone**; a tool that arms a SIGTERM handler being force-terminated; stdin round-tripping newlines, both quote styles, `$VAR`, backticks, backslashes, pipes, semicolons, tabs and unicode; 512 KiB of stdin; a tool that exits without reading its input; argv arriving verbatim with no word splitting, substitution or globbing (`$(touch /tmp/pwned)` asserted not to have run); the run directory gone afterwards, cancellation included.

Still not user-reachable, and deliberately so — see "What slice 3 owns" at the end.

### The flags were read off the binaries, not remembered

Every flag emitted here came from `claude --help` (2.1.220) and `codex --help` / `codex exec --help` (@openai/codex), both on 2026-07-30, and then from running the exact argv the code emits — success path and failure path — against the real tools. Nothing is carried over from an SDK, a blog post or a memory of an older interface.

That mattered immediately, because two things would have been got wrong by reasoning alone:

- **Claude Code reports `subtype: "success"` on a failed run.** A run against a non-existent model came back with `subtype: "success"`, `is_error: true`, `terminal_reason: "api_error"`, `api_error_status: 404`. Keying off `subtype` — the field whose name says outcome — would have reported an API failure as a successful answer whose text happened not to be JSON, i.e. as a model that "produced invalid output". `is_error` is the authoritative flag.
- **Codex emits error events that are not failures.** A run that completed normally still emitted `{"type":"item.completed","item":{"type":"error","message":"Model metadata … not found"}}` — a warning. A run that really did fail emitted five top-level `{"type":"error","message":"Reconnecting… n/5"}` lines before the terminal `{"type":"turn.failed"}`. Treating anything error-shaped as terminal would have failed perfectly good runs; treating the first error as the outcome would have reported a retry as a failure.

Both tools exit **0** on those failures. The exit status says the CLI ran, not that the request worked, so the envelope has to be read even after a clean exit.

### The invocations, and what each flag buys

```
claude --print --output-format json --no-session-persistence \
       --strict-mcp-config --permission-mode manual [--model M] [--tools '']

codex exec --json --color never --skip-git-repo-check --ephemeral \
           --sandbox read-only [--model M] -
```

`--no-session-persistence` and `--ephemeral` are the two that are about the user rather than the protocol. Both tools otherwise write the whole session to disk under the user's home directory — so reviewing a note the user deliberately excluded from AI would leave a verbatim copy outside the vault, outside the vault's exclusion rules, and outside anything this plugin could later delete (Business Rules #7, #12). Off on every path, consent or no consent.

`--strict-mcp-config` with no `--mcp-config` means "no MCP servers" instead of "whatever the user configured globally". An MCP server is an arbitrary program with network access; inheriting the user's set would hand the note to processes the plugin never mentioned.

`--skip-git-repo-check` is required rather than convenient: the boundary runs every tool in a throwaway directory that is deliberately not a git repository, and `codex exec` refuses to start in one without it. The refusal exists to stop an agent editing an unversioned tree; nothing here is edited and the directory is deleted when the run ends.

`--tools ''` goes **last** because `--tools` is variadic and swallows following non-option arguments. There is no positional prompt for it to eat either — the prompt is on stdin.

### Consent, stated honestly rather than uniformly

Claude Code has a real off position: `--tools ''` (the help's own spelling for "disable all tools"). So its adapter reports `canGrantTools: true`, and turning the backend's `allowTools` on removes that flag and nothing else — `--permission-mode manual` still stands, so what the agent actually gains is the tools that need no approval, in an empty throwaway directory. The dangerous values (`bypassPermissions`, `--dangerously-skip-permissions`) are emitted by no code path, spec-asserted for both consent states.

Codex has no such flag. Running shell commands is not a Codex feature that can be switched off; it is how Codex answers at all. So its adapter reports **`canGrantTools: false` and its argv does not vary with `allowTools` at all** — a toggle that silently did nothing would be worse than no toggle. What the plugin can state truthfully is the containment it does enforce: `--sandbox read-only` (no writes, no network from model-run commands), in a directory that exists only for this run, with an environment built from nothing. Granting Codex more than that is out of scope until there is a bound the plugin can actually enforce, which is the "do not ship what you cannot make safe" rule applied to a feature rather than to a bug.

`--ignore-user-config` was considered and rejected. It looks like isolation, but `~/.codex/config.toml` is where a user's provider, endpoint and model live — ignoring it would silently redirect the run away from the setup the user tested. That is a correctness bug dressed as a security measure, and it is the same reasoning that already forwards `HOME` so the tool can find its own login.

### One prompt entry point, one output contract

The API path splits its request in two: persona in the provider's system-prompt field, operation payload in the user message. Both CLIs have a system-prompt flag, and both are argv — which is the one place the boundary refuses to put content (`ps` is world-readable, and arguments are capped at 4096 characters precisely so a note cannot end up there). So the two halves are concatenated into one stdin payload with the persona delimited, and the operation half is `buildUserMessage` — the same function every API adapter calls — in its `'json-object'` style.

That style is not a preference; it is what is left. `--json-schema` (Claude Code) serializes the operation schemas to several kilobytes, well past the argument cap. `--output-schema` (Codex) takes a FILE path, and the boundary owns the only directory the run has. So the schema is embedded in the prompt, and Zod remains the enforcement boundary — which it was anyway.

A closing directive is appended after the operation's own output rules, because an agentic CLI is chattier than a chat completion: its final message is a report to a human by default, and a report wrapped around the JSON is the most likely way a CLI run fails where the equivalent API run succeeds. The parser was **not** widened to compensate: it tolerates exactly what `extractJsonPayload` already tolerates for API responses (a whole-string markdown fence). Instruct strictly, parse leniently, and never hunt for the first `{` in text the plugin does not control — the same doctrine `protocol.ts` was written with.

### The executor the orchestrator cannot tell apart

`createCliEditorExecutor` has the same signature as `createApiEditorExecutor`, the same exactly-one-terminal-event protocol, the same error vocabulary — and the same result validation, `extractJsonPayload` + `validateOperationResult`. A result that arrived over a pipe from a program on the user's machine is not more trustworthy than one that arrived over HTTPS; having passed through a general-purpose agent, it is arguably less so.

Failures map without guessing. `cancelled`, `timeout` and `stdout-overflow` have honest equivalents; everything else the boundary can report is `unknown`, because a process that exits non-zero because the user is logged out looks exactly like one that exits non-zero for any other reason, and a confident wrong diagnosis is worse than an honest vague one. `auth` and `rate-limit` therefore only ever come from an envelope the tool itself filled in.

Messages stay status-only, and three things are added because they are safe and useful: the **stderr summary** (a byte count, never the content — the difference between "exited with status 1" and "exited with status 1 and had something to say"), the **timeout setting's name** on a timeout, and a plain sentence when the process tree **survived**, which is the one outcome the boundary could not make safe.

Nothing tool-authored reaches a user-visible string. A shape-checked status token gets through (`/^[a-z][a-z0-9_]{0,39}$/`, dropped **entirely** rather than truncated when it does not match — a truncated secret is still a leaked secret) and so does a reported HTTP status number. The tool's own error text never does: the live Codex failure carried the full endpoint URL including query parameters, and Claude Code's failure `result` quotes back the configuration that caused it.

No `progress` events. The boundary hands over a bounded capture after the process has ended, so there is genuinely nothing incremental to report and every adapter's `capabilities().streaming` says `false`. A heartbeat here would make "the model is working" indistinguishable from "the pipe is open" — the exact confusion the slow-model work removed.

### The suite does not need the binaries

The adapters are pure, and the executor takes the boundary as an injected function, so the whole slice is spec-covered on a machine with neither `claude` nor `codex` installed. The envelopes in the fixtures are the real ones, copied from live runs including the failure shapes.

Three invariants are asserted for **every** tool rather than per tool, so a future adapter cannot quietly break the boundary's assumptions: argv always passes `validateCliArguments` even with a 16 KB persona (content stays on stdin), capabilities never claim streaming until it is verified, and a hostile payload with a secret in every plausible field never reaches the failure message.

## CLI backends become reachable, behind two consents (v1 sweep stage G, slice 3 — M7)

Slices 1 and 2 built the boundary and the two tool adapters and deliberately left them unreachable. This slice is the surface: settings, consent, health check, and the dispatch widening — landed together, because shipping any one of them earlier would have made a CLI backend reachable before there was a place to ask permission. Four commits: `a120cc0` (consent model), `926d9dd` (dispatch), `86eb529` (health check + detection), `6b23f79` (settings UI), plus this docs commit.

### `allowTools: boolean` was the wrong shape, and the reason is `data.json`

The schema already had `allowTools: z.boolean()`. Read it once more with Business Rules #12 in mind — `data.json` lives in the vault and syncs — and a boolean is not consent, it is a claim that travels. Machine A's "yes" arrives on machine B as permission to launch whatever `executablePath` happens to say there. The same applies to a settings import and to a hand-edited file.

So consent is stored as **the executable path it was granted for**: `consent: { launchPath, toolsPath }`, `''` meaning not granted. `hasLaunchConsent` is true only when the recorded path equals the configured one, and `hasToolsConsent` additionally requires launch consent, so tool mode can never outlive permission to start the process at all. Edit the path, import a file, merge a sync conflict — the record stops matching and the backend reads as not-consented, which is the state where nothing runs.

That also gave a state worth naming: `stale` (you consented, to a different binary) is not `missing`, and the dialog says so — "the executable path changed since you allowed this backend" rather than a first-time ask that would be a lie.

Dropping the boolean removes the possibility of drift entirely: there is now exactly one persisted fact per decision, and the Claude Code adapter reads `hasToolsConsent(config)` rather than a flag someone could set independently. Two spec cases pin the failure modes that boolean allowed — consent recorded for a different binary, and tool consent with no launch consent — both keeping `--tools ''` on.

**Transfer is where this bit immediately.** Export now blanks a CLI backend's consent record the way it blanks an API key — an export that says "allowed to run /Users/alice/.local/bin/claude" is a decision about one machine and one user, written into a file people paste into issues. The executable path itself stays, the same way `baseUrl` does: functional configuration, declared rather than blanked.

And on the other side:

**Import is where this bit hardest.** `planImport` already forced API backends off and cleared their keys, but a CLI backend passed through untouched: a shared JSON file could have arrived carrying `enabled: true` plus a matching consent record and started launching a local program. Imported CLI backends now arrive switched off AND unconsented, with their own adjustment line, because a file cannot establish that a user was shown what launching a program means.

### One factory, so "works everywhere" is structural

The refusal was one line (`family !== 'api'` → `cli-backend-unsupported`), but four call sites built executors by hand — reviews, panel aggregation, transforms, threads — each with its own `redactSecret(message, backend.apiKey)` and `reviewTimeoutMs(behavior)`. Deleting the refusal alone would have left four places that could each be widened wrongly, or forgotten.

`backends/backend-executor.ts` is now the only place a resolved backend becomes something the orchestrator can run, and no dispatch surface branches on `family` any more. Three things legitimately differ and are decided there once:

- **The executor.** The two `create*EditorExecutor` functions have deliberately identical signatures, so the caller cannot tell them apart — a property slice 2 built for and this slice cashes in.
- **The timeout.** A CLI backend carries its own per-backend budget rather than borrowing `requestTimeoutSeconds`. Forcing them to share one number means either cutting agents off mid-run or letting a hung HTTP request sit for the length an agent needs.
- **Redaction.** A CLI backend holds no key of ours — the tool authenticates out of the user's own login, which the plugin never reads — so redaction is identity. Wiring in a scrub that has nothing to scrub would advertise a protection that is not there; what actually keeps tool output out of user-visible strings is the executor's status-only messages (slice 2).

`resolveBackendRef` now resolves both families, and the consent check lives there: an enabled CLI backend without matching launch consent resolves to the typed skip `cli-consent-required` and is reported like any other skip, everywhere skips are reported. That covers every path the sweep asked about, because every one of them goes through this function: editors, panel members, panel aggregation, transforms, threads, "Generate more" (it reuses the run's stored executor), the `ai-editor:review` CLI handler and the daemon (both call `startReview`), and the "what will be sent" preview.

One asymmetry is deliberate: an empty model is a configuration error for an API backend (the request body needs one) and legal for a CLI backend (the tool ships a default that tracks its vendor's current recommendation). `resolvedBackendLabel` renders that as "Claude Code (tool default)" rather than an empty pair of brackets, which would read as a bug.

### The health check runs the real thing, and the detector runs nothing

These two pull in opposite directions and both are right.

`checkBackendHealth` now accepts both families and goes through `createBackendExecutor`, so a CLI probe really does spawn the tool, in the throwaway directory, with the allowlisted environment, under the boundary's timeout and process-tree kill. A probe that took a shorter path would certify a configuration nobody has exercised — worse than no probe, because the user would believe it. The probe is bounded per family (120 s for a CLI agent, which starts a runtime, reads its config and authenticates before answering) and clamped down to the backend's own timeout when that is shorter, so it can never outlive the setting it is testing. Failure messages name the setting that applies to THAT family: pointing a CLI user at the Behavior tab's request timeout would send them to a control that does nothing for them.

Detection is the opposite. It never runs anything — confirming with `--version` would start a program the user has not consented to yet, which is the exact act the consent dialog exists to gate — and it **never scans `PATH`**. Scanning would find more, and would faithfully surface whatever a writable directory ahead of the real one contains, presented as "found Claude Code here", one click from consent. `executable.ts` refuses PATH resolution for that reason; a suggestion list is not a safe place to reintroduce it. So detection is a curated list of official install locations, probed through `validateExecutablePath` — the boundary's own gate — because a suggestion the plugin would later refuse is not a suggestion, it is a trap.

**Windows returns no candidates at all.** Both tools install there as npm `.cmd` shims, which the boundary refuses; offering them would read as a recommendation for something the plugin then refuses to run. The summary says that plainly instead of reporting a failure. A Windows user with a real `.exe` can still paste its path. This is the "do not ship what you cannot make safe" rule applied to a convenience feature.

### Consent copy is spec-pinned, because the words are the decision

`settings/cli-consent-copy.ts` holds both dialogs as data. Consent only means something if the user was told what they were agreeing to, so what they are told is under test: the responsibility sentence, the named executable, the containment lines, "nothing runs until you ask", and the withdrawal line. A refactor of the modal cannot quietly drop any of them.

The two dialogs are deliberately unequal. The first leads with "starts a program on this computer, with the content of your notes on its standard input — you are responsible for what that program does", and the containment (temporary folder, minimal environment, no session on disk, cancel kills the tree) comes AFTER as supporting lines, so it cannot be read as "this is sandboxed, so it is fine". The second leads with the extra reach — read and write files, reach the network — states that it is a bigger permission, and admits the plugin cannot see or limit what the tool does with the network. A spec asserts the second is not a reworded copy of the first.

For Codex the tool row is not a toggle at all: `canGrantTools` is false (slice 2's honest capability), so the row states why and describes what is enforced regardless. A toggle that silently did nothing would be worse than no toggle.

### Where each consent is asked for, and why there

- **Launch consent** is asked at the moment permission is needed: flipping a CLI backend's enable toggle in the Backends tab. Cancelling writes nothing; agreeing records the permission and the enablement in ONE commit, because enabled-without-consent and consented-without-enabled are both states the user did not ask for. Withdrawing switches the backend off for the same reason.
- **The same dialog** appears from the CLI backend dialog's own "Allowed to run" row and from **Test connection**, through one entry point so the wording and the recording cannot diverge. Test connection needs it because the test IS a launch; a "just checking" path around consent would make the consent decorative.
- **Tool consent** is only in the backend dialog, only after launch consent, and `grantToolsConsent` refuses to record it otherwise — so the ordering is structural, not a UI convention.

The Backends tab row shows the consent state under a CLI backend's name. Without it, an enabled-but-unconsented backend looks like a working one and the user only finds out from a skip report after asking for a review.

## Stage G review fix pass (CLI boundary, adapters, settings, docs)

External review of the M7 slices (process boundary, tool adapters, CLI settings
and consent) returned 16 findings. Every one was checked against the code before
being touched; the three that could be reproduced with a real process were
reproduced first. All 16 are fixed. Nothing was skipped, but one proposed fix
was deliberately NOT taken — see "the flag that was not shipped" below.

Commits: `b046e89` (spawn boundary: tree kill, abort refusal, env pass-through
removal), `863494e` (Windows kill through the gate), `80a4185` (consent at the
executor seam), `fa5da22` (settings surfaces), `b453515` (docs + the NUL byte),

- this docs commit.

### Security, in the order it mattered

**1. A leftover process tree survived a clean exit — never killed, never
reported.** The guard was `ending.reason !== 'exit' || child.exitCode === null`,
and `child.exitCode` is non-null after any `exit` event carrying a status, so
the branch its comment described ("the child is still there and only the pipes
drained") was unreachable. Reproduced against a real child: a tool that spawns a
grandchild and then `process.exit(0)` returned `ok: true`, `kill: null`, and the
grandchild was still alive after `spawnCliProcess` resolved — with the run
directory, which is the survivor's `TMPDIR`, deleted out from under it. This is
the ordinary shape of an agent that starts an MCP server, a watcher or a
language server, not an exotic case.

The tree is now probed on EVERY path. `runKillEscalation` opens with a liveness
check, so a tool that genuinely finished costs one `kill(-pid, 0)` and reports
`already-gone` — the happy path pays one syscall for a guarantee that used to be
a comment.

**2. `survived` is now reachable on a successful run, and fails it.** `kill`
moved onto the shared outcome base. When the tree could not be stopped, the
executor emits an error rather than the result. The reasoning, written down
because it gives up a good review: containment is the premise the consent dialog
was granted on, the run contract has no durable place to hang a warning on a
successful result (`lastProgress` is transient and is not rendered anywhere),
and README plus the consent copy both promise the user is told. Discarding the
answer costs a review; it does not cost the leak, which happened either way.
`survived` is only reachable after SIGKILL to the whole group failed, so this is
rare by construction.

**3. An already-aborted signal still executed the program.** The check sat after
`createCliChild` and after stdin had been written; whether the tool's own code
ran before SIGTERM landed was a race. Reproduced: a pre-aborted controller came
back `cancelled` with `kill: 'terminated'`, and `'terminated'` is only reachable
when the escalation's first `isAlive()` returned true — the process really was
created. The refusal now runs before anything is allocated and again immediately
before the child is created. `createCliEditorExecutor` keeps its own pre-check,
but the guarantee no longer lives in the caller.

**4. The Windows kill was the one spawn outside the chokepoint.** `sendWindows`
passed no `env`, so `taskkill.exe` inherited the renderer's full environment —
exactly what `env.ts` exists to prevent for the tool itself — and its path was
concatenated from `SystemRoot`/`windir` with no `validateExecutablePath` call,
so a poisoned value redirected the kill at an arbitrary binary that then ran
with that environment. Now: the path goes through the same gate the user's own
executable passes (`SystemRoot`, then `windir`, then the literal system
location), returns null rather than guessing when none is a runnable program,
and the spawn goes through `createCliChild` with an environment of `SystemRoot`
and `windir` derived from the validated path. Impact was bounded — Windows only,
and poisoning the renderer environment implies prior code execution — but a kill
path outside the chokepoint does not belong in the module whose design premise
is that the chokepoint is the only way through.

**5. Consent was enforced on one path, not at the seam.** `checkBackendHealth`
starts a real process (deliberately — a shorter probe would certify a
configuration nobody exercised) but bypassed `resolveBackendRef`, the only place
consent was structural. The only gate was the dialog's own pre-check. No bypass
was reachable today; the defect was that consent had become a convention in the
subsystem whose whole premise is that it is not. The refusal moved into
`createBackendExecutor`, the one place a resolved backend becomes runnable for
both families. Pinned by a spec whose backend points at a path the boundary
would reject on its own: the message is about the missing permission, which it
could not be if the process seam had been reached.

### The half-built thing that was removed rather than finished

`passThroughEnvNames` / `passThroughNames` had no production caller and no
schema field, while README, the user guide and `env.ts` all described it as a
shipped part of the environment policy. It is deleted, not completed: adding a
settings field, a dialog row and the threading is a feature, and a fix pass is
not where a new door into the child environment gets opened. `buildCliEnv` now
takes nothing user-supplied, cannot refuse, and returns the environment
directly — which also retired the unreachable `invalid-environment` failure code
and the denied-names list that guarded a door that no longer exists.

The consequence is recorded rather than hidden: a user whose `claude`/`codex`
authenticates from `ANTHROPIC_API_KEY` in their shell has no way to forward it.
That was already true; only the docs claimed otherwise.

### The flag that was not shipped

Two doc findings had a tempting code fix: emit `--setting-sources` so that
"Claude Code sees none of your plugins / no pre-approved permissions" becomes
true instead of being corrected.

Checked against the binary rather than assumed. `claude --help` (2.1.220, on
this machine) documents `--setting-sources <sources>` as "Comma-separated list
of setting sources to load (user, project, local)", and an empty list IS
accepted — a real run with it completed normally under OAuth. What could not be
established is what it actually drops: the help says nothing about plugins,
hooks or skills, and the obvious external measurement (comparing system-prompt
token counts with and without) is confounded by prompt caching, which made the
two runs incomparable in both directions.

So it is not emitted. Shipping a flag as a security control on the strength of
its name is precisely how the false guarantee got written down in the first
place, and the mandate for this stage is that anything which cannot be made safe
is reported rather than shipped. What went in instead is the truth, in the three
places a user meets it. Revisit with a real before/after on a machine that has
plugins and pre-approved permission rules configured.

## Comments that outlive the session (v1 sweep stage H, slice 1)

M8's persistence layer. A margin comment is a question the user parked on a span; the promise is that they close Obsidian, reopen it, and it is still there, still in the margin. Three commits: `c3c665a` (domain: schema + re-anchoring), `f69eea9` (sidecar repository), `a0664f3` (Obsidian glue + lifecycle).

### Where it lives — decided, with the alternative argued down

ONE `comments.json` in the PLUGIN DATA FOLDER (`manifest.dir`, falling back to `Vault.configDir` — the config folder is user-configurable and the lint rule that catches a hardcoded `.obsidian` is right), keyed by vault-relative note path.

Per-note sidecars next to the notes (or a frontmatter block) were the real alternative and were rejected on three counts:

- **The vault stays clean.** This plugin writes nothing into a note without a visible diff and an Accept. Scattering machine-written files through the user's folders is the same violation with extra steps — they surface in searches, in the file explorer, in every "all files" query, in the Git diff of a versioned vault.
- **Sync conflicts land where they hurt least.** Obsidian Sync, Syncthing and iCloud all conflict-copy per file. A conflicted `comments.json` costs plugin state; a conflicted sidecar pollutes the folder the user is working in, and a frontmatter block would conflict the NOTE — turning a background comment into a merge conflict on the text being written.
- **One file, one code path** for rename handling, corruption recovery and atomic writes, instead of N.

Not `data.json` either: settings hold API keys and are rewritten on every settings change, and comment traffic must not ride along with either. Schema-versioned; per the no-users policy there are no migrations, but the version field ships because after release a migration hook needs somewhere to read a version from, and adding it later means guessing at unversioned files.

### Positions are resolved, never restored

The schema deliberately has no offsets. A comment persists `quote` + `prefix`/`suffix`/`occurrence` — the same locating vocabulary a finding carries — and is re-anchored on load through the SAME `matchQuote` engine, because the note may have been edited by another device, another plugin, or the user in a different app while Obsidian was closed. A stored offset would look authoritative while pointing at unrelated text.

Three outcomes, and the vocabulary is the contract with the margin UI: `exact`, `fuzzy` (matched only after typographic normalization — anchored, and its `anchoredText` is sliced from the SOURCE so any later precondition compares real text), `orphaned` (not found, or found in places the hints cannot tell apart). An orphan is KEPT and shown with its quote. Deleting a user's parked question because they rewrote a sentence would break the one promise the feature makes, and guessing it into a position is exactly what Business Rules #3/#4 forbid.

### Rename moves, delete drops

Rename re-keys the exact path AND any folder prefix, idempotently — so the glue does not have to know whether Obsidian emitted a per-file event, a folder event, or both. A folder rename that emitted no child events would otherwise orphan every comment under it at once. (The vault hooks are deliberately NOT guarded on `TFile` for the same reason.)

Delete drops the entry. The tombstone alternative was considered and rejected: the only thing a tombstone can key on is the PATH, so a note later created at `Drafts/Post.md` would silently inherit comments written about a different, deleted note — attaching a stranger's critique to the user's text, the exact failure mode the anchoring rules exist to prevent. It also grows without bound, and buys back only the narrow regretted-delete case: Obsidian's own file recovery restores the note TEXT, never plugin state, so the promise a tombstone appears to make is one it cannot keep.

### Corruption is preserved, never overwritten

Salvage granularity is ONE COMMENT (a malformed entry must not cost its siblings; a malformed note entry must not cost the other notes) — the settings loader's rule applied to data the user cannot retype. Any load that is lossy at all — unparseable JSON, an unusable top-level shape, or a single dropped entry — copies the bytes to a timestamped `comments.corrupt-*.json` BEFORE anything can write, never overwriting an existing backup (it takes the next free name). The plugin loads either way, with a Notice saying what happened and where the file went. If the copy itself fails, the repository refuses to write for the rest of the session: losing this session's comments beats losing the file.

### Write discipline

Debounced (2 s), and coalesced: at most one write in flight, and mutations landing during one fold into exactly ONE follow-up write rather than one write each. The payload is staged in `comments.json.tmp` and renamed over the store, so a crash between the two leaves the previous store intact instead of a truncated one. Adapters differ on renaming onto an existing path (POSIX replaces, Windows refuses), so the fallbacks are explicit and ordered by how much they risk: remove-then-rename (the temp still holds the full payload), then a direct overwrite as the last resort. A failed write keeps the changes dirty so the next mutation or flush retries them. `onunload` flushes — fire-and-forget, since Obsidian's `onunload` is synchronous, which is why the debounce is short.

Reads are synchronous by design (`load()` fills memory once at startup): the margin renders on every note open and refresh cycle and must never await disk.

### In-flight statuses cannot survive a restart

`submitted`/`running` describe the current session only. Read back from disk they mean the session died mid-job, so the loader normalizes them to `interrupted` and reports the ids. Nothing resumes: a resumed request is a backend call this session never authorized (Business Rule #1), which is why M8 says Retry and never fake resumption.

New Business Rule #13 records the whole contract.

## Background comment runs, and jobs that admit they died (M8 stage H, slice 2)

Slice 1 gave margin comments a place to live. Slice 2 makes them actually run in the background — and makes a job that was in flight when Obsidian quit say so instead of pretending. Five code commits plus this docs commit: `2638cde` (pure lifecycle), `0728810` (background admission gate), `38d7374` (the comment run), `ab3512e` (registry + dispatch), `180cc1e` (side panel + plugin wiring).

### Interrupted, never resumed — spelled out

A backend request dies with the process. Nothing about it can be recovered: no id to poll, no partial output, no way to tell whether the provider ever answered. So a job in flight at shutdown becomes `interrupted` and offers **Retry**, which is a brand-new request the user asks for. It is recorded from BOTH sides — `CommentJobRegistry.interruptAll()` at unload, and the load-time normalization in `loadCommentStore` — because either path can be the one that runs (a clean unload gets the first, a crash gets the second) and they must agree on the outcome.

The alternative, resuming, would be two lies at once: a backend call the user did not authorize in this session (Business Rules #1), and an answer presented as belonging to the original ask when nothing connects them. The UI wording carries it: the row says "Obsidian closed while this was running. Nothing was resumed — retry to ask again.", and the button is **Retry**, never "Resume".

`failed` was added as a status distinct from `interrupted`. Both offer Retry, but a failed job knows why it ended (`error` holds the redacted message and the row shows it) while an interrupted one knows nothing at all. Collapsing them would force the margin to either invent a failure reason or hide a real one. The schema version stays at 1 on purpose: widening an enum leaves every file written under version 1 valid, nothing branches on the version yet, and a bump with no migration and no reader would record a compatibility break that did not happen.

Retry re-anchors before it asks. The span is resolved against the note as it reads NOW (never restored from a stored position — Business Rules #13), the hints are recomputed from where it actually landed, and a quote that is gone REFUSES (`orphaned`) rather than falling back to a whole-note review: re-asking about text that no longer exists returns an answer about something else under the original question. The comment is kept, still retryable if the text comes back.

### The starvation policy — decided, and the reserve is not the interesting half

Background jobs share the ONE plugin-wide budget. Anything else would let parked comments blow past a limit the user set to control cost and rate limits. But sharing a budget FIFO is not enough: the user is present for a review and absent for a comment.

`BackgroundRequestGate` admits a background job only when

```
gate.queuedCount() === 0  ∧  gate.activeCount() < cap - 1
```

The **reserve** (`cap - 1`) is the obvious half — it keeps a slot the foreground can take without waiting. The **empty-queue clause** is the half that actually makes starvation impossible: `Semaphore` is strictly FIFO, so a background waiter that JOINED the queue would be admitted ahead of a review queued behind it, reserve or no reserve. Because the test only ever passes when the semaphore would admit synchronously, a background job never occupies a queue position at all — it waits outside and re-checks on an injected timer. Foreground callers keep using `Semaphore.acquire` directly and are never ordered behind background work. Spec-pinned with the exact scenario: pool full, one foreground waiter queued, one background job waiting; freeing a permit must hand it to the foreground.

The trade is deliberate and it costs the background side: a busy vault can leave a comment queued indefinitely. That is the right way round.

At `cap = 1` the reserve would be the entire budget, so the limit floors at 1 — a background job may take the single permit, but only while nothing is active and nothing is queued, delaying a foreground request by at most one job. Refusing to run the feature was the alternative and it is worse: a user who serializes their backend has not asked for margin comments to be dead. Preemption (killing a running background job when a review arrives) was rejected outright — the request is already paid for at the provider, and the user would watch a comment die every time they pressed Review.

### A third orchestration shape, and why

|                        | review run              | transform run      | comment run             |
| ---------------------- | ----------------------- | ------------------ | ----------------------- |
| keyed by               | file                    | file               | **comment id**          |
| survives a note switch | run does, view does not | no                 | **yes**                 |
| survives a restart     | no                      | no                 | **as `interrupted`**    |
| admission              | `Semaphore` (FIFO)      | `Semaphore` (FIFO) | `BackgroundRequestGate` |

Keyed by comment, not by file: the user can park several questions on one note and none of them is "the" run for that note. Bound to no view, so closing the note, opening another one or collapsing the pane changes nothing. It shares the event protocol (runId matching, exactly-once terminal, post-terminal discard, stream-end-without-terminal = `invalid-output`), the redaction seam and the budget with the other two. It anchors nothing — the answer is persisted as raw quotes and re-anchored when displayed, because anchoring at produce time would bake in offsets for a document the user has been editing the whole time the job ran.

`rawFindingIdentity` was extracted to `domain/operations/finding-identity.ts` so the review pipeline and the comment pipeline cannot drift on what a stream-vs-result duplicate is.

**No new operation kind.** A margin comment is a `review` scoped to the span, with the question carried as the per-run instruction (`commentInstruction`). Inventing a seventh request kind would have meant a second prompt serializer, a second result shape and a second set of protocol tests for the same conversation. The instruction quotes the span verbatim, repeats the verbatim-quoting contract (a background answer is re-anchored days later, so a paraphrased quote does not degrade — it orphans permanently), and explicitly allows a note-level answer so the editor does not manufacture a finding to have something to return.

### The registry is the join, and it follows notifications rather than promises

`CommentJobRegistry` is the one place the durable comment and the live run are kept agreeing, so a job can never be `running` on disk with nothing running. Status changes are driven by the run's OWN notifications, not by its `settled` promise: `cancel()` terminates a handle synchronously while the aborted stream may still be winding down (or, for an executor that ignores its signal, never wind down at all), and a cancelled job must become durable at the moment it is cancelled. A cancelled job is `interrupted`, not `failed` — nothing is known about why it ended.

The registry also owns the once-a-second ticker, started and stopped with the in-flight set: a surface must not poll to keep an elapsed timer honest, and a plugin that schedules a 1s interval forever to animate nothing is a battery bug. The elapsed time counts from when the request STARTED (permit granted), not from when the comment was parked — counting queue time as work time would make a waiting job look like a slow one. A restored `interrupted` job shows no timer at all: the only honest elapsed time for it is unknown.

Writes follow the vault. A comment whose note was renamed mid-flight is located by id and updated under its new key; a comment whose note was DELETED mid-flight is not resurrected.

### Dispatch, in the same order as everything else

`startCommentJob` is shaped like `startReview` / `startAction` / `startThreadTurn`: exclusions fail closed before anything is read (BR #7), the binding-rule kill switch refuses before any dialog can appear (plan §4b), then the size guard — a comment sends the whole note as context, unlike a thread turn which sends only a quote and a critique, and the user IS present when they park one, so the confirmation round trip is the same one reviews use — then one named editor resolved fresh, then context assembly (the vault IS the config), then the durable record, then the request. A rule's `assign` target deliberately does not override the comment's editor: a comment names who it asked, exactly like a push-back names the editor that produced the finding.

`spanHints` is the inverse of `matchQuote` — findings arrive with locating hints, but a user-created comment has to derive its own from the document. The guarantee is spec-pinned as a round trip: hints produced there re-anchor to exactly the span they were taken from, including for repeated and self-overlapping quotes.

### Surface: the side panel, not the status bar

Jobs are listed in a side-panel section (pure projection in `ui/comment-jobs-model.ts`; the `ItemView` only renders it). The status bar was the alternative and was rejected: it already carries the finding count, it is global chrome every note pays for, and a per-second timer there would put a permanently-animating element in the user's peripheral vision for a feature they are deliberately not watching. The side panel is opened on purpose, is already the narrow-pane fallback for everything else, and is where the M8 margin column will fall back to.

Rows show who was asked, the question, the state, the live timer and only the affordances that state offers (Retry / Cancel / Dismiss). What needs attention sorts first; the rest keeps stored order (history that reshuffles while you read it is worse than history). Dismissed comments are hidden but not deleted. The section is absent entirely when nothing is parked. Accessible names fold state and timer into one sentence, identically-labelled buttons say which comment they act on, and the status uses tabular figures so a ticking timer does not shift the row every second.

The section renders even when the note has no run — that IS the state a background job is usually observed in.

**Not shipped**: the margin column itself, and the UI that CREATES a comment (the service and the registry are complete and spec-covered; slice 3 gives them a selection affordance and the margin column). Nothing here assumes either.

- With a job in flight, the side panel row ticks `Reviewing 0:01`, `0:02`… and the row does not jitter as the digits change; when it finishes the ticker stops (no permanent 1s interval).
- Quit Obsidian with a job in flight, reopen: the row reads **Interrupted**, says nothing was resumed, and offers **Retry**. No request fires on load.

- Set `Max concurrent requests` to 2, park two comments, then press Review: the review starts immediately (the reserve) rather than waiting behind them.
- Set it to 1, park a comment, press Review while it runs: the review waits for at most that one job, and no background job ever overtakes it.
- Cancel a running job: the row becomes Interrupted immediately (not on the next stream event) and Retry appears.
- Dismiss a job: the row disappears from the panel and does not come back after a reload.
- Rename the note while a job runs: the answer still lands on the comment under the new path. Delete the note while a job runs: nothing is written back.
- Screen reader on a row: one sentence naming the editor, the state and the elapsed time; the Retry/Cancel/Dismiss buttons say which comment they act on.

## Performance passes: measured, then fixed (M9 stage I, slice 2)

The plan's M9 line is "performance passes (large notes, many findings)". Nothing here was chosen by intuition: a benchmark suite landed FIRST, calibrated to the code as it stood, and every change afterwards is justified by a number the suite prints. Six commits — `96142c5` (the suite), `17ae9ad` (anchoring), `dce515a` (context), `a15973e` (word diff), `f560297` (pathological-input guards), plus this docs commit.

### The suite comes first, and it asserts ceilings

`src/app/perf/perf.bench.spec.ts` runs under `bun test` like everything else and alone with `bun test perf.bench`. `src/app/perf/bench.ts` holds the harness (warm-up, median of three, one printed line per measurement) and deterministic fixtures (seeded LCG, numbered sentences so most spans are unique — a fixture of repeated filler would exercise the ambiguity path on every quote and measure the wrong thing).

Assertions are **ceilings, not targets**, sitting far above the measured median: a benchmark asserting a tight number is a flaky test on someone else's laptop, and one asserting nothing is a comment. What they catch is the thing that actually happens — an accidental O(n²) turning 20 ms into 2 s. Tightening a ceiling is a deliberate act made by the commit that earned it, so the git history of that file IS the record of what each fix bought. Benchmarks carry a 180 s per-test timeout because Bun's 5 s default reports "timed out" where the suite wants to report "2 872 ms".

Sizes are the documented pathological cases, not averages: a 200 000-character note (well past the 8 000-word size warning), 200 findings (the operation contract's per-result cap), 500 comments (`MAX_COMMENTS_PER_NOTE`).

### What the numbers said

**The matcher was the freeze.** `matchQuote` normalizes the whole document on its second rung, and it did so PER CALL. Every caller that matters resolves many quotes against one text — a review ingests up to 200 findings against its snapshot; the margin re-anchors up to 500 durable comments **on every refresh cycle**, i.e. while the user types. A comment whose quote no longer resolves never hits the exact rung, so 500 orphans meant 500 full normalizations: 7.2 s per keystroke batch on a large note.

`createQuoteMatcher(text)` binds a document and normalizes it at most once, lazily (a batch that all hits the exact rung never pays at all). `matchQuote` becomes that matcher used once, so there is still exactly one ladder and no second implementation to drift. `AnchorBase` now carries a matcher instead of a text (`anchorBaseText` where the text itself is needed), and `reanchorComments` builds one for the batch. Hints are also normalized once per call instead of once per candidate.

The one-shot form is kept, and kept measured at a smaller n (`matchQuote (one-shot) ×25 missing quotes / 200k note`, ~372 ms), so anyone tempted to loop it reads the price in the suite instead of shipping it.

**Context assembly read the same notes once per editor.** Assembly is per editor and a run has many; eight panel members over one note each walked the same link graph, resolved the same wikilinks, re-checked the same exclusions and re-read the same attachments. `createCachingVaultReader` answers each question once and `startReview` wraps the injected reader with it.

Scope is the whole point and it is deliberately narrow: one per RUN, thrown away with it. A longer-lived copy would answer with a note the user has since edited, moved or excluded — silently sending content the exclusion rules would now refuse (Business Rules #7). Within a run the freezing is CORRECT rather than tolerated: every member of a panel must be briefed on the same vault. Nulls and empty lists are cached like any other answer; a rejected read is not, so the next caller retries instead of inheriting a rejection forever; `getOutgoingLinks` hands out a copy so a caller that sorts the result cannot corrupt the cache. Spec-pinned that the run still attaches every note to EVERY editor — a cache that read less and sent less would be a bug wearing a benchmark's clothes.

**The word diff was fast and useless above the budget.** The cost guard degraded an over-budget region to one struck block plus one inserted block: measured, a 30 000-character 25 % rewrite produced **2 changed segments** — the user's whole selection in red, the whole replacement in green, and no indication of what changed. The threshold bit early, too: ~1 400 words was enough, so most whole-note transforms lost the word diff entirely.

The region is now split on tokens occurring **exactly once on each side** (the patience-diff idea): such a token can only align one way, so it is a safe anchor; the longest increasing subsequence of those pairs keeps the anchors monotone; each gap between anchors is small enough for a real LCS. Whitespace never anchors — it is the most repeated token in any text and a lone one aligns nothing. A region with no unique common token still degrades coarsely, which is the one case where a before/after is the honest answer. `MAX_SPLIT_DEPTH` bounds stack depth against an adversarial input that yields one anchor per level; real text never reaches it.

Result: 2 → 1 670 changed segments on the benchmark, and 0.9 ms → 8 ms. A 200 000-character rewrite diffs in 47 ms with 10 852 segments and the reconstruction invariants intact; a fully repetitive input (no unique tokens at all) still takes the coarse path in 1.2 ms.

### Left alone on purpose

The decoration set, the margin model and exact-pass anchoring were measured and NOT touched. 2 000 marks rebuild in ~1.2 ms and remap on a keystroke in ~0.06 ms; `markStaleEffect` over 2 000 marks costs ~0.5 ms — the incremental stale path the M3 work built is already doing its job. `marginColumnModel` + `marginModelKey` over 500 comments is ~2.4 ms, and the re-anchoring cache stage H added (keyed on the CM `Text` identity and the comments' revisions) already keeps the scroll frame off that path. 200 verbatim quotes anchor in ~11 ms. Optimizing any of these would have been work with no number behind it.

### Pathological input: one guard added, two verified

**Added — the decoration cap.** A single result is capped at 200 findings, but a note's marks are the SUM over the run's editors, and nothing stops a user enabling twenty. `MAX_DECORATED_FINDINGS` = 2 000 (`ui/editor/decoration-budget.ts`, pure and spec-covered). Not to rescue CodeMirror — 10 000 marks rebuild in ~6.4 ms — but because the marks are one of several per-finding costs paid on the same cycle (building the specs, keying them, rendering the list), the cycle fires on every edit batch, and those costs are additive. The cap bounds the editing loop by the DOCUMENT rather than by how many editors are enabled.

The rule is the first 2 000 **in document order** — observable and stable, unlike "the first 2 000 the store happened to hold", which reshuffles when an editor finishes — plus the keyboard-triage cursor wherever it stands, because triage can step to any finding and a cursor on an unringed span is a broken affordance. Under the cap the input array is returned untouched, which is the only path real usage takes. Nothing is hidden: every finding stays in the store, in the list, in the counts, acceptable and dismissable, and the side panel states how many are listed but not highlighted — a plugin that quietly stopped highlighting would look broken rather than bounded.

**Verified — a runaway response.** It is already bounded by the operation contract, and now by specs that say so: 10 000 findings, 201 findings, an oversized quote / critique / suggestion / replacement / reply, and a >1 MB body are each refused as `invalid-output` (the 1 MB case parses and is refused in well under 2 s). This is also WHY a note cannot accumulate ten thousand highlights from one run — no backend emits per-finding stream events, so findings only ever arrive inside a validated result. CLI stdout is separately capped at 8 MB (`cli/capture.ts`).

**Verified — the link graph.** Depth 1, `maxLinkedNotes` ≤ 20, `FOLLOWED_LINKS_CAP` = 20 per referenced note, `contextBudgetChars` bounding what is sent. Pinned against a complete 500-note graph: 20 attachments and 20 reads, not 500 and not 500²; following from a prompt ref attaches the root plus one capped hop; a 1 000-character budget on that graph sends ≤ 1 000 characters and still reports all 22 sections.

### Corrections the audit produced

1. **Findings do not stream in.** `usage.md` said Review "streams their findings in as highlights". The streaming path emits `progress` events and reassembles the payload at stream end — incremental finding extraction is out of scope by design (`api-editor-backend.ts` header comment). What arrives progressively during a multi-editor run is editors finishing at different times, and the docs now say that. Also recorded: Anthropic and the OpenAI-family kinds stream; Azure OpenAI and Ollama run buffered regardless of what their `capabilities()` reports.
2. **Context-menu order was reversed.** `editor-menu.ts` builds actions → Review selection → Ask for comments… → Ask an editor….
3. **Margin comments were still "coming next".** M8 shipped them; the banner is gone and they have a page.
4. **`docs/release-notes.md` was another repository's history.** Regenerated by calling the release script's own `syncToDocsReleaseNotes`, so the file now matches what CI writes from this repo's (empty) `CHANGELOG.md` rather than being hand-edited into something the next release would overwrite differently.
5. **Azure OpenAI's save-time rule is weaker than its request-time rule.** `validateApiBackend` only requires the deployment; `azureOpenAiAdapter.buildRequest` also requires base URL, api-version and key. A backend can therefore be saved as valid and fail on first use. Documented as-is (with "run Test connection before relying on it") rather than papered over — tightening the validator is code work.

### The largest thing that WAS fixable: sentence case was switched off

`obsidianmd/ui/sentence-case` ships **in `recommended` as `["error", { enforceCamelCaseLower: true }]`** — the reviewer runs it — and `eslint.config.ts` had:

```ts
// Disable sentence case rule - it has false positives for already-correct text
'obsidianmd/ui/sentence-case': 'off'
```

Turning it on reported 34 strings. The premise was half right: 30 were false positives. But switching the rule off to avoid them also meant **four genuine violations shipped unnoticed**, and that no future title-cased string would ever be caught.

Fixed rather than excused:

| Was                                                         | Now                                               |
| ----------------------------------------------------------- | ------------------------------------------------- |
| `Imported entities are ADDED to …`                          | `… are added to …`                                |
| `(Obsidian Sync, iCloud, git…)`                             | `(Obsidian Sync, iCloud, Git…)`                   |
| `How hard reasoning models think. 'Default' sends nothing.` | `… The 'Default' option sends nothing.`           |
| `“Disable plugin” is a kill switch: …`                      | `The “Disable plugin” action is a kill switch: …` |

The last two were reworded rather than added to `ignoreWords` for a mechanical reason worth recording: the rule only consults `ignoreWords` for tokens **after** the first in a sentence, so a sentence that OPENS on a quoted UI label cannot be excused by configuration. Rewording is also better copy.

The other 30 are the rule not knowing this plugin's vocabulary, so the vocabulary is now declared. The trap in `brands` is that it **replaces** the plugin's default list (`options?.brands ?? DEFAULT_BRANDS`) rather than merging with it — supplying only the additions would have silently dropped `Obsidian`, `GitHub` and `YouTube`. The declared set covers the defaults this codebase relies on plus the backends and products its copy names, with `ignoreWords` for literal UI labels quoted inside prose, key names, `PATH` and Azure's literal `api-version`, and `ignoreRegex` for whole strings that are not sentences: `e.g.` placeholder fragments, executable-path placeholders, the `ai_editor` frontmatter key (the rule reads `ai` as the acronym and proposes `AI_editor`), and the newsletter line in `support-links.ts` / `whats-new-view.ts`.

That last one is excluded **in the config rather than at the call site** on purpose: those two files are kept byte-identical with `obsidian-plugin-template` across all 22 repos, and an inline disable comment the template does not carry would break that.

Lint is now clean with the rule as an **error**, which is the actual win: sentence case stopped being a convention someone has to remember.

### Three deviations recorded rather than "fixed"

Each is deliberate, and the checklist states the reasoning so a reviewer gets an answer instead of a defence:

1. **The Adapter API** for the margin-comment sidecar. The guideline prefers the Vault API; the Vault API cannot address anything inside `<configDir>/plugins/<id>/`, which is exactly where the sidecar must live (Business Rules #13). Every other file operation uses the Vault API.
2. **One write outside the plugin folder** — `Export settings`, to a vault path the user typed, with traversal refused and overwrite confirmed.
3. **Nine literal colour values.** Six are fallbacks _inside_ `var()`/`color-mix()`, so the theme token wins whenever it exists. Three are the swatch checkmark: a white glyph with a dark halo drawn over a **user-picked hue**, where no theme token is guaranteed to contrast — and which exists precisely to be the non-colour indicator of which swatch is selected.

One more is flagged pre-emptively rather than hidden: `dist/main.js` contains exactly one `console.warn`, inside `zod`'s JSON-Schema emitter (a code path this plugin never calls). Better to name it in the checklist than to be asked.

### Timers in three service modules were left alone, on purpose

`api-editor-backend.ts:118`, `spawn.ts:370/390` and `node-process.ts:245` use bare `setTimeout` rather than `window.setTimeout`. `eslint-plugin-obsidianmd` has no timer rule, so nothing flags them; the first is inside a documented fallback branch that Chromium and bun both skip (`AbortSignal.timeout`/`any` are always present), and the other two are Node-side child-process bookkeeping where `window` is the wrong object conceptually. Every timer that touches the UI already goes through `window.*` typed as a plain `number`.
