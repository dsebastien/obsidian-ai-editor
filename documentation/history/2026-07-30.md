## Chip click reveals and cycles findings (v1 sweep stage D, slice 0)

The locked "Live-testing feedback #3" contract is implemented (commit `d186d1b`): rail chips now answer a click instead of just opening the side panel.

- **Cycle logic** (`finding-navigation.ts`): `navigableEditorFindings` narrows the revealable set (open/preview + live anchor — the exact `revealFinding` condition) to one editor in anchor order; `cycleFinding` is MEMORY-based, not cursor-based — the contract says the first click reveals the FIRST finding regardless of where the cursor sits, so the glue remembers the last chip-revealed finding per editor and the next click steps past it with wrap-around. Memory clears on note switch and run change; a remembered finding that left the cycle set (accepted, dismissed, went stale) restarts the cycle at the first target.
- **Decision matrix** (`chipClickAction`, rail-model.ts, pure): in-flight statuses (pending/running/transforming) win — a running chip is a no-op even with findings already streamed (the tooltip already says it's running); then revealable findings → cycle; then a non-empty summary or error/cancelled state → open the side panel scrolled to that editor's section; otherwise nothing. The controller derives the chip status exactly like `buildRailEditors` (including the transform overlay) so the decision always matches what the chip shows.
- **Reveal** goes through the exact side-panel path (`revealFinding`: scroll + brief selection + collapse timer), so chip clicks and panel clicks behave identically.
- **Emphasis** (`emphasizeEditorEffect`, finding-decorations.ts): the click simultaneously flashes that editor's highlights for ~2 s. The effect rebuilds exactly that editor's live marks with `ai-editor-finding-emphasized` (marks already carry `data-editor-id`); stale marks never flash (dimmed + pulsing would contradict "no longer actionable" — `applyStale` also drops the flash from a mark going stale mid-window). A full `setFindingsEffect` rebuild resets emphasis because specs never carry it, so note switches and run changes clear the flash structurally. Per-glue auto-clear timer (re-click restarts the window), cleared on rebind/teardown/dispose; the CSS pulse is disabled under `prefers-reduced-motion` while the static stronger tint stays (WCAG 2.3.3).
- **Panel scroll-through** (`side-panel.ts`): sections carry `data-editor-id`; `revealEditorSection` scrolls instantly (no smooth animation → reduced-motion safe without a media query). `activateSidePanelAtEditor` scrolls after `activateSidePanel` pushed the binding so the section exists.
- **Click-target separation**: untouched by design — the chip's dot and its retry affordance are separate sibling `<button>`s, so retry keeps working and Enter/Space follow the click behavior natively.

Specs: +29 (editor-scoped navigation, cycle stepping incl. wrap and evicted-memory restart, decision matrix, emphasis effect semantics: scoping, stale exclusion, move/clear/reset, mapping through edits). 971 tests total.

## Stage C review fix pass

External review of the stage C work surfaced 5 findings; all verified against the code and fixed. Commits: `6d44d08` (review-service), `b100e6e` (review-controller + spec + dep), plus this docs commit.

- **Transform preview note-switch race (`b100e6e`)**: `dispatchTransformPreview` destructively discarded a valid done transform when a deferred refresh fired during the note-switch load window — Obsidian assigns `view.file` before the async content load replaces the CM doc, so `glue.filePath` matched `run.snapshot.filePath` while the doc still held the previous note's text; `checkPrecondition` returned 'text-changed' and the run died with a spurious Notice. Fix: the stale path is non-destructive when file/doc coherence is unproven — on a refresh cycle where the glue just rebound (`previousPath !== filePath`, includes fresh mounts) the widget stays cleared but the run is kept; the doc-replacing load transaction fires `handleEditorUpdate`'s settled-transform hook, which schedules the coherent re-check that presents or discards for real. A genuinely-stale run on a rebind cycle lingers (undiscarded, widget hidden) until the next refresh — delayed Notice, never a destroyed result.
- **Accept undo isolation (`b100e6e`)**: the accept dispatch had no history annotation, so CM6 joined it to adjacent history events within `newGroupDelay` (500ms) in BOTH directions (an annotation-less transaction joins the previous event when adjacent; later `input.type` transactions join it) — typing near the span then accepting, or accepting then continuing to type, made Ctrl+Z revert the transform AND the keystrokes. Fix: `annotations: isolateHistory.of('full')` on the accept transaction. `@codemirror/commands@6.10.1` added as a dev dependency — it was already in `EXTERNAL_MODULES` (Obsidian provides it at runtime), which unblocks the history spec slice 2 had queued as a manual check: 3 specs in `transform-preview.spec.ts` pin the isolation contract, including a control demonstrating the annotation-less merge hazard.
- **Instruction skip reporting (`6d44d08`)**: `startReview` silently dropped disabled members (`continue`, no `EditorSkip`) and deleted member ids (filtered from the pool, no trace) — contradicting the `ResolvedAction.editorIds` doc contract ("the review pipeline reports them as skips") and this file's earlier claim that undispatchable members surface as run skips (now true). Fix: new `SkipReason` values `editor-disabled` / `editor-missing` (labels included), emitted ONLY when the pool comes from an instruction — editors the instruction names are candidates by definition. The default pool and the daemon/retry `editorIds` redispatch stay silent about disabled editors on purpose (the user turned them off).
- **Plan §0 spec-delta arithmetic**: the "Transform ops — preview UI" row claimed +36 specs; the real delta is +44 (28 `it()` in `4fff879` + 16 in `01e485c`; suite went 855 → 899). Corrected.
- **Configuration.md follow-links overclaim**: the doc presented the panel charter's "Follow links" toggle as live behavior, but context assembly only consumes the voice profile and editor prompts (charter aggregation is M6). Qualified: the charter's flag is persisted but inert until M6.

Specs: +4 (3 history-isolation contract, 1 panel-dispatch skip reporting; the unknown/disabled instruction spec extended to assert the typed skips). 942 tests total.

## Keyboard triage state machine (v1 sweep stage D, slice 1)

The M4 keyboard triage loop is code-complete: a per-file "current finding" cursor, next → judge → auto-advance, all driven by ONE stepping engine. Three commits: `f25912d` (pure engine + cursor store), `87bf9d9` (CM6 current-ring + programmatic card open), `8da93e4` (controller wiring + `accept-finding`/`dismiss-finding` commands).

- **One engine** (`triageStep`, finding-navigation.ts): memory-based next/prev through the revealable set (ALL editors, anchor order — multi-editor interleave is purely positional, spec-pinned) with wrap-around at both ends, plus a position-based eviction fallback: stepping from a finding that left the set (accepted, dismissed, went stale) resumes from where it USED to sit — `next` lands on the first target at/after that position. Chip cycling (`cycleFinding`, locked slice-0 contract: restart at first) is now a thin special case of the same engine (`{ id, from: 0 }` memory), and the judge auto-advance IS the eviction fallback — no second code path.
- **Cursor** (`TriageCursorStore`, commands/triage-cursor.ts): per-file `{ id, from }` validated against an opaque run token (the `RunHandle`); a replaced/discarded run evicts the stale cursor on first contact. Cleared on Escape, file rename/delete, dispose. Survives note switches on purpose (the run does too). Distinct from the per-glue chip-cycle memory.
- **Stepping** (`next-finding`/`prev-finding`, now triage steps): no cursor yet → seed cursor-relative via the pre-existing `stepFinding` (pre-triage behavior preserved); cursor present → `triageStep`. Every step: remember, refresh decorations, reveal through the EXACT side-panel path (scroll + brief selection), then open the finding card at the target (card-on-jump).
- **Current ring** (`ai-editor-finding-current`): deliberately the OPPOSITE mechanism from slice 0's emphasis flash — current RIDES THE SPECS (`FindingDecorationSpec.current`, so the refresh cycle's full `setFindingsEffect` rebuilds preserve it while the cursor stands; an evicted-run cursor drops on the first rebuild), emphasis stays effect-only (any rebuild clears the flash). Both can coexist on one mark; going stale drops both (`applyStale` + `buildSet` guard). Static ring (background + box-shadow in the persona color), no animation → no reduced-motion variant needed.
- **Card-on-jump** (`showFindingCardEffect`, string | null): opens the same card a click would, anchored at the finding's live mark span (`findingSpanById`) via a CM6 measure cycle with one retry (the reveal's scroll may land a cycle later); `null` closes. No new card lifecycle — same lookup, same close rules.
- **Judging** (`accept-finding` "Accept current finding" / `dismiss-finding` "Dismiss current finding", no default hotkeys, hidden when not applicable): accept gates on a current finding + `FindingStore.isActionable` + the note open in an editor, and routes through the EXACT card-button path — `FindingStore.accept` re-verifies the precondition against the live doc (BR #3), one regular undoable transaction applies the replacement + drops the mark, the canonical-view forwarding remaps every other anchor. Failed precondition → one Notice ("The text changed since this suggestion was made."). Dismiss gates on current existing (navigable ⇒ non-terminal ⇒ dismissable). Both auto-advance: recompute the set post-mutation, `triageStep` from the judged position — the accept edit's anchor remaps have already applied synchronously, and positions only shift forward past the replaced span, so the pre-edit position is a valid threshold. Nothing left → cursor cleared, card closed via the effect, one Notice ("No more findings to triage.").
- **Escape precedence** (documented in `editorExtension`): while a finding card is open, its document-level CAPTURE listener consumes Escape (closes the card, stops propagation) before the editor ever sees the key — the cursor SURVIVES so stepping continues. With no card open, a `Prec.highest` non-consuming editor keydown observer clears that file's triage cursor (returns false always — Obsidian/vim/other plugins keep their own Escape behaviors).

Specs: +30 (engine: null/in-set/evicted stepping, wrap both directions, same-position sibling, multi-editor interleave through the real `navigableFindings` pipeline, the full next→judge→auto-advance→wrap loop, cursor validity; store: token eviction, per-file independence; decorations: current ring render/rebuild-survival/spec-drop/stale-drop/emphasis-coexistence; span lookup incl. mapped positions). 1001 tests total.

## Bulk operations and severity filter (v1 sweep stage D, slice 2)

M4's bulk triage and severity filter are code-complete. Four commits: `1a513a4` (pure planning + filter state + shared command diff), `045986c` (finding-accept history isolation), `ec886ee` (bulk ops end-to-end), `2cce37d` (severity filter end-to-end).

- **Accept-all-non-conflicting** (`commands/bulk-triage.ts`, pure): `planBulkAccept` takes the candidate findings plus the CURRENT document text and returns the edits to dispatch — every acceptable finding whose precondition still holds (BR #3, never fuzzy-relocated), in document order, skipping any whose span overlaps an already-planned edit. Overlaps keep the EARLIER anchor: composing two rewrites of one span produces nonsense, so the later suggestion is reported as skipped instead. Adjacent spans (`from === previous.to`) do NOT conflict — CM6 accepts touching changes in one transaction. Skips are counted in two buckets (overlapping / no longer matching the text) and worded by `bulkAcceptNotice`. `isBulkAcceptable` deliberately mirrors `FindingStore.isActionable`; a spec drives both over the same store fixtures so the panel's "Accept all (n)" count and the planner can never advertise different sets.
- **One transaction, one undo step**: `ReviewController.acceptAllFindings(editorId | null)` commits each planned accept through `FindingStore.accept` (so the store re-verifies every precondition, exactly like the card button) and dispatches the survivors as ONE `isolateHistory`-annotated transaction carrying all changes + `removeFindingsEffect` for the accepted ids. The canonical-view forwarding then remaps every remaining finding once (intersecting ones go stale). `dismissAllFindings` closes the set through the store, drops the marks and closes any open card (its sections may no longer exist); no document change, nothing to undo.
- **Accept history isolation, single case too**: the transform accept was isolated in the stage C fix pass, but the FINDING accepts (card button, `accept-finding`) were still annotation-less — CM6's history joins an annotation-less transaction to the previous event when adjacent and within `newGroupDelay`, and later `input.type` transactions join symmetrically, so one Ctrl+Z reverted the accepted suggestion together with the user's keystrokes. Both now dispatch `isolateHistory.of('full')`. New `finding-accept.spec.ts` pins the accept transaction shape for the single and the bulk case, including the batch promise (many changes → one history event, untouched findings remapped).
- **Commands** (`commands/bulk-commands.ts`): `accept-all-<editorId>` / `dismiss-all-<editorId>` are dynamic on the EDITOR entities — registration syncs through the settings mutation observer (ids embed the entity id so user hotkeys survive renaming the editor; a rename re-adds in place with the new palette name), while availability is re-checked per invocation against the ACTIVE note's run. Registering per run instead would churn commands on every stream event and orphan hotkeys between runs. Plus the static `accept-all` ("Accept all non-conflicting findings") over every editor of the run at once. Accept-side gates additionally require the note open in an editor to dispatch into.
- **Severity filter** (`ui/severity-filter.ts`): a per-file VIEW lens, `all → warnings and suggestions → warnings only → all` (severities in increasing importance, so repeated triggering narrows the noise and comes back). Filtered-out findings stay in the store untouched. Scope decision: the lens governs the editor decorations, the panel finding list, triage stepping, rail-chip cycling and the bulk operations — accepting or stepping onto a finding the user cannot see would be a surprise mutation — while run-report surfaces (rail chip counts, panel section status label) keep reporting what the editors actually found. `ReviewController.visibleFindings` is the single application point; filters are cleared on rename/delete and dispose like triage cursors.
- **Filter surfaces**: `filter-severity` ("Cycle severity filter", gated on the active run having live findings) Notices the new mode AND the number of hidden findings — the palette gives no other feedback, and a lens that silently hides findings is untrustworthy. The panel shows the same as a button next to the file name (`Show [All severities] · 3 hidden`), and a section whose findings are all hidden says so instead of looking empty.
- **Shared plumbing**: `commands/command-sync.ts` now holds the dynamic-command diff rules once (add / remove / re-add renamed in place / no churn on unrelated mutations); `diffActionCommands` delegates to it.

## Per-finding push-back threads (v1 sweep stage D, slice 3)

M4's per-finding threads are code-complete — the card's "Coming soon" placeholder is now a working conversation. Three commits: `5eb3fbf` (contract + pure rules + store state), `112b0ef` (orchestration + dispatch), `42dd072` (card UI + docs).

- **No new operation needed**: `thread-turn` already existed in the contract (request: findingId, quote, critique, history, message). Only the RESULT lacked the withdrawal branch, so it gained `concede` (defaulted — every existing payload stays valid) and `revisedCritique`, and `reply` tightened to non-empty (a blank reply is an `invalid-output`, not a silent no-op). `kindRules` in the prompt serializer now spells out when to concede vs hold, and that a revised suggestion is a complete replacement.
- **Pure rules** (`domain/operations/thread.ts`): cap = 6 completed exchanges (a push-back thread is a triage device, not a chat — and every turn replays the whole history, so cost grows quadratically); `resolveThreadOutcome` normalizes a result (concede WINS over any revision — a withdrawn finding has no suggestion left to apply; blank revisions read as absent); `currentSpanText` resolves what the turn talks about — the LIVE text of an anchored span (the user may have edited it since the review), falling back to the anchored text, then the raw quote. A stale anchor's offsets are never consulted (BR #3/#4).
- **State on the finding** (`FindingStore`): `thread` holds COMPLETED exchanges ONLY, so it stays strictly alternating and replay-safe, while the in-flight or failed turn lives in `threadTurn` (`pending` / `failed` with the message kept for a retry). Decision: a hold updates critique and suggestion **in place** — it is the same observation, refined — rather than superseding; `supersede` stays for the refine-proposal flow that mints a NEW finding. Updating in place re-derives the accept precondition for free: the anchor and `anchoredText` are untouched, so a span that went stale mid-turn keeps the revised suggestion display-only, and a finding sitting in `preview` whose suggestion CHANGED falls back to `open` (the diff on screen is no longer the proposal). A concede dismisses and flags `conceded` — but never undoes an accept that landed while the turn was in flight (the exchange is still recorded).
- **Threads live on the run handle** (`RunHandle.startThreadTurn`), because the run owns the findings they hang off: a replaced or discarded run kills its turns for free, and `cancelRun` aborts them AND marks their findings failed immediately (same rationale as reclaiming editor permits: an executor that ignores its signal must not leave a card spinning forever). Same event protocol as reviews (runId match, exactly-once terminal, post-terminal discard, wrong result kind / stream-end-without-terminal = failures), same plugin-wide permit, same redaction seam. A turn deliberately does NOT participate in `settled`/`isSettled()` — the review is over, a thread is a side conversation. Aborts are per-turn rather than composed with the run signal, so pushing back on a CANCELLED run's findings still works (cancel keeps findings inspectable).
- **Cancellation contract**: closing the card cancels nothing (the reply lands in the store and shows when reopened, plus a Notice); `Cancel review` does cancel.
- **Dispatch** (`services/thread-service.ts`): shaped like `startReview` / `startAction` — exclusions fail closed before anything is read (BR #7), only the editor that PRODUCED the finding may answer (typed skip when it is missing, disabled, review-incapable, or has no usable API backend), the persona prompt is assembled fresh (the vault IS the config), the span text is resolved BEFORE any await, refusals are typed results. Deliberate omission: no size guard — a thread-turn request carries the quote, critique, prior turns and the message, never the note text (the note only counts against the context budget), and the review that produced the finding already passed the guard. Asking again inside a card would be noise.
- **Card**: a compact scrollable thread (max-height, scrolled to the newest turn after every render) plus a reply row; Enter or **Send** dispatches, the message immediately shows as a pending row with the rail's pulse while the input locks, and a failed turn shows the reason with the message restored so it can be re-sent. Pure `threadView` pins idle / pending / failed / capped; `threadRefusalNotice` words the store refusals (mostly races — accepted or dismissed in another pane while the reply was typed).
- **Async replies into an open card**: new `refreshFindingCardEffect`, dispatched from the refresh cycle only while some finding of the run has thread activity (the thread-free path stays a no-op). Re-rendering would eat what the user is typing, so the reply drafts, keyboard focus and caret are carried across the rebuild; drafts live and die with the card.
- **Notices**: every completed turn reports once (withdrew / revised / replied / failed) because the card is usually closed by the time the answer arrives. `cancelled` and `discarded` stay silent — cancelling is a user action with its own feedback, and a discarded turn means the finding is gone.

Specs: +55 (thread cap/outcome/span-text helpers, contract boundary, store transitions incl. stale-mid-turn + preview fallback + accept race + late events, request shape incl. history/critique evolution, resolution vocabulary, protocol enforcement, redaction, cancellation, permit sharing, service refusals + exclusion fail-closed, card thread projection + refusal copy). 1096 tests total.

- Type a second message while the first is still in flight (from another pane's card): the refusal Notice says the editor is still answering.
- Reduced motion: the pending row is static (dimmed only).

## Adaptive narrow-pane layout (v1 sweep stage D, slice 4)

Stage D is complete: the editor chrome now adapts to the pane it lives in. One commit: `10ad3d0`.

- **One pure module** (`ui/editor/layout-mode.ts`) owns every rule; the observer glue in `review-controller.ts` and the card only measure and apply.
- **Threshold with hysteresis**: `nextLayoutMode` collapses at ≤500px pane width and returns to wide only at ≥560px. A single threshold would re-render the rail on every observed frame while a split is dragged across it — and the rail is chrome the user is aiming at with the mouse. A non-finite or ≤0 width is deliberately NOT a narrow pane: it is a pane being measured while hidden (collapsed sidebar, deferred leaf, a view being detached), and flipping those to compact would make rails flicker on unrelated workspace changes, so they keep their current mode.
- **Card box** (`paneCardViewport`): the pane rect, inset by the padding and intersected with the window box. The pane constraint is dropped **per axis** when it would leave less than a usable card (`CARD_MIN_WIDTH` 240 / `CARD_MIN_HEIGHT` 160): squeezing a card into a sliver of a pane is worse than letting it overlay its neighbour, and a pane dragged partly out of the window can intersect to nothing. The axes decide independently because horizontal and vertical splits are independent.
- **Observer glue is thin**: one `ResizeObserver` per glue on `view.contentEl`, constructed from the VIEW's own window so panes in popout windows are observed by their own document's implementation (absent implementation ⇒ the rail simply stays in wide form). The initial mode is measured synchronously in `createGlue`, so a pane that is already narrow never renders the wide rail for a frame. Disconnected in `destroyGlue` — which `dispose()` runs for every glue. The callback stores a CHANGED mode and schedules the normal debounced refresh; it never does synchronous DOM work (that is how ResizeObserver loops start), and an unchanged mode costs nothing.
- **Compact rail**: the rail was ALREADY icon-only chips carrying their info in tooltips, so the compact form is the button plus spacing — the Review/Cancel button drops its label for a glyph (`▶` / `■`; text glyphs on purpose, the rail is Obsidian-free DOM with no `setIcon` and no innerHTML, same reasoning as the retry chip's `↻`) while `label`/`action` stay semantic, and dots, retry, badges and gaps shrink; the wrapper hugs the pane edge because in a 500px pane every reclaimed pixel is a pixel of text.
- **Nudge to the side panel** (the real narrow-pane surface, plan M2): `NARROW_PANEL_HINT` is appended to the button's accessible name only. Repeating it on every chip would be noise, and the chip tooltips already carry name + live status — which is exactly the information a label-less rail drops.
- **Cards clamp into the pane**: `positionCard` builds the window box from the card's own document (popouts), intersects it with `view.dom`'s rect, applies the width cap BEFORE measuring (the measurement has to be of the box that then gets positioned) and clamps the position into that box. A card opened in a right-hand split no longer spills over the document to its left.
- **Overflow sweep**: the card's action row and the transform preview's action row wrap instead of overflowing, the push-back input may shrink (`min-w-0`), and the card is `min-w-0` with a code-set `max-width` that beats its preferred `min(560px, 94vw)`. Settings and side-panel surfaces already wrapped (`flex-wrap`, `auto-fill` grid) — nothing to fix there.

Specs: +21 (mode thresholds incl. the hysteresis band and hidden-pane rule, pane viewport intersection with per-axis fallback and exact minimums, width cap, rail compact view model incl. glyph/semantics split and unchanged chips, card position composed against a pane box). 1117 tests total.
