## Chip click reveals and cycles findings (v1 sweep stage D, slice 0)

The locked "Live-testing feedback #3" contract is implemented (commit `d186d1b`): rail chips now answer a click instead of just opening the side panel.

- **Cycle logic** (`finding-navigation.ts`): `navigableEditorFindings` narrows the revealable set (open/preview + live anchor — the exact `revealFinding` condition) to one editor in anchor order; `cycleFinding` is MEMORY-based, not cursor-based — the contract says the first click reveals the FIRST finding regardless of where the cursor sits, so the glue remembers the last chip-revealed finding per editor and the next click steps past it with wrap-around. Memory clears on note switch and run change; a remembered finding that left the cycle set (accepted, dismissed, went stale) restarts the cycle at the first target.
- **Decision matrix** (`chipClickAction`, rail-model.ts, pure): in-flight statuses (pending/running/transforming) win — a running chip is a no-op even with findings already streamed (the tooltip already says it's running); then revealable findings → cycle; then a non-empty summary or error/cancelled state → open the side panel scrolled to that editor's section; otherwise nothing. The controller derives the chip status exactly like `buildRailEditors` (including the transform overlay) so the decision always matches what the chip shows.
- **Reveal** goes through the exact side-panel path (`revealFinding`: scroll + brief selection + collapse timer), so chip clicks and panel clicks behave identically.
- **Emphasis** (`emphasizeEditorEffect`, finding-decorations.ts): the click simultaneously flashes that editor's highlights for ~2 s. The effect rebuilds exactly that editor's live marks with `ai-editor-finding-emphasized` (marks already carry `data-editor-id`); stale marks never flash (dimmed + pulsing would contradict "no longer actionable" — `applyStale` also drops the flash from a mark going stale mid-window). A full `setFindingsEffect` rebuild resets emphasis because specs never carry it, so note switches and run changes clear the flash structurally. Per-glue auto-clear timer (re-click restarts the window), cleared on rebind/teardown/dispose; the CSS pulse is disabled under `prefers-reduced-motion` while the static stronger tint stays (WCAG 2.3.3).
- **Panel scroll-through** (`side-panel.ts`): sections carry `data-editor-id`; `revealEditorSection` scrolls instantly (no smooth animation → reduced-motion safe without a media query). `activateSidePanelAtEditor` scrolls after `activateSidePanel` pushed the binding so the section exists.
- **Click-target separation**: untouched by design — the chip's dot and its retry affordance are separate sibling `<button>`s, so retry keeps working and Enter/Space follow the click behavior natively.

## Stage C review fix pass

External review of the stage C work surfaced 5 findings; all verified against the code and fixed. Commits: `6d44d08` (review-service), `b100e6e` (review-controller + spec + dep), plus this docs commit.

- **Transform preview note-switch race (`b100e6e`)**: `dispatchTransformPreview` destructively discarded a valid done transform when a deferred refresh fired during the note-switch load window — Obsidian assigns `view.file` before the async content load replaces the CM doc, so `glue.filePath` matched `run.snapshot.filePath` while the doc still held the previous note's text; `checkPrecondition` returned 'text-changed' and the run died with a spurious Notice. Fix: the stale path is non-destructive when file/doc coherence is unproven — on a refresh cycle where the glue just rebound (`previousPath !== filePath`, includes fresh mounts) the widget stays cleared but the run is kept; the doc-replacing load transaction fires `handleEditorUpdate`'s settled-transform hook, which schedules the coherent re-check that presents or discards for real. A genuinely-stale run on a rebind cycle lingers (undiscarded, widget hidden) until the next refresh — delayed Notice, never a destroyed result.
- **Accept undo isolation (`b100e6e`)**: the accept dispatch had no history annotation, so CM6 joined it to adjacent history events within `newGroupDelay` (500ms) in BOTH directions (an annotation-less transaction joins the previous event when adjacent; later `input.type` transactions join it) — typing near the span then accepting, or accepting then continuing to type, made Ctrl+Z revert the transform AND the keystrokes. Fix: `annotations: isolateHistory.of('full')` on the accept transaction. `@codemirror/commands@6.10.1` added as a dev dependency — it was already in `EXTERNAL_MODULES` (Obsidian provides it at runtime), which unblocks the history spec slice 2 had queued as a manual check: 3 specs in `transform-preview.spec.ts` pin the isolation contract, including a control demonstrating the annotation-less merge hazard.
- **Instruction skip reporting (`6d44d08`)**: `startReview` silently dropped disabled members (`continue`, no `EditorSkip`) and deleted member ids (filtered from the pool, no trace) — contradicting the `ResolvedAction.editorIds` doc contract ("the review pipeline reports them as skips") and this file's earlier claim that undispatchable members surface as run skips (now true). Fix: new `SkipReason` values `editor-disabled` / `editor-missing` (labels included), emitted ONLY when the pool comes from an instruction — editors the instruction names are candidates by definition. The default pool and the daemon/retry `editorIds` redispatch stay silent about disabled editors on purpose (the user turned them off).
- **Plan §0 spec-delta arithmetic**: the "Transform ops — preview UI" row claimed +36 specs; the real delta is +44 (28 `it()` in `4fff879` + 16 in `01e485c`; suite went 855 → 899). Corrected.
- **Configuration.md follow-links overclaim**: the doc presented the panel charter's "Follow links" toggle as live behavior, but context assembly only consumes the voice profile and editor prompts (charter aggregation is M6). Qualified: the charter's flag is persisted but inert until M6.

Specs: +4 (3 history-isolation contract, 1 panel-dispatch skip reporting; the unknown/disabled instruction spec extended to assert the typed skips). 942 tests total.

## Keyboard triage state machine (v1 sweep stage D, slice 1)

The M4 keyboard triage loop is code-complete: a per-file "current finding" cursor, next → judge → auto-advance, all driven by ONE stepping engine. Three commits: `f25912d` (pure engine + cursor store), `87bf9d9` (CM6 current-ring + programmatic card open), `8da93e4` (controller wiring + `accept-finding`/`dismiss-finding` commands).

- **One engine** (`triageStep`, finding-navigation.ts): memory-based next/prev through the revealable set (ALL editors, anchor order — multi-editor interleave is purely positional, spec-pinned) with wrap-around at both ends, plus a position-based eviction fallback: stepping from a finding that left the set (accepted, dismissed, went stale) resumes from where it USED to sit — `next` lands on the first target at/after that position. Chip cycling (`cycleFinding`, locked slice-0 contract: restart at first) is now a thin special case of the same engine (`{ id, from: 0 }` memory), and the judge auto-advance IS the eviction fallback — no second code path.
- **Cursor** (`TriageCursorStore`, commands/triage-cursor.ts): per-file `{ id, from }` validated against an opaque run token (the `RunHandle`); a replaced/discarded run evicts the stale cursor on first contact. Cleared on Escape, file rename/delete, dispose. Survives note switches on purpose (the run does too). Distinct from the per-glue chip-cycle memory.
- **Stepping** (`next-finding`/`prev-finding`, now triage steps): no cursor yet → seed cursor-relative via the pre-existing `stepFinding` (pre-triage behavior preserved); cursor present → `triageStep`. Every step: remember, refresh decorations, reveal through the EXACT side-panel path (scroll + brief selection), then open the finding card at the target (card-on-jump).
- **Current ring** (`ai-editor-finding-current`): deliberately the OPPOSITE mechanism from slice 0's emphasis flash — current RIDES THE SPECS (`FindingDecorationSpec.current`, so the refresh cycle's full `setFindingsEffect` rebuilds preserve it while the cursor stands; an evicted-run cursor drops on the first rebuild), emphasis stays effect-only (any rebuild clears the flash). Both can coexist on one mark; going stale drops both (`applyStale` + `buildSet` guard). Static ring (background + box-shadow in the persona color), no animation → no reduced-motion variant needed.
- **Card-on-jump** (`showFindingCardEffect`, string | null): opens the same card a click would, anchored at the finding's live mark span (`findingSpanById`) via a CM6 measure cycle with one retry (the reveal's scroll may land a cycle later); `null` closes. No new card lifecycle — same lookup, same close rules.
- **Judging** (`accept-finding` "Accept current finding" / `dismiss-finding` "Dismiss current finding", no default hotkeys, hidden when not applicable): accept gates on a current finding + `FindingStore.isActionable` + the note open in an editor, and routes through the EXACT card-button path — `FindingStore.accept` re-verifies the precondition against the live doc (BR #3), one regular undoable transaction applies the replacement + drops the mark, the canonical-view forwarding remaps every other anchor. Failed precondition → one Notice ("The text changed since this suggestion was made."). Dismiss gates on current existing (navigable ⇒ non-terminal ⇒ dismissable). Both auto-advance: recompute the set post-mutation, `triageStep` from the judged position — the accept edit's anchor remaps have already applied synchronously, and positions only shift forward past the replaced span, so the pre-edit position is a valid threshold. Nothing left → cursor cleared, card closed via the effect, one Notice ("No more findings to triage.").
- **Escape precedence** (documented in `editorExtension`): while a finding card is open, its document-level CAPTURE listener consumes Escape (closes the card, stops propagation) before the editor ever sees the key — the cursor SURVIVES so stepping continues. With no card open, a `Prec.highest` non-consuming editor keydown observer clears that file's triage cursor (returns false always — Obsidian/vim/other plugins keep their own Escape behaviors).

Specs: +30 (engine: null/in-set/evicted stepping, wrap both directions, same-position sibling, multi-editor interleave through the real `navigableFindings` pipeline, the full next→judge→auto-advance→wrap loop, cursor validity; store: token eviction, per-file independence; decorations: current ring render/rebuild-survival/spec-drop/stale-drop/emphasis-coexistence; span lookup incl. mapped positions). 1001 tests total.

## Bulk operations and severity filter (v1 sweep stage D, slice 2)

M4's bulk triage and severity filter are code-complete. Four commits: `1a513a4` (pure planning + filter state + shared command diff), `045986c` (finding-accept history isolation), `ec886ee` (bulk ops end-to-end), `2cce37d` (severity filter end-to-end).

- **Accept-all-non-conflicting** (`commands/bulk-triage.ts`, pure): `planBulkAccept` takes the candidate findings plus the CURRENT document text and returns the edits to dispatch — every acceptable finding whose precondition still holds (BR #3, never fuzzy-relocated), in document order, skipping any whose span overlaps an already-planned edit. Overlaps keep the EARLIER anchor: composing two rewrites of one span produces nonsense, so the later suggestion is reported as skipped instead. Adjacent spans (`from === previous.to`) do NOT conflict — CM6 accepts touching changes in one transaction. Skips are counted in two buckets (overlapping / no longer matching the text) and worded by `bulkAcceptNotice`. `isBulkAcceptable` deliberately mirrors `FindingStore.isActionable`; a spec drives both over the same store fixtures so the panel's "Accept all (n)" count and the planner can never advertise different sets.
- **One transaction, one undo step**: `ReviewController.acceptAllFindings(editorId | null)` commits each planned accept through `FindingStore.accept` (so the store re-verifies every precondition, exactly like the card button) and dispatches the survivors as ONE `isolateHistory`-annotated transaction carrying all changes + `removeFindingsEffect` for the accepted ids. The canonical-view forwarding then remaps every remaining finding once (intersecting ones go stale). `dismissAllFindings` closes the set through the store, drops the marks and closes any open card (its sections may no longer exist); no document change, nothing to undo.
- **Accept history isolation, single case too**: the transform accept was isolated in the stage C fix pass, but the FINDING accepts (card button, `accept-finding`) were still annotation-less — CM6's history joins an annotation-less transaction to the previous event when adjacent and within `newGroupDelay`, and later `input.type` transactions join symmetrically, so one Ctrl+Z reverted the accepted suggestion together with the user's keystrokes. Both now dispatch `isolateHistory.of('full')`. New `finding-accept.spec.ts` pins the accept transaction shape for the single and the bulk case, including the batch promise (many changes → one history event, untouched findings remapped).
- **Commands** (`commands/bulk-commands.ts`): `accept-all-<editorId>` / `dismiss-all-<editorId>` are dynamic on the EDITOR entities — registration syncs through the settings mutation observer (ids embed the entity id so user hotkeys survive renaming the editor; a rename re-adds in place with the new palette name), while availability is re-checked per invocation against the ACTIVE note's run. Registering per run instead would churn commands on every stream event and orphan hotkeys between runs. Plus the static `accept-all` ("Accept all non-conflicting findings") over every editor of the run at once. Accept-side gates additionally require the note open in an editor to dispatch into.
- **Severity filter** (`ui/severity-filter.ts`): a per-file VIEW lens, `all → warnings and suggestions → warnings only → all` (severities in increasing importance, so repeated triggering narrows the noise and comes back). Filtered-out findings stay in the store untouched. Scope decision: the lens governs the editor decorations, the panel finding list, triage stepping, rail-chip cycling and the bulk operations — accepting or stepping onto a finding the user cannot see would be a surprise mutation — while run-report surfaces (rail chip counts, panel section status label) keep reporting what the editors actually found. `ReviewController.visibleFindings` is the single application point; filters are cleared on rename/delete and dispose like triage cursors.

- **Shared plumbing**: `commands/command-sync.ts` now holds the dynamic-command diff rules once (add / remove / re-add renamed in place / no churn on unrelated mutations); `diffActionCommands` delegates to it.

## Per-finding push-back threads (v1 sweep stage D, slice 3)

M4's per-finding threads are code-complete — the card's "Coming soon" placeholder is now a working conversation. Four commits: `5eb3fbf` (contract + pure rules + store state), `112b0ef` (orchestration + dispatch), `42dd072` (card UI + docs) and `bea3060` (layer isolation, landed after the docs commit: `ThreadBeginFailure` moved from `finding-store.ts` into `domain/operations/thread.ts` so the card does not import refusal vocabulary from the services layer).

- **No new operation needed**: `thread-turn` already existed in the contract (request: findingId, quote, critique, history, message). Only the RESULT lacked the withdrawal branch, so it gained `concede` (defaulted — every existing payload stays valid) and `revisedCritique`, and `reply` tightened to non-empty (a blank reply is an `invalid-output`, not a silent no-op). `kindRules` in the prompt serializer now spells out when to concede vs hold, and that a revised suggestion is a complete replacement.
- **Pure rules** (`domain/operations/thread.ts`): cap = 6 completed exchanges (a push-back thread is a triage device, not a chat — and every turn replays the whole history, so cost grows quadratically); `resolveThreadOutcome` normalizes a result (concede WINS over any revision — a withdrawn finding has no suggestion left to apply; blank revisions read as absent); `currentSpanText` resolves what the turn talks about — the LIVE text of an anchored span (the user may have edited it since the review), falling back to the anchored text, then the raw quote. A stale anchor's offsets are never consulted (BR #3/#4).
- **State on the finding** (`FindingStore`): `thread` holds COMPLETED exchanges ONLY, so it stays strictly alternating and replay-safe, while the in-flight or failed turn lives in `threadTurn` (`pending` / `failed` with the message kept for a retry). Decision: a hold updates critique and suggestion **in place** — it is the same observation, refined — rather than superseding; `supersede` stays for the refine-proposal flow that mints a NEW finding. Updating in place re-derives the accept precondition for free: the anchor and `anchoredText` are untouched, so a span that went stale mid-turn keeps the revised suggestion display-only, and a finding sitting in `preview` whose suggestion CHANGED falls back to `open` (the diff on screen is no longer the proposal). A concede dismisses and flags `conceded` — but never undoes an accept that landed while the turn was in flight (the exchange is still recorded).
- **Threads live on the run handle** (`RunHandle.startThreadTurn`), because the run owns the findings they hang off: a replaced or discarded run kills its turns for free, and `cancelRun` aborts them AND marks their findings failed immediately (same rationale as reclaiming editor permits: an executor that ignores its signal must not leave a card spinning forever). Same event protocol as reviews (runId match, exactly-once terminal, post-terminal discard, wrong result kind / stream-end-without-terminal = failures), same plugin-wide permit, same redaction seam. A turn deliberately does NOT participate in `settled`/`isSettled()` — the review is over, a thread is a side conversation. Aborts are per-turn rather than composed with the run signal, so pushing back on a CANCELLED run's findings still works (cancel keeps findings inspectable).
- **Cancellation contract**: closing the card cancels nothing (the reply lands in the store and shows when reopened, plus a Notice); `Cancel review` does cancel.
- **Dispatch** (`services/thread-service.ts`): shaped like `startReview` / `startAction` — exclusions fail closed before anything is read (BR #7), only the editor that PRODUCED the finding may answer (typed skip when it is missing, disabled, review-incapable, or has no usable API backend), the persona prompt is assembled fresh (the vault IS the config), the span text is resolved BEFORE any await, refusals are typed results. Deliberate omission: no size guard — a thread-turn request carries the quote, critique, prior turns and the message, never the note text (the note only counts against the context budget), and the review that produced the finding already passed the guard. Asking again inside a card would be noise.
- **Card**: a compact scrollable thread (max-height, scrolled to the newest turn after every render) plus a reply row; Enter or **Send** dispatches, the message immediately shows as a pending row with the rail's pulse while the input locks, and a failed turn shows the reason with the message restored so it can be re-sent. Pure `threadView` pins idle / pending / failed / capped; `threadRefusalNotice` words the store refusals (mostly races — accepted or dismissed in another pane while the reply was typed).
- **Async replies into an open card**: new `refreshFindingCardEffect`, dispatched from the refresh cycle only while some finding of the run has thread activity (the thread-free path stays a no-op). Re-rendering would eat what the user is typing, so the reply drafts, keyboard focus and caret are carried across the rebuild; drafts live and die with the card.
- **Notices**: every completed turn reports once (withdrew / revised / replied / failed) because the card is usually closed by the time the answer arrives. `cancelled` and `discarded` stay silent — cancelling is a user action with its own feedback, and a discarded turn means the finding is gone.

Specs: +55 (thread cap/outcome/span-text helpers, contract boundary, store transitions incl. stale-mid-turn + preview fallback + accept race + late events, request shape incl. history/critique evolution, resolution vocabulary, protocol enforcement, redaction, cancellation, permit sharing, service refusals + exclusion fail-closed, card thread projection + refusal copy). 1096 tests total.

Stage D is complete: the editor chrome now adapts to the pane it lives in. One commit: `10ad3d0`.

## Binding rules actually filter, and note types are real (v1 sweep stage E, slice 1)

The `SEAM M6` marker in `review-service.ts` is gone. `settings.rules` had been modelled since M1 and consumed by nothing; it now governs both of plan §4b's effects. Five code commits plus this docs commit: `5a926f7` pure engine, `2251df5` vault seam + OSK adapter, `d0710ed` dispatch, `adf6bdd` UI suppression, `3d419a2` Rules tab.

### Evaluation order — decided, not inherited

Two phases, and the reasoning matters more than the code:

1. **A matching `disabled` rule wins from ANY position in the list.** The alternative — plain first-match-wins across both effects, which is what the tab's old copy promised — lets an unrelated `assign` rule ordered above a kill switch silently re-enable the plugin on the notes the user fenced off, with no visible cause. A kill switch is a safety control; being shadowed by an ordering accident is a bug class, not a preference.
2. **Among `assign` rules, the FIRST match in list order wins.** Sorting by match specificity (note-type > frontmatter > tag > folder) was considered and rejected: the tab exposes explicit move-up/move-down, so list order IS the user's priority statement, and a hidden sort would make the visible order a lie. Any specificity the user wants is expressible by moving a rule up.

Assignments are **not** unioned across matching rules. A rule saying "only the Humanizer touches this folder" has to be able to mean exactly that; accumulating with a broader rule's target makes narrowing inexpressible.

No match → the pre-rules behavior, every enabled review-capable editor. The tab says so, including in its empty state.

### Cold metadata cache fails in opposite directions per effect

Obsidian's metadata cache resolves asynchronously, so tag / frontmatter / note-type facts can be missing right after startup. `disabled` rules then fail **closed** (treated as matching) and `assign` rules fail **open** (treated as not matching). Same trade-off `isExcluded` already makes for privacy, applied where it belongs: a warm-up window in which the plugin wakes up on the notes the user switched it off for is the one outcome a kill switch may not produce, while an assignment failing open lands on the documented default pool, not on a leak. Folder matching needs no metadata and is always evaluated — so a folder-scoped kill switch is exact even during warm-up.

### Note-type identity is a SET, and the OSK plugin stays optional

The Starter Kit names a type `Personal Notes` and tags it `type/personal`. There is no reliable transformation between those, so a note's identity is the union of both spellings, normalized (`personal-notes`, `personal`), and a rule matches **any** of them. A rule written against the canonical name works with the plugin installed; a rule written against the tag works either way. The alternative — guessing a singular/plural mapping — would silently mismatch on types like `Personal Notes` / `type/personal`, where the stem itself differs.

`recognizeNoteType` was deliberately **not** ported from `starter-kit.service.ts`: it is asynchronous, and every consumer here is a synchronous decision (context-menu construction, command gate, rail render) that cannot await a cross-plugin call. Its inputs — the type list and the note's tags/path — are synchronous, so recognition is done locally in `domain/rules/note-type.ts` by matching each type's own enabled tag / folder / filename-regex mappings. `formula` mappings are not evaluable outside the Starter Kit and recognize nothing; a user-authored regex that fails to compile recognizes nothing rather than taking down a menu build.

`ui/osk-note-types.ts` is the entire dependency on that plugin: feature-detected, `ApiResult`-envelope tolerant, every field defensively normalized, `[]` on anything unexpected or thrown. Nothing else in the plugin knows the Starter Kit exists.

`domain/rules/matchers.ts` now owns the folder/tag primitives and `context/exclusions.ts` imports them. A user who excludes `Private` and disables the plugin for `Private` must get the same set of notes both times; that is now true by construction rather than by two implementations agreeing.

### Cost of asking

Rule evaluation runs on every menu open, command gate and refresh cycle, so the fact gathering reads only what the configured rules can use: no rules or folder-only rules never touch the metadata cache, and only a rule matching on note types triggers the registry call. The counting fake in `note-rules.spec.ts` pins that — the common vault pays nothing.

### `rule-disabled` is not `excluded`

A new typed refusal on `ReviewStart`, `ActionStart` and `ThreadStart`, plus the matching CLI error code. Keeping it separate is the point: `excluded` means "this content never leaves the vault" and the fix is in the Behavior tab, `rule-disabled` means "AI Editor does not operate here" and the fix is in the Rules tab. The message names the rule (its name, or its match expression when unnamed). It is checked **before** the size guard, so a switched-off note never pops a confirmation dialog on its way to being refused.

Only the kill switch applies to actions and threads. An `assign` rule picks who REVIEWS a note; a bound action already names its own target editor, and a push-back can only be answered by the editor that produced the finding.

### Participant pools, unified

`startReview`'s pool precedence is now explicit: a per-run `instruction` (ask-an-editor, a bound review verb) > a daemon's `editorIds` re-dispatch > a matching `assign` rule > every editor. Rules supply the DEFAULT pool only — when the user or the daemon named editors, that choice wins.

The two pool kinds that NAME editors (instruction, rule) share one code path and report every named editor that cannot run, disabled and deleted included, instead of silently shrinking. The daemon's re-dispatch pool keeps its old silence about disabled editors: the user turned them off on purpose and an automatic refresh must not nag. A rule pointing at a deleted panel refuses with a new `rule-target-missing` skip rather than quietly reviewing with everyone the rule was meant to replace — referential integrity reports the same dangling reference in the settings.

### The kill switch reaches every surface

`isReviewable` now takes the vault reader instead of a pre-read metadata value (rules need note-type facts too) and folds the kill switch in, so every surface already gated on it — the review commands, the file menu, the CLI, the daemon's fire-time probe — refused a switched-off note with no further wiring.

Where the exclusion path stopped short, this slice went further:

- `isNoteExcluded` became `isPluginEnabledFor` (exclusion AND kill switch), because both produce the same UI outcome: nothing offered. `EditorMenuState.excluded` became `blocked` with an explicit "nothing at all" early return, so the contract is local to the pure model instead of inferred from a caller that happens to build consistent state.
- **The rail is now hidden and the highlights cleared** for a blocked note. Previously the rail stayed up on excluded notes, offering a Review button whose only possible outcome was a refusal Notice.
- `runContextFor` became the single choke point for every ambient triage surface (next/previous finding, accept/dismiss current, bulk accept/dismiss, severity filter): a blocked note reports no run, so none of those commands is available and none can mutate it. `activeRunContext` delegates to it. The side-panel binding and the finding-card lookup refuse the same way; a card open when the rule lands is closed once, on the transition.
- **`Cancel review` stays available on purpose.** Stopping an in-flight backend request is never the wrong outcome, and gating it would leave a run nothing could stop.
- A hidden run stays **bound** to its glue. Edit forwarding keeps its anchors remapping, so removing the rule restores a coherent run instead of a set of stale offsets (Business Rules #3/#4).

### Rules tab

The UI could already create, edit, reorder and delete rules, so this was polish only: copy that matches the engine, the obsolete "OSK auto-discovery lands in a later milestone, rules using it stay inert" paragraph replaced by a live Starter-Kit-detected / not-detected line telling the user which spelling to match, and `ruleSummary` upgraded to say what a rule RESOLVES to (`folder "Blog" → reviewed by panel Pre-publish (Hater, Humanizer)`) and to say so when it does nothing: no target yet, deleted editor, deleted panel, panel with no members left. ## The context budget is a policy, and the plugin will show you what it sends (v1 sweep stage E, slice 2)

Plan M5's two remaining context items — the budget across every source, and the "what will be sent" preview. Three code commits plus this docs commit: `094f41b` budget policy, `5d05749` one prompt-build entry point + preview service, `64bdfd3` modal / command / settings button.

### What was already there, and stayed there

The task list asked to "check whether context assembly honors `includeLinkedNotes` / `maxLinkedNotes`". It does, fully, and has since the follow-links work: `assembleContext` attaches the reviewed note's outgoing links as `linked-note` attachments — links AND embeds (`ObsidianVaultReader.getOutgoingLinks` merges `cache.links` with `cache.embeds`), markdown only, depth 1, deduplicated against everything already attached under an earlier reason, capped at `maxLinkedNotes`, budget-aware, and with excluded notes never inlined _and_ never consuming the cap. All of it spec-covered. So this slice verified it instead of rebuilding it; the only change on that path is that attachment blocks now carry a `role`.

That `role` is the one thing the labeling was missing. Every block used to read `<context-note path="…">`, whatever it was. A note the persona references is instruction material; a note linked from the document under review is subject matter; a model that cannot tell them apart will happily critique the reference material. The `role` value is the attachment reason, so the prompt, the preview and the budget all name the same thing with the same word.

### The budget had no owner and no honesty

`contextBudgetChars` was four lines of arithmetic inlined in the assembler, and the two fields meant to explain it — `preview` and `truncated` — had **no production consumer at all**. They were produced on every run and read only by their own tests. Worse, `truncated` held both the note that got a prefix and the notes that got nothing, which is the distinction a user needs most.

`services/context/context-budget.ts` now owns the policy: the send/priority order, the allocation, the labels. The assembler collects candidates and applies it. Splitting them is what makes the whole policy pure and spec-pinnable without a vault, and gives the preview one place to read it from.

**Priority order, decided rather than inherited:**

1. The **system prompt** — voice text + persona text + memory text as one string. Never truncated: half a persona silently produces a different editor.
2. The **reviewed note** — never truncated. Findings must quote the submitted snapshot verbatim and anchors resolve against it (Business Rules #3/#4), so a trimmed note would make anchoring lie. The assembler could not trim it even if it wanted to: the note text travels in the operation payload (`operation.text`), not in the system prompt. The budget only ACCOUNTS for it.
3. **Attachments** in assembly order: `prompt-ref` → `wikilink-ref` → `followed-link` → `linked-note`.

Because the first two are never truncated, the ordered truncatable region IS the attachment list — so ONE list serves as both the send order and the priority order. That coupling is deliberate. Two orders would let the preview show notes in an order that does not explain which of them got dropped, and explaining that is the entire point of the preview.

Inside `prompt-ref`, voice-profile notes precede persona notes, mirroring the system prompt's text order (the assembler's documented invariant). So the global voice profile outranks a persona's own reference notes. Considered and rejected: hoisting persona refs above it because "the persona IS the editor" — the persona's _text_ is never truncated at all, and the voice profile is one small globally-configured note set while persona refs are per-editor and typically the larger group. Dropping the persona's fifth reference before the single voice-profile note is the better failure, and anyone who disagrees can express it by turning `injectVoiceProfile` off for that editor.

Two reporting decisions follow from wanting the preview to be honest rather than reassuring:

- **Truncated is not dropped.** An attachment allocated zero characters is `dropped`. "Truncated" promises a prefix arrives, and an empty prefix is no content at all. Blurring them would make the preview's most actionable row meaningless.
- **Every candidate reports its REAL source size**, even when dropped. That means reading notes the budget will not send — deliberate cost: the number that tells a user whether to raise the budget or cut a reference is how big the dropped note was. A note that cannot be read at all is not a section; reporting it as dropped would blame the budget for a missing file.
- **Over budget is reported, not absorbed.** When the never-truncated sections alone exceed the budget, every attachment is dropped and `overBudgetChars` says by how much. The run still goes out — refusing to review a long note would be worse — and the preview says so in words, without implying a fix that does not exist.

### One prompt-build entry point, which is what makes the preview trustworthy

Reviews, transforms/generations and push-back threads each had their own `assembleContext` + `composeSystemPrompt` pair. The preview would have made it four, and the fourth would eventually have disagreed with the other three. A trust surface that drifts is worse than no trust surface.

`buildEditorPrompt` is now the only way a system prompt gets built, and all four callers go through it. The spec that matters is in `context-preview-service.spec.ts`: it runs a REAL `startReview` against a capturing `fetch`, pulls the `system` field out of the request body, and asserts the preview's string equals it. Drift is now a test failure instead of a discovered lie.

### The preview surface

`previewEditorContext` resolves everything the modal shows: the exact system prompt, one section row per accounted part with what the budget did to it, the resolved backend (or the reason the editor cannot run — a prompt the user approves that no backend can carry is still a run that will not happen), and the two refusals as their own statuses. `excluded` names the Behavior tab, `rule-disabled` names the Rules tab and the rule; keeping them apart matters because the fixes are in different places, and "nothing would be sent" is the most important sentence a preview can produce.

It takes the editor as a **value**, not an id. That is what lets the editor settings dialog preview its unsaved draft — previewing the persona you are currently writing is the whole point of the button there.

Two entry points, deliberately different, both documented in code:

- **`preview-context`** (palette: "Preview what will be sent") reads the **live editor buffer**. Unsaved edits are what a review would send, so a preview reading vault state would describe a different request.
- The **Preview** button in the editor dialog reads the **vault** but previews the **unsaved draft**. The settings dialog covers the editor, so there is no focused markdown view to read a buffer from.

The modal re-resolves on every picker change rather than caching: each editor has its own persona, voice-profile opt-in and linked-note policy, so there is nothing shared to cache, and a stale panel here would be exactly the lie this surface exists to prevent. A `renderToken` guard drops an out-of-order resolve. The system prompt renders into a `<pre>` via `text` (no `innerHTML`), keyboard-reachable with an accessible name that says whose prompt it is, since the picker above it changes that. The modal sends nothing — its only injected dependency is `previewEditorContext`.

Copy updated where it was now wrong or thin: the Behavior tab's context-budget field states the spend order and points at the command; the editor dialog's "Include linked notes" toggle says links _and embeds_, one hop, that excluded notes are never attached, and that the budget applies.

## Custom actions grow up, and settings become portable (v1 sweep stage E, slice 3)

Plan M5's last two feature items (§4e). Five code commits plus this docs commit: `8b2b589` schema + verb registry + resolution, `7ab0c51` dispatch, `b83c530` Actions tab, `50fd566` the transfer module, `cd34766` the dialogs.

### A custom action was a rewrite, whatever its instruction said

`actionBindingSchema` already carried `customName` and `customInstruction`, and `action-resolution.ts` hardcoded `verbClass: 'transform'` for anything that was not a registry verb. So a custom action called "Check the numbers", with the instruction "flag every unsupported number", replaced the selected text with the answer. The instruction and the effect were unrelated.

`customVerbClass` (`transform` | `generate` | `review`) fixes that, and it is **required with no default**. That was the decision worth making: a Zod default of `'transform'` would have satisfied "class required" on paper while keeping exactly the bug above for every action whose author did not think about the dropdown. So a custom action with no class resolves to a new typed reason, `custom-class-missing`, and is offered nowhere — the same treatment a blank name or a blank instruction already received, surfaced the same way in the tab.

### One verb interface, because two would drift

`resolveActionVerb(actionId, custom?)` in the verb registry is now the only way a dispatch path turns an action id into the verb it runs: the registry entry for a built-in id, the custom action's own `ActionVerb` (label + class + already-resolved instruction) otherwise. Built-ins win over a supplied custom verb — a persisted binding must not be able to redefine what "Humanize" does behind the shared label.

The consequence in the controller is the interesting part. `startBoundAction` used to split on `verbClass` FIRST and then, on the transform branch only, resolve a custom instruction from the vault. A review-class custom action had nowhere to put its instruction, which is precisely why custom actions could not be review-class. Verb resolution now happens ahead of the split (`resolveBoundVerb`), so all three routes receive the same resolved verb — and a review-class custom action can bind a panel, because the panel rule was already written in terms of the class rather than in terms of "is it built-in".

Two asymmetries kept on purpose: the review branch reuses the already-resolved instruction across the size-confirmation round trip (the instruction rides inside `RunInstruction`), while the transform branch re-enters at the top and re-resolves. And an action whose instruction resolves to nothing still refuses with a Notice rather than dispatching — billing a backend to ask for nothing is worse than a refusal.

### `followLinks` on an instruction now means what it means everywhere else

The custom-instruction UI needed the note-refs control, and that control ships a "Follow links" toggle. Rendering the toggle and ignoring the flag would have been a lie, so `resolveCustomInstruction` now expands it with the SAME semantics as context assembly: depth 1, embeds count, deterministic link order, `FOLLOWED_LINKS_CAP` per referenced note, exclusions decided before any content is read, each note inlined once. Excluded notes are never followed either (Business Rules #7).

The instruction cap (`CUSTOM_INSTRUCTION_MAX_CHARS`) makes this safe: the direct text is serialized first, so the cap can only ever cut reference material, never the directive itself.

### Export and import: the key rule runs in both directions

`domain/settings/settings-transfer.ts` is pure and owns the whole contract; `settings/transfer-model.ts` owns every string the user reads; `settings/transfer-modals.ts` is glue that wires checkboxes and writes one file. Entry points live under Behavior → Import & export.

**API keys never travel.** Stripping happens inside `exportSettings`, the only function that produces an export, so no call site can forget. The import clears the field too — even when the file carries a key. That second half matters more than it looks: a `data.json` copied from another vault is a legitimate import source, and accepting its key would silently bill its owner's account. Both dialogs state the rule on screen, because "my keys are in this file" is the one wrong assumption a user could act on by sharing it. The advanced `extraBodyJson` field travels as-is; it is functional request configuration, and blanking it would break the backend it configures.

**Imports add.** Every imported entity gets a fresh id, and references inside the import are remapped onto the new ones. `resolveIdCollisions`' load-time semantics — keep-first, references untouched — were considered and deliberately not reused: there a duplicated id means "the same entity twice after a sync merge", so keeping references pointing at the survivor is right; here it means "a different entity from another vault", and keeping the reference would point an imported panel at the user's own editor. A reference to something OUTSIDE the import survives only when that id exists in the current settings, which is what makes re-importing panels back into the vault their member editors still live in do the obvious thing; otherwise it is cleared and reported as a typed adjustment.

`voiceProfile` is the exception: a single value cannot be added, so it replaces, and the summary says so in capitals before anything is written.

**Nothing is silent.** Elements are validated one by one, so a hand-edited entity never drops its siblings. Everything that cannot come in is a typed rejection with a reason the dialog spells out: invalid for this version, a panel none of whose member editors exist here, a built-in verb already bound (two bindings for one verb would give it two menu entries and make every lookup depend on array order), or a section already at its schema maximum. That last one is enforced while PLANNING rather than at save time, because the facade rejects a schema-invalid update wholesale and "could not save" names nothing; the cap constants mirror the schema and a spec pins the mirror against `pluginSettingsSchema` itself.

The format marker is not required on import — a foreign `data.json` has none. An object with no recognizable section is the error case, because that is when the user picked the wrong file.

## The panel can start a review (GitHub issue #16)

Two commits: `e749cf2` the pure gate + button state, `e0d85ab` the panel header and the dispatch.

### One gate, and it says why

`isReviewable` answered a yes/no. The panel button needs the same answer plus the REASON, because the whole point of the control is that it adapts to the bound note: an excluded note and a kill-switched note are both "no", and their fixes are in different settings tabs.

So `reviewGate` is now the single evaluation and returns `excluded` / `rule-disabled` (with the rule label) / `no-editor` / `ok`, with `isReviewable` and `isPluginEnabledForNote` as projections of it. A spec pins the projection in every case, which is the actual guarantee: an explanation cannot drift from the decision it explains, because there is only one decision.

The note-level half (`noteGate`) is split out so `isPluginEnabledForNote` never pays for the editor/backend scan it does not care about — it runs on every rail refresh of every open pane.

### The panel gained a header, not a button

`SidePanelBinding` requires a run. A Review button that only exists once a run exists is useless: a note with no findings yet is exactly when you want to start one. So the binding became the optional half of a `SidePanelState` whose other half is the review target, and the header (bound note name + button) renders regardless.

`setBinding` became `setPanelState`. The rename is not cosmetic — `setState` collides with Obsidian's `View.setState`, and the collision is a compile error rather than a silent shadow only because `noImplicitOverride` is on (AGENTS.md's reserved-name hazard, caught by tsc on the first run).

### Refusing, not cancel-replacing

`RunController.startRun` cancels the previous run for the same file. The rail's button turns into Cancel while running, which is right there — the rail sits in the editor, on the text. In the panel it would be wrong twice over: the panel is DISPLAYING that run's findings, and a click on a button that looks like "Review" would destroy them.

So the panel button refuses while a run or retry is in flight, gated on `canCancelRun` — the same predicate the `Cancel review or action` command uses. That is not a coincidence to be tidied away later: "a run is in flight" has exactly one definition, and the button refuses exactly when cancelling is possible. The check is re-done on click rather than trusted from the rendered state, because a run can start between the last render and the click.

A transform/generate run deliberately does NOT count as busy. `startReview` never replaces a transform run, so nothing is lost by dispatching alongside one, and the shared concurrency gate queues the request. The rail shows both as running because it has one button for both; the panel button is about reviews.

Busy is read through a THUNK, not captured as a boolean. The panel re-renders on run notifications without any push from the controller, so a captured value would leave the spinner turning after the run settled. The spinner itself is `aria-hidden` decoration — the label and the accessible name already say "Reviewing…", so announcing it twice would be noise — and it is static under `prefers-reduced-motion`, because a slow local model can legitimately spin for minutes (WCAG 2.2.2).

### A kill-switched note gets a disabled button, not a hidden one

Plan §4b says a matching `disabled` rule removes the plugin's chrome from a note, and the panel binding is indeed gone. Following that literally would hide the button too — and leave the user staring at a blank leaf they opened on purpose, with no way to learn that a rule emptied it.

The kill switch's promise is that nothing dispatches. A disabled button dispatches nothing. It also names the rule and the tab to find it in, which is the difference between an explained panel and a mysteriously empty one.

## The setup wizard, and M5 is feature-complete

Plan §4f. Two code commits — `540b2c0` the pure core, `592a464` the modal, its copy, the command and the first-run trigger — plus this docs commit.

### Nothing is written until Finish

The task allowed committing per step or at the end. Per-step commits sound safer and are not: they require every step to be independently valid, and the backend step is not. A label with no model is a backend that exists and cannot run — persisting it mid-wizard is precisely the "broken settings" the requirement was about.

So the wizard accumulates a draft and `applySetupWizard` turns it into ONE settings update. Cancelling at any step cannot leave a half-configured plugin because there is no sequence of partial writes to interrupt. The apply is a pure whole-value function, which is what makes "everything the wizard did not touch comes back identical" a spec rather than a hope.

### Empty is allowed; half-filled is not

Every step except the backend is optional by nature — which editors, which voice notes, which mode all have defaults. The backend step is optional too, and that matters: a user who wants to look around before pasting a key must not be trapped on step 2. But it refuses to advance with an incomplete backend, because that is the one input where some of it is worse than none of it.

The refusal reuses the Backends tab's rule rather than restating it. `domain/settings/backend-validation.ts` now owns what makes a backend usable, messages included, and the tab's dialog calls it instead of carrying its own copy of the checks. The messages live with the rule on purpose: each one IS the rule stated in words ("OpenAI-compatible backends need a base URL"), and splitting them into a copy module is how two surfaces end up enforcing the same requirement while explaining it differently.

### `onboarded` means "the wizard has had its chance"

The schema field already said it: "True once the setup wizard completed **or was skipped**." So any exit sets it — Finish, Cancel, Escape, the X. The alternative (only Finish sets it) turns an accidental dismissal into a modal that greets you on every launch, and the flow is re-runnable from a command and a Behavior → Setup button, so "seen" is never a one-way door.

Re-runs are edits, not resets: the draft seeds from the current settings. One deliberate exception — the wizard never edits an EXISTING backend. It adds one. Silently rewriting a configured backend from a flow called "setup" would be a surprise, and the Backends tab is where editing lives.

### The default-backend wiring is the difference between working and looking like it works

Editors inherit their backend. A wizard that added a backend without also making it the global default would end with a configured backend, six enabled editors, and nothing that runs — the exact state the wizard exists to prevent, presented as success. So a wizard-added backend becomes the default when there is none. When one already exists it is never repointed: a re-run must not silently redirect a working setup.

The same instinct drives the last step. It reports "nothing will run yet" from `hasReviewCapableEditor` over the settings about to be written — the predicate that knows about disabled backends, dangling references, missing models and per-editor overrides. Re-deriving an approximation of it inside the wizard is how a "you're all set" screen starts lying, so `setupOutcome` deliberately does not carry that field at all.

### Test connection tests the thing that matters

The cheap ways to test a connection answer a question nobody asked. A models-list GET or a bare chat completion goes green for an endpoint that authenticates perfectly and then fails every review, because the model will not produce the structured output the operation contract requires.

So the health check sends a real `review` operation over a one-sentence document through `createApiEditorExecutor` — the same path a review takes. A pass means "reviews will work here".

That produces **three** outcomes rather than two, and the third is the useful one: an endpoint that answers but whose payload the plugin cannot parse is `unusable`, not `failed`. Credentials and connectivity are fine; the model is not. Different sentence, different color, different fix.

Its timeout is 60 s, deliberately NOT `behavior.requestTimeoutSeconds` (ten minutes by default): a connection test that can hang for ten minutes is not a test. And because 60 s genuinely is not always enough for Ollama to load a cold model, the timeout message says a real run may still succeed with a higher request timeout — so a slow local model is never reported as a broken one.

### Two small implementation truths

Field edits skip the re-render, because text inputs must keep focus. That has a consequence the obvious code gets wrong: the Test connection handler must read the backend at CLICK time (a draft captured at render time would test the model as it read one keystroke ago), and its in-flight guard must key on the backend's **id** rather than object identity (every keystroke replaces the draft object, so identity comparison would discard the verdict for anyone who kept typing while the request was out).

And the keyboard: the forward button is focused on every step, so the defaults path is Enter, Enter, Enter through native button activation. A modal-wide Enter binding was written and then removed — with the CTA focused it fires alongside the button's own activation and advances two steps at once.

### Deviation worth recording

The last step's pointers name the command palette, the review command, the rail, the panel and the send preview, but **no documentation URL**. `docs/` is still the template stub (`docs/README.md` says "TODO: Add a brief description"), and shipping a first-run flow that sends new users to a placeholder page is worse than not mentioning it. Add the pointer when M9 fills in the docs content.

## Stage E review fix pass

External review of stage E (binding rules, context budget + send preview, custom actions + settings transfer, the panel Review button, the setup wizard) returned 17 findings. Every one was verified against the code before touching it; all 17 were real, and all 17 are fixed. Five code commits, privacy first: `06be0ff`, `47dd1f1`, `7de8c4c`, `ba85644`, `b42ba2c`, plus this docs commit.

### An imported backend is a destination, and the confirmation never showed it

The blocker. `planImport` cleared `apiKey` and kept everything else verbatim, and `importSummaryLines` reported counts — never a URL, never that an imported editor joins every review.

The stripped key is no protection. `resolveApiBackend` never checks for a key; Ollama's request builder needs only a model and a base URL; the OpenAI adapter requires a key for `openai`/`openrouter` and nothing else. Imported editors arrive enabled with `capabilities.review` on, and with no `assign` rule matching, `startReview` runs every enabled review-capable editor. So a foreign settings file — the documented import source, since a bare `data.json` with no format marker is accepted on purpose — could silently add a review participant that ships note text plus every linked-note attachment to a host the user never saw.

Two changes, and the second is the one that matters. API-family backends now arrive **disabled**, with a typed `backend-disabled` adjustment: enabling one means opening the Backends tab, which is where its URL is. And the confirmation now lists, per imported backend, its kind, the host it would send to (or "<kind> default" when it has no base URL — never a blank), and whether it carries a custom request body; plus a line stating how many imported editors would take part in every review of every note.

The equivalent honesty problem runs the other way on export. `EXPORT_KEY_NOTICE` asserted "API keys are never exported" and the dialog called the file "safe to share", but `exportSettings` strips only `apiKey`: `baseUrl` and `extraBodyJson` travel verbatim, because they configure the request and blanking them would break the backend. A gateway URL of the form `https://gw.example/v1?api-key=SECRET`, a `https://user:pass@host/v1`, or an `extraBodyJson` holding the token for a host that takes it in the body all end up in a file the dialog said was safe to hand over. Rather than redact functional configuration, the export DECLARES it: `exportSecretRisks` names the backends concerned and the dialog says why, and the notice now says the key **field** is never exported.

Deliberately broad detection (`@`, or a query key containing `key`/`token`/`secret`/`password`/`auth`/`sig`): a false positive costs one sentence, a false negative costs a live token.

### A cap that runs after remapping orphans every reference into it

`capSection` trimmed sections AFTER cross-references had been rewritten, so an entity dropped by a cap left survivors pointing at an id that would never exist — and no adjustment reported it, contradicting the module's own rule that every cleared reference is a typed adjustment. Reproduced: 199 existing editors plus an import of 2 editors and a panel over both yields `additions.panels[0].memberEditorIds = [gen-0, gen-1]` with `gen-1` never added, and `adjustments: []`.

The fix is ordering, not patching. Each section's survivors are settled first, in dependency order (backends → editors → panels → actions → rules), and only then are ids generated and references rewritten. A capped-out entity is therefore indistinguishable, to everything that referenced it, from an entity that was never in the file: the reference goes through the same `remap` path and comes out cleared and reported. Salvaged entities now carry their source index through every filtering pass, so a rejection names the position in the file rather than a position in an intermediate array — and the member pass still runs before the panel cap, so room freed by a memberless panel goes to the next one.

### `..` in the export path was resolved by the adapter, not by us

`normalizeExportPath` stripped leading slashes and appended `.json` and never looked at `..`. The result went to `vault.create`, whose adapter joins it onto the vault base path and resolves the traversal — writing outside the vault, past Obsidian's sandbox and past the dialog's `getAbstractFileByPath` existence check, which only ever sees in-vault paths and therefore skipped the overwrite confirmation for exactly the files least safe to overwrite silently. It now returns a typed refusal; backslashes are folded first so `..\escape.json` cannot slip through.

### The trust surface could not show what a custom action sends

`previewEditorContext` called `buildEditorPrompt` with no instruction and had no entry point that took a verb — yet `resolveCustomInstruction` inlines referenced vault notes into the dispatched instruction, up to `CUSTOM_INSTRUCTION_MAX_CHARS` (10 000). So up to 10 KB of vault content left the vault on every custom-action run without appearing in the one surface whose module doc promises that the prompt shown IS the string the adapter receives, and whose modal claims to show exactly the assembled context.

The preview now takes an optional action binding. `resolveBoundActionVerb` moved out of the controller into `action-resolution.ts` and both callers use it, so preview and dispatch cannot resolve different instructions — that shared function is the fix, the picker is just how it is reached. A review-class instruction is appended to the system prompt exactly as `startReview` appends it, so the byte-for-byte spec still holds with an action selected. A transform/generate instruction rides the operation payload instead, so it gets its own summary line with its own size and an explicit statement that it is not in the prompt and not in the budget — folding it into the budget report would have been a second lie, since the instruction obeys its own cap, not `contextBudgetChars`. The clipboard payload carries it too, for the payload case only: repeating a review-class instruction would misrepresent the request as sending it twice.

An action that no longer resolves is a refusal, matching the dispatch. The editor dialog's Preview button gets no picker on purpose — its question is about the draft persona.

### A regex from another plugin's settings ran unbounded on the UI thread

`mappingMatches` compiled and executed an OSK note-type `regex` mapping inside synchronous decisions that fire on every rail refresh, menu build and command gate. ## A panel run becomes one run (v1 sweep stage F, slice 1 — plan M6)

A panel used to be a fan-out: an action bound to a panel, or a rule assigning one, resolved the panel to its member ids and started N ordinary reviews that happened to begin together. Nothing downstream knew a panel had convened. This slice makes a panel run a first-class run — the members AND the aggregation step that follows them — and settles the partial-failure policy M6 required.

Three code commits: `6ffdb22` (charter seam), `ef41d84` (run + aggregation lifecycle), `89e8583` (dispatch), plus this docs commit.

### The charter is a shared brief, not a script for the chairperson

Plan §4 called `charterSource` "aggregation instructions", and the starter panel's charter was written to match: _"You are the chairperson of the Pre-publish Review panel. Four editors have each reviewed the same document… Produce: 1. A verdict per member…"_.

Two things are wrong with that once the charter has to reach the members. Read in a member's prompt it is nonsense — a member is not the chairperson and produces findings, not verdicts. And it re-specifies output the `aggregate-panel` operation prompt already dictates, in a contract-shaped way the user cannot change anyway (`kindRules` in `providers/prompt.ts` already says: never invent findings, record real disagreement in `dissent`, list failed members in `missingMembers`, rank `topFixes` by impact).

So the charter is now the panel's shared brief — what this panel is for and how it weighs things — and it plays both roles: appended to every member's system prompt, and used as the system prompt of the aggregation call. One user-authored field, no place for the two halves of one panel to disagree about what the panel is for. A second field ("brief for members" plus "instructions for the chairperson") was considered and rejected for exactly that reason.

The starter charter was rewritten accordingly: the publication bar, the four failure modes the panel exists to catch, the weighting rule (one load-bearing objection outweighs several shrugs), and an explicit instruction that every member keeps its own mandate. That last line matters — a panel that homogenized its members would be four copies of one editor, which is the opposite of why panels exist.

### It rides the existing seam, through the one prompt-build entry point

`augmentPanelCharter` sits next to `augmentSystemPrompt` and is applied inside `buildEditorPrompt`. Order: persona + context, then the charter, then the per-run instruction — the last block is the most salient, and the instruction is what the user asked for THIS time while the charter is standing context for every run of that panel. Because it goes through `buildEditorPrompt`, the "what will be sent" preview keeps showing the exact string the adapter receives.

Charter resolution needed the same `PromptSource` machinery a custom action's instruction already had: resolve fresh at dispatch time, never read an excluded note, never FOLLOW into one, inline each note at most once, cap the followed links, cap the total. That is four privacy/config guarantees in one loop and it was about to exist twice, so it came out as `resolvePromptSourceText` (services/context) parameterized by block tag and cap. `resolveCustomInstruction` delegates to it; `resolvePanelCharter` is the second caller. The persona/voice-profile path deliberately does NOT route through it — that produces budgeted `ContextAttachment`s with a reported drop list, a different shape with a different failure mode.

### Members are ordinary editor streams, on purpose

`StartRunInput.panel` adds the aggregation step and nothing else. Members go through the same anchoring, the same `FindingStore`, and the same plugin-wide `Semaphore` — so a four-member panel under `maxConcurrentRequests: 2` cannot starve another note's run (a spec pins the FIFO interleaving), and every finding keeps the `editorId` of the member that reported it. A panel weighs its members; it does not merge them, and nothing re-attributes a finding to the panel.

### Partial-failure policy — decided

`domain/panels/panel-aggregation.ts`, pure and spec-covered:

**The panel completes with the members that succeeded.** A member that failed is reported as failed, stays individually retryable inside the run, and travels to the chairperson with `failed: true` so the scorecard can state what it did not see. Aggregation runs as soon as at least ONE member succeeded; with none it reports `skipped` rather than billing a backend to synthesize emptiness.

The alternative — fail the whole panel when any member fails — was rejected. One member timing out on a laptop-hosted model is common enough that all-or-nothing would mean "usually nothing", and three honest reviews plus a named gap is strictly more useful than a refusal.

Two smaller decisions inside it. A member that finished with zero findings SUCCEEDED: a clean read is a real verdict, not a failure. And the failed members still travel in the request, because sending only the survivors would let the chairperson write a confident scorecard over a partial panel without ever knowing it was partial — the exact failure `missingMembers` exists to prevent.

Verified explicitly, since M6 asked: the stage-A per-editor retry machinery works inside a panel run. Retrying a member replaces its findings as usual, AND re-opens the panel — the scorecard that named it missing is about to be wrong, so it is discarded and re-derived when the run settles again. An attempt epoch guards it, mirroring the per-editor `runId` attempt check: a late aggregation settle carrying an older epoch belongs to a scorecard the run has already thrown away.

### Cancellation reaches the scorecard

`cancelRun` cancels every in-flight member and the pending or in-flight aggregation — the scorecard is a statement about a run the user just stopped. An already-produced scorecard is left alone, exactly like the findings of the members that did finish: cancelling stops work, it does not erase results.

### Dispatch: one path, so no surface can convene half a panel

`startReview` takes a `panel`, but the interesting case needs no caller at all: the rule outcome is resolved inside `startReview`, so a binding rule assigning an ENABLED panel makes the run a panel run for the command, the rail, the panel Review button, the CLI and the daemon at once. A DISABLED panel still supplies its members — the flag governs the panel as an aggregation entity, so turning it off drops the charter and the scorecard, not the reviewers. That is the promise `resolveRuleEditorPool`'s own header already made before M6 existed; it is now true rather than aspirational, and `RuleEditorPool` carries `panelId` to say so.

A review verb bound to a panel dispatches ONE panel run with its instruction on top of the charter. A daemon refresh carries the panel identity of the run it refreshes — dropping it would silently downgrade the note to loose editors.

`panel-unavailable` (missing / disabled) is its own refusal rather than falling through to `no-editors`: the members may be perfectly healthy, and the fix is in the Panels tab. Conversely, a panel whose aggregation backend does not resolve still RUNS — the members' reviews are the bulk of the value, and the scorecard reports `unavailable` instead of the whole run being refused over a settings mistake the user can fix after reading the reviews.

One tidy-up fell out: `resolveApiBackend` is now a thin call over a new `resolveBackendRef`, which the panel's aggregation backend uses. Two implementations of "inherit the default backend" would have drifted.

Specs: 1434 → **1472** (+38), per commit +11 / +19 / +8 — verified by running the suite at each commit, not by arithmetic on the diff.

Gates: `bun run format`, `bun run validate` (tsc + eslint --max-warnings 0 + 1472 tests), `bun run build` green after each commit. Nothing pushed.

## The scorecard is typed, budgeted and on screen (v1 sweep stage F, slice 2 — plan M6)

Slice 1 made a panel run one run and settled the partial-failure policy. This slice makes its OUTPUT a first-class thing: a typed `PanelResult` the aggregation must produce, an input that fits a budget, and two surfaces that render it.

Four code commits: `cdb9e4e` (contract), `ffdb4f8` (aggregation compaction + budget), `6bb0efb` (side-panel scorecard), `35e1ba1` (rail panel entity), plus this docs commit.

### `topFixes: string[]` and `dissent: string` were the two weakest fields in the contract

Both were already there; both were the wrong shape for what the panel is for.

A top fix that reads _"tighten the opening paragraph"_ leaves the user to find the span themselves — even though the member that reported it quoted that span verbatim, two fields away. So `topFixes` is now `{ action, editorName?, quote? }`. The pointer is **optional and stays optional**: a legitimate top fix can be structural ("cut the second half") and anchor to no single span, and a pointer the model invented to fill a required field would be strictly worse than none.

`dissent` as one string invites the model to average four readings into one balanced sentence and lose which member held which position. That is the exact information a panel has and a single editor does not, so it is now `{ subject, positions: [{ editorName, stance }] }[]` — subject and positions in separate fields, so no surface downstream can merge them, and an empty array stays a valid "they agreed". The prompt rules say not to report a difference of emphasis as dissent, because a schema that rewards filling the field would get it filled.

Two smaller additions: `recommendation` gained a one-line `rationale` (a verdict token states a conclusion without stating why), and the aggregation request's members gained `omittedFindings`, filled by the budget below.

### The aggregation request had no budget, and would have been truncated by the model

A four-member review of a long note produces hundreds of findings, each carrying anchoring aids, evidence and a full replacement suggestion. Sent raw that request is several times the size of the note the members read — and the thing that then truncates it is the MODEL, silently, in the middle, with no record of what it dropped.

`domain/panels/panel-aggregation.ts` now does the dropping, and reports it.

**Compaction** is unconditional and per field. `prefix`, `suffix`, `occurrence`, `confidence`, `rationale` and `evidence` go: the chairperson weighs members — it never anchors a span, re-verifies a source or applies a replacement. `critique`, `suggestion` and `summary` are clipped to fixed caps. **Quotes are never truncated**, because a `PanelTopFix` points back at its finding BY QUOTE and a shortened quote comes back as a pointer that resolves to nothing or, worse, to the wrong span.

**The budget** is half of `contextBudgetChars`, minus the charter (which IS the aggregation call's system prompt, and is never truncated for the same reason a persona is not) and the member envelopes, with a floor so a user who set a small review budget still gets a usable panel.

**Fitting is round-robin**, one finding per member per pass. Filling member by member is the obvious implementation and the wrong one: a spec pins the exact case where sequential filling spends everything on A and B and leaves C — the last member of the panel — entirely unheard, while the scorecard claims to weigh it. Round-robin gives C a turn first.

A member whose next finding does not fit **leaves the rotation**; its remaining findings are omitted even when a later, smaller one would have fit. Skipping one and taking the next would present the member's list as something other than a prefix, and a prefix is exactly what `omittedFindings` promises — which is what lets the chairperson reason about what it did not see. Truncation is never per finding: half a critique changes what the member said, while a shorter list of complete findings is honest and countable.

### The scorecard renders above the member sections, never instead of them

`ui/panel-scorecard.ts` is a pure projection with its own specs; the side panel only turns it into DOM.

It produces a view for **every** aggregation status — waiting, running, failed, cancelled, skipped, no backend — and the member sections render underneath it in all of them. There is no branch anywhere that hides the run because the synthesis failed: an aggregation that dies costs the user a summary, never the four reviews they paid for, and the failure copy says exactly that ("the member reviews below are unaffected"), with the redacted backend message under it. `unavailable` names the setting that fixes it.

A member that failed is listed even when the chairperson never mentioned it, marked "No review — not weighed". Silence about a member that did not run is the failure `missingMembers` exists to prevent, and the prompt tells the model not to speak for it.

**Top-fix resolution** (`resolveTopFixFinding`) matches the fix's quote against the live findings: exact inside the credited member, then exact anywhere, then the same two passes on whitespace-and-case-normalized text. The normalized pass runs LAST so an exact match is never displaced by a fuzzy one (a spec pins the case where the credited member's finding only matches after normalization and another member's matches exactly — the exact one wins). No match means no pointer, and the row renders as plain text rather than a button: revealing the wrong span is worse than revealing none, because the user acts on it (Business Rules #4), and a control that cannot act must not look like one.

Dissent renders as structure — subject, then each member's position — never collapsed.

`verdictLabel` (All good / Needs work / Not ready) moved out of `side-panel.ts` into its own module. An editor's verdict and a panel's recommendation are the same vocabulary; two relabelings would eventually have disagreed about what `kill` is called.

### The rail shows the panel as one entity (Business Rules #11)

The rail rendered a panel run as N loose editor dots, indistinguishable from four unrelated editors that happened to start together.

A panel run is now ONE **hollow ringed** chip inside a bracketed group holding its member dots. Editors stay SOLID: the distinction is shape, so it survives at 16px and does not depend on colour. Editors that are not members keep their place outside the group — a panel weighs its members, it does not absorb them.

The chip projects the scorecard's lifecycle through the SAME mapper the side panel uses (`scorecardStatusKind`), so the two cannot disagree about where the aggregation stands, and the overall verdict rides it as a badge. `(panel)` is in the accessible NAME, not only in the shape — a ring is invisible to assistive tech, so #11 would otherwise hold only visually. Selecting it opens the side panel: a verdict, ranked fixes and dissent do not fit in a tooltip. The compact rail keeps the ring and drops the badge (no room at 12px); the tooltip carries it.

One pre-existing defect fixed on the way: `applyTooltip` wrote the tooltip into `aria-label`, clobbering the name the Review button set immediately before it — so the compact button's accessible name was the narrow-pane guidance rather than what the control is, which is precisely the split the stage-D fix pass introduced the two fields for. The name is now a parameter defaulting to the tooltip.

## Editors stop looking like panels, and an editor can be asked for more (v1 sweep stage F, slice 3 — plan M6)

Four commits: `435e6ad` (entity vocabulary), `f4b1816` (continuation core), `37ce095` (continuation UI), `00ec193` (charter refinement), plus this docs commit.

### Business Rules #11 was being satisfied four times, in four wordings

The rule says editors and panels must be distinguishable in every surface. Four surfaces each had their own answer, and each was half an answer.

The rail wrote `(panel)` inline in the chip's accessible name. The settings dropdown wrote `◎ Name (panel)`. The scorecard header drew a ring and then printed the bare name. The context menu and the palette said **nothing at all** — an action bound to a four-member panel read exactly like one bound to a single editor, so the surface where the choice costs the most was the one surface that did not mention it.

`ui/entity-label.ts` is now the one author, with the two decisions stated in it rather than rediscovered per surface:

**The distinction is never carried by shape or colour alone.** A ring is invisible to a screen reader and unreadable at 12px to plenty of sighted users, so wherever a panel is named, the name says `(panel)`. The glyphs are an addition.

**Only panels are marked.** An editor is the unmarked default — it is what the rest of the plugin is already about — so tagging both kinds would turn the marker into noise and stop it standing out. That asymmetry is why `entityName` takes the kind rather than the caller picking a helper.

Applied to: the rail chip and the group holding its member dots, the target dropdowns, the scorecard header, the side-panel member sections (an indent plus an `aria-label` naming the panel they belong to — while keeping the editor's own name, because a panel weighs its members and does not absorb them), the editor context menu and the dynamic action commands.

A panel-bound verb now reads `Critique (panel: Pre-publish Review)`. The panel is NAMED rather than merely flagged: one press there is one request per member, so the user is choosing a cost, and "which panel" is what tells them how big it is. Menu **ordering** deliberately still sorts on the bare label — the marker is about which kind the action convenes, and letting it move `Critique` under `C (panel…)` would shuffle a menu people navigate by verb. `ResolvedAction` carries `panelName` for this: one lookup at resolution time rather than four surfaces each finding the name for themselves and eventually wording it differently.

### "Generate more" is the mirror image of Retry, and the difference is the whole feature

`RunHandle.continueEditor` asks one editor for MORE findings. Every respect in which it differs from `retryEditor` is deliberate:

- a retry REPLACES the editor's findings (they came from a failed attempt); a continuation KEEPS them and appends;
- a retry clears the dedupe keys (the new attempt may legitimately re-report); a continuation keeps them, so a literal repeat is dropped on arrival;
- a retry is for `error`/`cancelled`; a continuation is for `done` only. A failed editor has nothing to build on, and a running one is already working.

**Not repeating itself is handled twice, because either mechanism alone is weak.** The request carries `alreadyReported` — quote plus clipped critique, enough to recognize the ground covered without re-sending suggestions, evidence and anchoring aids the editor does not need in order to avoid itself — and the prompt reframes the pass as an additional one, forbidding repeats and rephrasings and _explicitly_ allowing an empty result, because a second pass is exactly the situation that invites padding. Whatever ignores all that still hits the retained dedupe keys. `alreadyReported` is ABSENT rather than empty on a first pass, so a backend can tell "nothing yet" from "found nothing".

### The failure policy is what makes the feature safe

A continuation that fails or is cancelled does **not** put the editor into `error`/`cancelled`. It restores `done` and records `continuationError` separately.

Marking it failed would be the obvious implementation and a data-loss bug: `error` and `cancelled` are exactly the statuses that offer **Retry**, and Retry replaces an editor's findings. One click, immediately after an optional extra pass timed out, would destroy the first pass's findings — the ones the user was in the middle of triaging, and the only reason they pressed the button in the first place. So the editor stays finished, the failure renders as a note beside the button, and Retry is not offered at the moment it would do the most damage.

The same reasoning governs summary and verdict: a continuation that reports neither leaves the first pass's standing. It was an _additional_ pass, so silence about the note as a whole means "nothing to add", never "withdraw what I said".

New findings anchor against the text passed in at call time — a fresh per-editor anchor base, exactly like a retry (Business Rules #3/#4) — so the extra round reads the note as it is now, which is also what the user is looking at. A member going back to work re-opens its panel's scorecard, which named which members it weighed and what they found and is about to be wrong; `reopenPanel` is now shared with `retryEditor` instead of duplicated.

### The count is in the button because the button costs money

`Generate more (n)` sits under each finished editor's bulk row — the opposite move to bulk triage, acting on the same list, which is why it belongs there. `n` is how many findings are already on the note.

A bare "Generate more" would read as a free refresh. With the count it reads as "add to these three", which is what it is, and the number changing after a round is the feedback that the round did something.

The button **disables rather than disappears** while its own round runs: a control must not vanish under the pointer that just pressed it, and that is also what makes one press one round — a double click cannot buy two. There is no auto-repeat and no "keep going" mode.

An editor sitting at `(0)` still gets the button. "I found nothing" is a real answer, and it is worth challenging once.

The count comes from the findings the section shows and is deliberately **not** the severity-filtered list: the lens hides findings from view, it does not un-report them, and telling an editor it found fewer than it did would invite it to repeat them.

`Generate more findings` in the palette does one round for every finished editor of the active note's run — the whole-note gesture, keyboard reachable. Still one round each.

### The starter charter had no opinion about ranking

Slice 2 made top fixes ranked and pointed at a span, dissent a structure of attributed positions, and the recommendation carry a rationale. The `aggregate-panel` operation prompt dictates all of that as FORMAT. Nothing supplied the judgment behind it, so the model was being asked to rank by nothing and to preserve a disagreement it had no reason not to average.

Two paragraphs added at charter level: rank by what unblocks publication (blocking first, then what visibly improves the document, polish last or not at all), prefer a concrete action tied to the exact passage over a description of the problem — a fix the author cannot locate is a fix they will not make; and keep disagreement as the positions actually held, attributed, rather than a middle nobody argued for, while a difference of emphasis stays not a disagreement.

Both read correctly in the charter's other role. It is appended to every member's prompt, and "name the blocking problem first, quote the passage, do not soften what you disagree with" is advice a single member can follow as written.

## Stage F review fix pass — and the CLI finally sees a panel (v1 sweep stage F — plan M6)

External review of the three panel slices: 15 findings, every one verified against the code before touching it, none dismissed. Five commits: `6d11cdf`, `f2c62b6`, `ab409e9`, `a2d5313`, `49cd9f3`, plus this docs commit.

### "Settled" was answering the wrong question

`isSettled()` derives from the editor states, and `maybeAggregate()` only opens the aggregation once it is already true. So a panel run reported itself settled for the entire time its scorecard request was in flight — and every busy gate in the plugin keys on that predicate. Cancel disappeared from the palette at the one moment there was a single request left to cancel, `ai-editor cancel` answered `already-settled`, the rail swapped its spinner for Review, the side-panel Review button started a run that cancel-replaced the aggregation, and the daemon's probe read the note as free. `cancelRun`'s own documentation promises to cancel "the pending/in-flight aggregation"; that branch was unreachable from every user surface.

The fix is not to redefine `isSettled` — two consumers need it exactly as it is (`maybeAggregate` would deadlock on itself, and the CLI's `settled` promise is about the member streams). `isBusy()` is the new question: **is anything still running**, editors plus a waiting/running panel. Six surfaces ask it now; `isSettled` keeps its two callers and a doc comment saying which is which.

### A continuation does not invalidate what it adds to

`continueEditor` reused `reopenPanel()`, which nulls the scorecard. For a retry that is right — a retry REMOVES the editor's findings, so the top fixes point at spans that no longer exist. For a continuation it is backwards: the findings are all still there, so every member verdict still holds and every fix still resolves. Worse, the loss was unrecoverable: `cancelRun` moves a `waiting` panel to `cancelled` and never re-aggregates, so cancelling the extra round left the run with **no scorecard** while the editor sat back at `done` with its original findings — the exact asymmetry `terminate` and `cancelRun` already implement for `state.continuing`, missing from the panel half.

`reopenPanel({ keepResult })` states the difference in one word. A continuation keeps the result and marks it `resultStale`; the side panel says so in one line above the block ("From the previous round — a member is generating more, so this will be rewritten") rather than presenting it as current or hiding it. A re-aggregation that then fails or is cancelled leaves it alone — which is what `cancelRun` said all along.

### The scorecard is model text; it is now checked against the run

`memberVerdicts[].editorName` is a string the chairperson wrote. Nothing verified it, so a panel that invented a member — or merely misspelled one ("Beginner Reader" for "Beginner") — produced a row for an editor that never ran AND hid the real one, unless it happened to also be in `missingMembers`. `PanelRunState.memberNames` carries the roster; unknown names are dropped and every roster member the panel did not name is listed as `unnamed` (distinct from `missing`: one is the chairperson's silence, the other is the run's own record that no review exists). This is `resolveTopFixFinding`'s stated policy — "returns null rather than guessing" — applied to the function one screen above it that was guessing.

The same function had the mirror defect: its cross-member fallback is deliberate (a fix may quote a finding the credited member did not report), but the row still displayed the model's credit. A row reading "Hater" that reveals Beginner's finding asserts a provenance the click contradicts. `resolveTopFix` returns the candidate, and the credit follows the resolution; the model's name stands only when nothing resolved, which is the structural-fix case.

### The preview was under-reporting what leaves the vault

`previewEditorContext` called `buildEditorPrompt` without `panelCharter`. A charter inlines whole vault notes as `<charter-note path=…>` blocks, so "what will be sent" omitted up to 10 000 characters of vault content in two reachable cases: a panel-bound action (its `panelId` was resolved and dropped) and any note whose binding rule assigns an enabled panel (the rule outcome was resolved and dropped). `buildEditorPrompt`'s docstring names this exact failure — "a trust surface that drifts is worse than none" — and the charter had been added to the dispatch path without its single preview caller. The preview now runs the same panel precedence the dispatch runs, and the charter gets its own summary line rather than disappearing into the prompt total. Pinned by extending the "preview assembly equals dispatch assembly" spec to a rule-assigned panel run.

Also ordering: the `panel-unavailable` refusal sat after the size guard, so an oversized note bound to a deleted panel popped the size-confirmation modal, got confirmed, and was then refused anyway. The rule kill switch is deliberately placed before the size guard for this reason; the panel check needs nothing from the word count and now sits next to it.

### `omittedFindings` was lying about the cap

The field's contract: "carried so the chairperson knows the member's list is a prefix and does not write 'nothing else was reported' over a truncation". It was computed against the ALREADY-capped candidate array, so only budget drops counted — a member holding 500 findings sent 200 and declared nothing omitted. Reachable because "Generate more" appends rounds to the same editor. The pre-cap count is captured per member now; the existing clamp spec asserts the number rather than only the length.

### The CLI now returns the scorecard it was already paying for

Since slice 1, a CLI review of a note whose rule assigns a panel IS a panel run — so the aggregation fires the moment the members settle, and the CLI then called `releaseRun`, which for a note not open in a view discards the run and aborts that request a tick after it started. A billed request nobody ever saw, and inconsistent besides: with the note open, the run survived and the scorecard appeared in the UI.

`ai-editor:review` awaits `panelSettled` alongside `settled` and returns `panel` in its document: verdict, rationale, member rows, ranked fixes with their quotes, dissent, missing members, status, error — plus text-format lines. Every non-`done` status renders, because the member findings are in `findings` either way and "the scorecard was cancelled" is the answer a script needs.

The layering forbids `services/` reaching into `ui/`, and duplicating the two reconciliations is precisely the bug class above, so they moved to `domain/panels/scorecard-model.ts`. `ui/panel-scorecard.ts` keeps the display vocabulary (status copy, `(panel)` marker, verdict labels) and re-exports the resolution, so its callers are unchanged. This closes M6's last open item.
