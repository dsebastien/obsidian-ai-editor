# Configuration

User-facing configuration of the plugin (persisted in `data.json`, schema-versioned with migrations).

## Settings tabs

1. **Backends** — 1-n provider instances (Anthropic, OpenAI, OpenRouter, OpenAI-compatible with custom base URL, Azure OpenAI deployment-based, Ollama), each with label, credentials, default model, per-kind thinking/reasoning controls; CLI agents (explicit executable selection, consented health check) are M7. Global default backend. What makes a backend valid is one rule shared with the setup wizard (`domain/settings/backend-validation.ts`), messages included.
2. **Editors** — persona gallery: name, color, prompt (textarea + ordered note-ref control + follow-links toggle), backend/model override, context policy (opt-in linked notes + cap), capabilities, optional learning memory (settings | vault note), enabled.
3. **Panels** — compose 1-n editors, charter (textarea + note refs + follow-links toggle), aggregation backend/model. Distinct visual identity everywhere both kinds can appear (Business Rule #11), from one vocabulary in `ui/entity-label.ts`: a ring where an editor is a solid dot, plus `(panel)` in the NAME — dropdown options, rail chip and its member group, scorecard header, side-panel member sections, menu items and palette commands. Only panels are marked; an editor is the unmarked default.
4. **Actions** — built-in verbs + custom actions, each bound to an editor (review-class verbs — critique, find evidence, identify assumptions — may bind a panel instead, which dispatches ONE panel run: the charter briefs every member and the run produces a scorecard). A panel-bound action is offered as `<Verb> (panel: <Panel>)` in the context menu and the palette, because one press there is one request per member. A custom action carries its own name, instruction (textarea + ordered note-ref control + follow-links toggle) and, REQUIRED with no default, what it does: rewrite the selection / write more at the cursor / report findings. That class picks the dispatch pipeline exactly like a built-in verb's, so a review-class custom action may bind a panel too; leaving it unset (or blank name/instruction) keeps the action out of every surface, with the reason shown under its row. Changing a bound action away from review-class clears a panel binding the new class cannot use. Bound + dispatchable actions appear in the selection context menu and as dynamic `action-<bindingId>` palette commands (hotkeys via Obsidian's hotkey system; command ids stay stable across renames). Bound-but-undispatchable actions show why under their row; unbound actions stay hidden.
5. **Voice & Style** — global voice profile (textarea + note refs + follow-links toggle), per-editor injection opt-out.
6. **Rules** — ordered binding rules matching folder / tag / frontmatter (`key: value`, or a bare key as a presence check) / OSK note type. Two effects: **Disable plugin** (kill switch — no rail, no menu items, no commands, no dispatch for matching notes) and **Assign reviewer** (an editor, or a panel — which makes the run a panel run, charter and scorecard included). Evaluation: a matching kill switch wins from any position in the list; among the rest the first match from the top assigns the reviewer (one rule, never a union); a note no rule matches is reviewed by every enabled editor. Assignments supply the DEFAULT pool only — an explicit ask-an-editor / bound action, and a daemon re-dispatch of a note's previous run, both win over a rule. OSK note types resolve two ways: the Starter Kit plugin's own type names when it is installed (optional, feature-detected, never required) and the `type/<x>` tag convention, which always works; a rule matches either spelling. Rows say what they resolve to, and say so when a rule does nothing.
7. **Behavior** — the **setup wizard** entry point (see below), size-warning threshold, concurrency, request timeout, character context budget (the copy states the spend order and points at the preview command), daemon mode (off by default; toggle + idle delay — automatic review refresh after the user pauses editing, cost implication stated in the toggle copy, Business Rule #1 carve-out), exclusions (folders, tags, `editor_ai_daemons: false` frontmatter flag, strip-frontmatter toggle), default comment editor, language override, and **Import & export** (see below).

Every prompt source (voice profile, editor prompt, panel charter) carries a `followLinks` flag ("Follow links" toggle on its note-refs block). All three are live (the charter's since M6 slice 1, where the charter started reaching every member's prompt and the aggregation call). When on, context assembly also inlines the notes linked FROM each referenced note — depth 1 only, embeds count, deduped against already-included notes, capped at 20 per referenced note (deterministic link order), subject to `contextBudgetChars`; unresolved/non-markdown links skipped silently, excluded referenced notes never followed. Default ON for the voice profile (its motivating case: `[[My Voice Profile]]` linking out to style notes), OFF elsewhere.

## What will be sent (preview)

The palette command **Preview what will be sent** and the **Preview** button in the editor dialog open one read-only modal showing the REAL assembly for one editor and one note: total characters against the budget, one row per section (system prompt, reviewed note, every attached note) with its size and whether the budget truncated or dropped it, the resolved backend, and the verbatim system prompt, with a copy button. It sends nothing.

The palette command additionally offers an **Action** picker listing every dispatchable bound action. Choosing one previews what THAT dispatch sends: a custom action inlines its referenced vault notes into its instruction (up to 10 000 characters), so a preview that only ever showed the plain review understated the request by everything an action adds. Review-class instructions are appended to the system prompt, exactly as `startReview` appends them; transform and generate instructions travel in the operation payload, so they are reported separately, with their size, and the summary says which of the two it is. An action that no longer resolves — deleted, class cleared, every instruction note missing or excluded — is a refusal, because the dispatch refuses in exactly those cases.

Both entry points assemble through the same `buildEditorPrompt` a dispatch uses, and resolve an action's instruction through the same `resolveBoundActionVerb` — a preview that re-derived either would eventually disagree with the request, which is the one failure a trust surface may not have. They differ deliberately in two ways: the command reads the LIVE editor buffer (unsaved edits are what a run would send), while the settings button reads the vault but previews the UNSAVED draft persona (previewing the editor you are currently writing is the only useful answer there) and offers no action picker. Privacy exclusions and a binding-rule kill switch are shown as refusals naming the tab that fixes them, because "nothing would be sent" is the most important thing a preview can say.

## Setup wizard

Six steps, modal, cancellable at any point: welcome (what the plugin does + the plain-text key disclosure) → add a backend (provider picker, key, model, **Test connection**) → which editors are on → optional voice-profile notes (with Follow links explained) → summon vs daemon with the cost stated → summary + pointers. Entry points: automatically on the first load where `onboarded` is false, the `Run setup wizard` palette command, and Behavior → Setup.

**Nothing is written until the last step.** The wizard edits a draft and applies it as one settings update, so cancelling at any step leaves the settings exactly as they were. The single exception is `onboarded`, which any exit sets — the flag means "the wizard has had its chance" (completed or skipped), so a dismissed wizard is not re-offered every launch while the command and the button keep it re-runnable. Re-runs seed their draft from current settings, so a second pass edits rather than resets; the wizard adds a backend and never edits an existing one.

A step may be left empty but not half-filled: the backend step can be skipped outright, and refuses to advance with an incomplete backend, using the same validity rule the Backends tab applies. A wizard-added backend becomes the global default when there is none (editors inherit, so otherwise nothing would use it); an existing default is never repointed. The summary states plainly when the result cannot run a review, asked of the same predicate every dispatch surface uses.

**Test connection** sends ONE small real request through the exact executor a review uses, so a pass means reviews will work rather than "the endpoint answers". Three outcomes: works, **reached but not usable** (the endpoint answered, the model ignored the required structure — a model problem, not a connection problem), and failed (credentials / network / timeout / configuration). Its timeout is 60 s rather than the Behavior tab's request timeout, and the timeout message says a slow local model may still work for real runs with a higher request timeout.

## Import & export

Behavior tab → **Import & export**. Both directions operate on one JSON document, and both are dialog-driven.

**Export** writes the sections the user ticks (backends / editors / panels / actions / rules / voice profile) to a vault-relative `.json` path or to the clipboard. The path must stay inside the vault: a `.`/`..` segment is refused rather than normalized, because the adapter would resolve it and write past both Obsidian's sandbox and the dialog's own overwrite confirmation. Unselected sections are absent from the file rather than empty. An existing file is only overwritten after an explicit confirmation. **The API key field is never exported** — every API backend leaves with an empty `apiKey`, stated on the dialog, and stripped inside `exportSettings` so no caller can forget. Two exported fields can still hold a credential and are therefore DECLARED rather than blanked (blanking would break the backend they configure): a `baseUrl` carrying userinfo or a `key=`/`token=` parameter, and a non-empty advanced `extraBodyJson`. The dialog names the backends concerned instead of calling the file safe to share.

**Import** accepts a pasted document or a vault file — including a plugin `data.json` copied from another vault, which carries no format marker. It validates element by element (one invalid entity never drops its siblings), regenerates every entity id, and remaps references onto the new ids. A reference pointing outside the import survives only when that id exists here (re-importing panels into the vault their member editors still live in), and is otherwise cleared. Nothing is written until the user confirms a summary listing what will be added, what will be adjusted, and what will be skipped with the reason (invalid entity, panel with no member editor, built-in verb already bound, section at its schema maximum). Imports ADD; the voice profile is the single value that replaces, and the summary says so. Section caps are decided BEFORE references are remapped, so an entity that does not fit is invisible to the entities that pointed at it: their reference is cleared and reported like any other reference to something outside the import, never left dangling.

**An imported backend is a destination.** API keys are never imported — even when the file carries one, so importing someone else's file cannot silently bill their account — but a stripped key protects nothing on its own: Ollama needs none, an OpenAI-compatible host takes whatever key is entered later, and an imported editor arrives enabled and review-capable, which makes it a participant in every review. So imported API backends arrive **disabled** (an adjustment says so), the confirmation lists the kind and the URL each one would send notes to plus whether it carries a custom request body, and it states how many imported editors would take part in every review. Enabling a backend means opening the Backends tab, where its URL is visible.

## Notable defaults

- No backend configured → the setup wizard, never an error dump.
- Starter pack seeded on first run (idempotent): Concision Editor, Devil's Advocate, Fact Checker, Flow & Structure Editor, Humanizer, Beginner Reader + the Pre-publish review panel + default action bindings (rephrase/summarize/simplify → Concision Editor, humanize → Humanizer, critique/identify assumptions → Devil's Advocate, find evidence → Fact Checker; continue/say more left unbound). Verbs the user already bound are never overridden.
- Exclusions default to empty; nothing is ever sent without a user action regardless.

## Key storage disclosure

API keys are stored in the plugin's `data.json` inside the vault. If the vault is synced (Obsidian Sync, Syncthing, git…), keys travel with it. This is documented in the README and the Backends tab. Keys and prompts are redacted from logs and error reports.
