# Business Rules

This document defines the core business rules. These rules MUST be respected in all implementations unless explicitly approved otherwise.

---

## Documentation Guidelines

When a new business rule is mentioned:

1. Add it to this document immediately
2. Use a concise format (single line or brief paragraph)
3. Maintain precision - do not lose important details for brevity
4. Include rationale where it adds clarity

## Product invariants (locked 2026-07-29)

1. **User-initiated only.** No AI call ever runs automatically — not on note open, not on file change. Every backend request is triggered by an explicit user action (Review, an action verb, a push-back, a comment submission, a gate run). **Carve-out (2026-07-29, daemon mode; per-note since 2026-08-06):** daemon mode is PER-NOTE runtime state — every note starts with it OFF when it opens (even if it is on for another open note), the rail toggle / `Toggle daemon mode for the current note` command enable it for the current note only, and the choice is never persisted (closing the note drops it); renaming the note (or a parent folder) is not a close — the choice follows the file. The per-note enable IS that explicit action; the `Enable automatically for every note` setting (`behavior.daemonAlwaysOn`, default off — replaces the retired global `daemonMode` flag, which maps to it at load so upgrading opted-in users keep their refreshes) flips the default so every bound note starts armed, and enabling IT is the explicit action for all notes. With daemon mode on for a note, editors re-dispatch a review automatically after the user pauses work on it, if its text actually changed since its last run (idle delay configurable, short by default; typing and cursor/selection movement restart the window, triage — panel/card use, accept/dismiss, reference adds — deliberately does NOT, even when it CHANGES the document: a triage edit is folded into a pending window without moving its deadline, and arms an unarmed note (two-tier carve-out, 2026-08-06), and only an edit arms it (issue #20); oversized notes silently skipped; never while a run is in flight). The toggle Notice and settings copy state the cost implication plainly.
2. **Suggestions, never silent mutations.** Every AI-proposed change goes through a visible diff with Accept/Reject. There is no code path that writes AI output into a note without user confirmation.
3. **Accept verifies preconditions.** A proposal may only be applied if the target text still equals the text the proposal was computed against. Stale proposals are marked and must be regenerated — never silently fuzzy-relocated.
4. **Findings must quote verbatim.** Backends return exact quotes from the submitted snapshot; anchoring resolves quotes to positions. Only exact or uniquely-contextualized matches are actionable; fuzzy matches are display-only.
5. **Desktop only.** `isDesktopOnly: true`. Mobile is out of scope.
6. **Live Preview and Source mode: equivalent semantics.** Every interaction works in both modes; rendering may differ (Live Preview hides syntax), behavior may not.
7. **Privacy exclusions are absolute.** Notes excluded by folder/tag/frontmatter flag are never sent to any backend — not as the review target, not as linked context, not via an explicit wikilink reference.
8. **Vault as configuration.** Every prompt field (persona, panel charter, voice profile) accepts direct text AND/OR ordered vault note references, resolved fresh at run time.
9. **CLI backends are a security boundary.** Spawn without shell, content over stdin, isolated working directory, allowlisted environment (no configurable additions), tools/session persistence off by default, the strongest sandbox flag each tool actually offers (`--sandbox read-only` for Codex; Claude Code has none, and the docs say so rather than implying otherwise), process-tree kill on EVERY run including a clean exit, and on cancel/unload. What the plugin cannot bound — each tool's own user configuration, which is loaded — is stated in the consent dialog rather than omitted. Two separate consents, both revocable: (a) launching the tool at all, (b) tool/research mode — stronger, off by default, and revoking it must not disable the backend. **Consent records WHICH executable it was granted for**, never a bare boolean: `data.json` syncs (rule 12), so a changed, imported or sync-merged executable path invalidates the consent and the user is asked again about the program that is actually there. `enabled` is not consent — an enabled backend without matching consent is refused by backend resolution. Imported settings never carry CLI consent or enablement.
10. **Nothing is renamed to change only casing** (repo files); Conventional Commits enforced; hooks never bypassed.
11. **Editors vs Panels are visually distinguishable** in every surface (rail, menus, cards, side panel).
12. **API keys** live in plugin `data.json` (may sync) — documented prominently; keys and prompts are redacted from logs and error reports.
13. **Durable margin comments never write into the vault, and never restore a position.** They persist to ONE sidecar in the plugin data folder (never next to a note, never in a note's frontmatter, never in `data.json`), storing quote + prefix/suffix/occurrence and no offsets; every comment is RE-ANCHORED against the live text on load through the same matcher findings use. A comment that no longer resolves is kept and shown as orphaned with its quote — never silently deleted, never guessed into a position (rules #3/#4). A vault rename moves its entry, a delete drops it (no path-keyed tombstone: a note later created at that path would inherit a stranger's comments). A store that cannot be read is preserved as a backup copy and reported, never overwritten — and neither is one another writer changed: the file syncs, so a write that finds bytes this session has not seen UNIONS the two by comment id (this session wins a shared id) and says so, rather than reverting whatever another device parked. An interrupted write is recovered from its staged temp file at load and reported, because a missing store is otherwise indistinguishable from a first run and reported as silence. Nothing is dropped without saying so: a rename merging onto a note already at the cap reports the overflow, and a session that cannot write refuses NEW comments and retries rather than accepting questions it will lose at quit. A comment persisted as in-flight loads back as `interrupted` and offers Retry — nothing is ever resumed automatically (rule #1). **Resolving** a comment closes it and KEEPS it (so the same question is not re-asked); **deleting** one removes it for good and is only ever reachable through an explicit confirmation — the rule forbids deleting a comment silently, not deleting one at all.

14. **Nothing non-functional is offered.** A command, a context-menu item, a CLI flag or a settings option is registered only when it can actually dispatch; an unavailable item is HIDDEN, never disabled and never a placeholder (`setDisabled(true)` is used nowhere). Command ids embed entity UUIDs and stay stable across renames so user hotkeys survive; dynamic commands are diffed against the settings on every mutation rather than re-registered per run. The one deliberate exception is an explanation the user asked for: the side panel's Review button renders disabled and NAMES the rule on a note a kill-switch rule emptied, because a leaf the user opened must be able to say why it is empty. Corollary for settings: a control that reads as a promise (a privacy toggle, a language override) must have a consumer — `behaviorSettingsSchema` is walked by a spec that fails on any key nothing reads.

15. **Background comment jobs yield to the foreground, and cancel cleanly.** A background comment run shares the ONE plugin-wide concurrency budget (`behavior.maxConcurrentRequests`) with reviews, transforms and threads, but never queues for it: it takes a permit only while the gate would admit synchronously (nothing queued) and the pool is one short of the cap, so a parked question can never be ordered ahead of a review the user is watching. At a cap of 1 the reserve floors at one permit rather than disabling the feature. Running background work is never preempted — the request is already paid for. Every job is individually cancellable; plugin unload cancels every in-flight job and records it as `interrupted` before the store is flushed (rule #13), and a cancelled job is `interrupted` rather than `failed` because nothing is known about why it ended.

16. **Proposals are structured edits; validation failures degrade, never silently.** (Contract v2, 2026-08-01 — issues #17/#22.) A finding's proposed change is a typed edit list (`replace` / `insert-before` / `insert-after` / `delete`), never free text applied over a span: the model's explanation (`critique`/`rationale`) has no code path into the note, and adding content never destroys the text it is added around. Accept is all-or-nothing per finding, one undoable transaction, every edit precondition-verified (rule #3 applies per edit). A proposal that fails validation is stripped and the finding shown display-only with a marker; a finding whose observation core fails validation is dropped and counted — both are REPORTED (side panel salvage line), because silently absorbing a loss and silently applying a wrong edit are the same lie in opposite directions.

17. **Re-reviewing never wipes the user's triage.** (Issue #19, 2026-08-02.) Replacing a note's run carries the previous findings into the new run — visible (dimmed) through the whole wait, still fully actionable, triage statuses and push-back threads intact — and reconciles them against what the new round reports: a repeated observation (same quote + hints + critique; proposal content excluded, contract v2 §9) keeps its finding id and its user decision; a dismissed/rejected finding also matches loosely (same editor, overlapping span), so a reworded critique cannot resurrect a judged objection; a repeat of an ACCEPTED finding is dropped as stale (the edit is already applied); an observation not repeated is dropped only when the completed round actually covered it — out of a selection-scoped round's range it is kept, and a FAILED or CANCELLED round keeps everything (the previous round's findings are the current information again). Per-editor retry re-dims carried findings instead of destroying them; the triage cursor follows the replacement run. Carried findings re-anchor against the new snapshot through the same matcher ladder (rules #3/#4 unchanged).

18. **Failures are classified, and only what is transient is ever retried automatically.** (Issue #23, 2026-08-02.) Every automatic retry is a paid request, so the policy is small and typed (`retry-policy.ts`): `network`/5xx → at most 2 retries with jittered exponential backoff; `timeout` and `invalid-output` → at most 1, immediate; `rate-limit` → at most 1, honouring the provider's `Retry-After` up to a 30 s cap (a longer ask surfaces as the error); `auth`, `quota` (credits exhausted — detected via HTTP 402 and quota-coded 429 bodies, read for classification only, never echoed — BR #12), `truncated` and `cancelled` → never. A backend with 3 consecutive final failures is unhealthy (`backend-health.ts`): automatic retries stop being spent on it, while manual summons always run — the summon IS the try-again gesture, and any success (or a passing "Test connection", or a settings change) resets it. **Daemon mode disables itself** after 3 consecutive automatic refreshes in which every editor failed, with a sticky Notice naming the last failure — an unattended loop must never keep billing a broken backend; re-enabling the toggle is the recovery gesture.

19. **History is an archive, never a participant — and it obeys every privacy rule requests do.** (Issue #21, 2026-08-02.) The History tab records clipped copies of findings, push-back exchanges and scorecards via a read-only `RunObserver` whose failures can never break a run — and (issue #43, 2026-08-06) of accepted/rejected transform outcomes at DECISION time, through the same service and record-time gate; an outcome the user never ruled on (cancelled, superseded, stale-discarded) is never recorded. An excluded note, or a note a rule disabled the plugin for, is NEVER recorded (rule #7 extends to history), and its archived entries are never SHOWN — the History tab lists nothing for a note the plugin is currently disabled on. Enforcement is record-time + display-time, deliberately NOT hydration-time (round-3 review, 2026-08-02): the recordability predicate also reflects editor availability and cold-start metadata, so filtering persisted entries at load silently destroyed durable history on transient answers. Excluding a note darkens its history; un-excluding it brings the archive back. Session history is memory-only; durable history is opt-in (`behavior.durableHistory`, default OFF because entries contain quoted note content in a plugin file that may sync), persists to `history.json` with the sidecar write discipline (staged writes, temp recovery, corrupt-store backup — last-writer-wins across devices, stated, unlike comments), is excluded from settings export, expires by policy (90 days / 100 per file / 2000 total, hard-clipped fields), and is clearable per note and entirely. Verbatim repeats (same observation identity, same content) are not recorded twice — daemon-mode re-runs must not grow the archive.

20. **No `obsidianmd/*` lint rule is ever disabled.** (2026-08-04, Sébastien.) Every rule in `eslint-plugin-obsidianmd`'s recommended config stays on, globally — no `rules: { 'obsidianmd/…': 'off' }` blocks in `eslint.config.ts`, no per-file overrides, no inline disables. A rule that fires is fixed in the code, not silenced in the config. The rationale is that the community-catalog reviewer runs **its own** ruleset against the source archive, so a local disable suppresses nothing on their side — it only hides the finding from us until submission. Where a rule genuinely conflicts with a design decision (plain-DOM UI under stub-document tests, service-layer timers), the design changes or the tests adapt; the rule does not.

21. **Disabling an editor hides its persona everywhere, immediately, purging nothing.** (2026-08-06, Sébastien.) `editor.enabled = false` removes the editor from every review surface on the toggle itself — rail chip, text decorations, side-panel section and findings, panel-scorecard member/dissent/top-fix-credit rows and skip notices (the scorecard block itself and the panel's own verdict/rationale stay — they are the panel's voice), status-bar count, open cards — and daemon refreshes resolve their editor set at FIRE time against the live settings, so a disabled editor is never re-dispatched (an all-disabled captured set dispatches nothing rather than widening to the default pool). Findings are hidden, never deleted: re-enabling restores them without a new backend request (a re-review that ran meanwhile legitimately replaced them — rule #17 carries only participating editors). A DELETED editor is the opposite contract: its findings stay visible under the name the run knew. Lens: `ui/editor-visibility.ts`.

22. **Memory distillation is user-command-only, and nothing is saved without the user reading the exact text.** (Issue #4, 2026-08-07.) The per-editor learning loop has exactly one trigger: the `Distill editor learnings` palette command (rule #1 — never a triage event, never a run end, never a timer). Its input is the session-scoped **memory journal** (in-RAM only, never persisted: events quote note content), fed from the `FindingStore` decision choke point; history is never the input (rule #19 — an archive, not a participant). Events whose note is excluded or rule-disabled are dropped AT CONSUME TIME — against the note's CURRENT path (journal paths follow vault renames; a note moved into an excluded folder takes its events with it) — and an excluded memory note refuses the whole distillation — its content would ride along as `currentMemory` (rule #7 applies to both directions). The memory note path must stay inside the vault: absolute or `..`-carrying paths are refused before any read or write. The result is saved only through the editable confirmation modal (rule #2), to the editor's configured destination: `memoryText`, or the designated memory note — the plugin's only vault-note write outside CM6 edits, allowed precisely because it is user-confirmed content into a note the user explicitly designated (distinct from rule #13's margin comments, which never write into the vault). A save first re-reads the destination and REFUSES when it changed since the proposal was distilled — the exact-review promise covers what the save replaces too; the user's meanwhile-edits are never silently overwritten. The journal is cleared per editor only after a confirmed, successful save, and only the events that distillation snapshotted — a cancelled or failed distillation keeps the session's signal, and decisions recorded while a request or its modal was pending stay journaled for the next one. The journal records only for editors whose memory is on (Off means nothing recorded, per `docs/editors.md`). `memoryText` never travels in a settings export: it is personal learned data derived from the user's own triage, not shareable configuration.

23. **A vault rename never destroys review state — only a delete does.** (Issue #47, 2026-08-12.) A rename changes a note's path, never its content, so everything anchored to content survives it: the live review run (findings, threads, in-flight attempts), the pending transform preview, the triage cursor, the severity lens, hidden-findings state, all-good acknowledgements, the daemon's per-note state including its pause, margin comments (rule #13), history and journal paths. All of it REMAPS to the new path, prefix-aware for folder renames (Obsidian emits no per-child events). State already at a target path (a stale leftover of a replaced note) is discarded rather than inherited — a moved note must never wear another note's findings. A vault DELETE is the opposite: per-note runtime state dies with the note (comments and journal drop their entries; durable history follows its own retention, rule #19).

24. **Users exist — compatibility is mandatory (the v1 "no users yet" policy retired 2026-08-12).** The v1-era standing policy that allowed free schema breaks lapsed with the public releases and the community-catalog submission (#41). Settings (`data.json`), the sidecar stores (`comments.json`, `history.json`) and command/manifest ids are compatibility surfaces: schema changes ship migrations through the existing schema-version machinery, ids stay stable (rules #13/#14), and on-disk shapes older sessions wrote must keep loading (legacy formats, not deprecated ones).
