# Architecture

High-level structure of the Editor AI Daemons plugin. See `Domain Model.md` for entities, `Business Rules.md` for invariants, and `plans/editor-ai-daemons-v1-implementation-plan.md` for the roadmap.

## Layers

```
src/app/
├── types/        # Settings interfaces, branded IDs
├── domain/       # Pure logic: operation contract (Zod), anchoring engine, snapshots
│                 # No Obsidian imports — fully unit-testable under bun test
├── services/     # Backends (API providers, CLI agents), context assembly,
│                 # run orchestration, persistence (sidecar repository)
├── commands/     # Obsidian command registrations (review, triage, actions)
├── ui/           # CM6 integration (decorations, rail, cards, diffs), side panel,
│                 # settings tab, wizard, modals
└── settings/     # Settings tab + components
```

Dependency direction: `ui`/`commands` → `services` → `domain` → `types`. The domain layer never imports from Obsidian or CM6 — editor-position mapping is abstracted behind `TextChange` (adapted from CM6 `ChangeDesc` at the ui boundary).

## Core flow (a review run)

1. User triggers Review (command/rail). The active note is snapshotted (`DocumentSnapshot`: text + hash + id).
2. Binding rules are consulted (`domain/rules/`): a kill-switch rule refuses the run with its own typed status (distinct from a privacy exclusion) and suppresses every surface for that note; an assign rule supplies the default participant pool. An explicit ask/bound action, and a daemon re-dispatch, both override the rule's pool.
3. Context is assembled per editor through the ONE prompt-build entry point, `buildEditorPrompt` (`services/review-service.ts`): system prompt (voice profile + persona prompt text + memory), then the vault notes that ride along — prompt note refs, wikilinks in the prompt text, links followed from prompt notes, and the reviewed note's own links when the editor opts in — all after privacy exclusions and under the character budget whose policy lives in `services/context/context-budget.ts`. The system prompt and the reviewed note are never truncated; attachments are spent in that order and the last ones are dropped first, with every candidate reported. Transforms, push-back threads and the "what will be sent" preview call the SAME function, so the preview cannot drift from the request.
    - A bound ACTION resolves its verb before that step (`resolveActionVerb`): built-in verbs come from the registry, a custom action supplies its own label, class and vault-resolved instruction. The class then picks the pipeline — `transform-selection`, `insert-at`, or the review pipeline with the instruction augmented onto the system prompt — identically for built-in and custom actions.
4. Each enabled editor's backend runs an `Operation` (see contract in `src/app/domain/operations/`). Backends emit `OperationEvent`s: findings (as they complete, when streaming is verified for the provider), progress, exactly one terminal event (result/error), all tagged with the run id.
5. Findings are anchored against the snapshot (exact → normalized → contextual; ambiguous/fuzzy = display-only) and projected into CM6 decorations. User edits remap positions via change-mapping; edits intersecting a finding's range mark it stale.
6. Triage: cards, diffs, threads, keyboard commands, bulk operations. Accept re-verifies the precondition text, applies as a single undoable transaction.
7. Panel runs add an aggregation operation over member results, producing a typed `PanelResult` scorecard. A run is "busy" until BOTH its editors and its aggregation settle (`RunHandle.isBusy()`; `isSettled()` is editor-only and gates the aggregation itself). The scorecard is model-authored text, so both renderers (side panel, CLI) reconcile it through `domain/panels/scorecard-model.ts` — member names against the run's roster, a top fix's credit against the finding it actually resolves to.

## Backends

Two families behind one adapter contract (per-instance capability negotiation: streaming?, JSON schema?, usage?):

- Both families are turned into something runnable by ONE factory, `services/backends/backend-executor.ts`. No dispatch surface (reviews, panel aggregation, transforms, threads, health checks, preview) branches on `family`, so supporting one family and not the other is not expressible. The factory decides the three things that legitimately differ: which executor, the timeout (a CLI backend carries its own per-backend budget instead of borrowing `requestTimeoutSeconds`), and redaction (a CLI backend holds no key of ours, so it is identity — the executor's status-only messages are what contain tool output).
- **API providers** (v1 core): Anthropic, OpenAI, OpenRouter, OpenAI-compatible (custom base URL), Azure OpenAI (deployment-based), Ollama. A backend's "Test connection" (`services/backends/health-check.ts`) accepts both families and runs one probe operation through the SAME executor a review uses, so a pass means reviews will work rather than "the endpoint answers"; a reachable endpoint whose model ignores the required structure is reported as its own outcome. Buffered structured output is the baseline; per-provider streaming decoders only where verified. Transport constraint: Obsidian's `requestUrl` does not stream; renderer `fetch` is used where CORS permits, `requestUrl` as buffered fallback.
- **CLI agents** (opt-in, desktop-only): Claude Code, Codex — headless spawns behind the security boundary defined in Business Rules #9. The boundary is `services/backends/cli/` and it is the ONE place in the plugin that starts a local process: `spawnCliProcess` re-validates the user's absolute executable path (never PATH), builds the child environment from an empty object, creates and removes the throwaway working directory itself (a caller cannot name one, so an agent's files can never land in the vault), sends note content over stdin only, caps both output streams, refuses to create a process at all for an already-aborted signal, and ends EVERY run — a clean `exit 0` included — with a verified process-tree kill (an agent that exits successfully can leave a background helper holding the note text; a run whose tree could not be killed is reported as failed rather than as a success). `createCliChild` (in `cli/node-process.ts`) is the only import of `node:child_process` in the codebase and its options type has no shell field, so `shell: false` is the only reachable state. stderr is returned as `StderrDiagnostics` whose `toString`/`toJSON` are status-only (BR #12). Per-tool adapters build argv and interpret the JSON-document / JSONL output; they get no say in how the process is created or stopped. Node access is confined to `cli/node-fs.ts` and `cli/node-process.ts`.
    - The adapters live in `cli/tools/` (one per tool, registered in `cli/tools/index.ts` exhaustively over `cliBackendSchema`'s kind vocabulary — the settings schema is the authority on which tools exist). Each is pure: `buildInvocation` returns argv + stdin + which protocol its stdout speaks, `parseEnvelope` returns the model's final message or a typed failure, `capabilities` reports what has actually been verified. Session persistence is off for both tools, so a reviewed note never leaves a verbatim copy outside the vault (BR #7, #12). Tool/research consent is per tool and stated honestly: Claude Code has a real off switch (`canGrantTools: true`), Codex does not — it cannot run without its tools, so its adapter reports `canGrantTools: false` and its argv does not vary with the backend's tool consent, which the settings UI states plainly instead of showing a toggle that would do nothing. Nothing an adapter reads out of a payload reaches a user-visible message: only a shape-checked status token and a reported HTTP status get through.
    - `cli/cli-editor-backend.ts` bridges an adapter to the `RunController`'s injected `execute`, deliberately indistinguishable from `createApiEditorExecutor`: same signature, same exactly-one-terminal-event protocol, same error vocabulary, and the SAME `extractJsonPayload` + `validateOperationResult` as the provider adapters — a result from a local pipe is not more trusted than one from HTTPS. Prompt delivery goes through `buildUserMessage` (`'json-object'` style) so both families answer to one output contract; the persona rides on stdin because every system-prompt flag is argv-bound and argv is world-readable. Model resolution is per-editor override → backend default → the tool's own default, where empty is a valid answer.
    - **Consent** (`domain/settings/cli-consent.ts`) is stored as the executable path each of the two permissions was granted for, never as a boolean: `data.json` syncs (BR #12), so an edited, imported or sync-merged path stops matching and the backend reads as not-consented. `hasToolsConsent` requires launch consent, so tool mode cannot outlive permission to start the process. `resolveBackendRef` is the enforcement point — an enabled CLI backend without matching launch consent is the typed skip `cli-consent-required`. The dialog wording lives in `settings/cli-consent-copy.ts` and is spec-pinned, because consent only means something if the user was told what they agreed to. `settings/tabs/cli-backend-modal.ts` hosts the fields, the two consent rows and Test connection (which asks for launch consent first — the test IS a launch); `cli/detect.ts` fills the path from a curated location list and never executes anything and never reads `PATH`.

## UI integration points

- CM6 `StateField` for finding decorations (mapped through transactions), single active tooltip per view for cards, view-owned panel element for the persona rail, `ItemView` workspace leaf for the side panel (a header bound to the note — name + Review button — over the findings list, scorecards and comments), status-bar item (finding count / gate verdict).
- Every surface that gates on "can a review start here" asks ONE function, `reviewGate` (`services/reviewability.ts`), which returns the reason (`excluded` / `rule-disabled` with the rule label / `no-editor` / `ok`); `isReviewable` and `isPluginEnabledForNote` are projections of it. Surfaces that must SAY WHY (the panel's Review button) read the gate itself, so an explanation cannot drift from the decision it explains.
- The panel's Review button dispatches the shared whole-note review path and REFUSES while a run or retry is in flight (same `canCancelRun` predicate the Cancel command uses) — `RunController.startRun` cancel-replaces an existing run, and destroying findings from the surface displaying them is never what a click meant. Cancelling stays on the rail and the palette.
- Multiple leaves/popouts: a file-level run controller with per-view projections; all DOM created via the owning view's document.

## Persistence

- Settings (editors, panels, actions, rules, providers): plugin `data.json`, schema-versioned with migrations, stable UUIDs, referential integrity on delete. Transfer in and out of a vault goes through `domain/settings/settings-transfer.ts` (pure): export strips API keys and declares the fields that can still hold one; import validates per entity, applies section caps BEFORE remapping (so a capped-out entity leaves no dangling reference), regenerates ids, remaps references, brings API backends in disabled, and returns a plan — destinations included — that the user confirms before anything is written.
- Findings/runs: ephemeral (in-memory per session).
- Async margin comments: ONE sidecar file, `<pluginDataDir>/comments.json` (`manifest.dir`, falling back to `Vault.configDir` — the config folder is user-configurable and is never hardcoded), keyed by vault-relative note path, schema-versioned. `domain/comments/` owns the shape, the defensive load and the re-anchoring; `services/comments/comment-repository.ts` owns the location decision, the write discipline and corruption recovery; `ui/comment-store.ts` is the `Vault.adapter` seam plus two vault hooks.
    - **Location, decided**: per-note sidecars next to the notes (or a frontmatter block) were rejected — not polluting the vault is a core promise of this plugin, a conflicted `comments.json` costs plugin state while a conflicted sidecar or frontmatter block conflicts the user's own file, and one file means one code path for rename, corruption and atomic writes. Not `data.json` either: settings hold API keys and are rewritten on every settings change.
    - **Anchoring is never restored, always resolved**: a comment persists `quote` + `prefix`/`suffix`/`occurrence` and deliberately no offsets (the note may have changed while Obsidian was closed), and is re-anchored against the live text through the same `matchQuote` engine findings use. Outcomes: `exact`, `fuzzy` (normalized match, anchored to the SOURCE slice so any precondition compares real text), `orphaned` — kept with its quote, shown as orphaned, never guessed into a position and never deleted.
    - **Rename moves, delete drops**: the repository re-keys the exact path AND any folder prefix, idempotently, so it does not depend on which event Obsidian emitted. A delete drops the entry; a path-keyed tombstone was rejected because a note later created at that path would silently inherit a deleted note's comments.
    - **Corruption**: an unreadable or partially-salvaged store is copied to a timestamped `comments.corrupt-*.json` BEFORE anything writes, the plugin loads with what could be salvaged, and the user is told. If the copy fails, the repository refuses to write for the session.
    - **Writes**: debounced, coalesced (one in flight, at most one queued behind it), staged to `comments.json.tmp` and renamed over the store, with ordered fallbacks for adapters that will not replace an existing file.
    - **Interrupted jobs**: `submitted`/`running` cannot be true in a session that has not started, so they load back as `interrupted` — Retry, never fake resumption. Plugin unload records the same thing from the other side (`CommentJobRegistry.interruptAll()` before the store is flushed), because either path can be the one that runs and they must agree.

## Background comment jobs

A parked margin comment is the only work in the plugin the user walks away from, so it gets its own orchestration shape (`services/orchestration/comment-run.ts`) — keyed by COMMENT id, not by file, bound to no view, surviving note switches by construction. It is a `review` operation scoped to the span with the question carried as the per-run instruction (`domain/comments/comment-prompt.ts`); no seventh request kind was added, so there is one prompt serializer, one result shape and one set of protocol tests.

- **Admission** (`services/orchestration/background-gate.ts`): background work shares the ONE plugin-wide budget but never queues for it. A job takes a permit only while `queuedCount() === 0` and `activeCount() < cap - 1`. The reserve keeps a slot the foreground can take immediately; the empty-queue clause is what actually prevents starvation, because `Semaphore` is FIFO and a queued background waiter would be admitted ahead of a review queued behind it. The cost falls on the background side (a busy vault can leave a comment waiting indefinitely), which is the right way round. Floors at one permit so `maxConcurrentRequests: 1` does not kill the feature. Preemption was rejected: the request is already paid for at the provider.
- **The registry** (`services/comments/comment-job-registry.ts`) is the ONE join between the durable comment and the live run, so a job can never be `running` on disk with nothing running. It follows the run's own notifications rather than its `settled` promise — `cancel()` terminates a handle synchronously while the aborted stream may still be winding down — and owns the once-a-second ticker that keeps elapsed timers honest, started and stopped with the in-flight set.
- **Dispatch** (`services/comments/comment-job-service.ts`) has the same gate order as `startReview`: exclusions fail closed, the binding-rule kill switch refuses before any dialog, then the size guard (a comment sends the whole note as context, unlike a thread turn), then one named editor resolved fresh, then context assembly, then the durable record, then the request. A rule's `assign` target does not override the comment's editor — a comment names who it asked, like a push-back does.
- **Retry** re-anchors the span against the note as it reads NOW and refuses (`orphaned`) when the quote is gone: re-asking about text that no longer exists would return an answer about something else under the original question. A retry clears the previous error and answer rather than merging with them.
- **Span hints** (`domain/comments/span-hints.ts`) are the inverse of `matchQuote` — a user-created comment derives its own `quote`/`prefix`/`suffix`/`occurrence`, with a spec-pinned round-trip guarantee that hints re-anchor to exactly the span they came from.
- **Surface**: the margin column (below) and the side panel section (`ui/comment-jobs-model.ts` is the pure projection; the `ItemView` only renders it). The status bar was rejected — it is global chrome, and a per-second timer there would animate permanently for a feature the user is deliberately not watching.

## Margin comment column

Comments are rendered beside the lines they were parked on by a positioned overlay owned by the markdown view — deliberately NOT a CM6 gutter, for the same reason the rail is not one: gutters are left-side, line-oriented strips inside the scroller, while this is a right-hand column of prose cards that must coexist with Obsidian's own gutters instead of competing for their slot. Three pure modules decide everything and the glue only measures and applies.

- **Geometry** (`ui/editor/margin-layout.ts`): where a column may exist, which comments share a line, and where each group lands. Groups push each other DOWN from their anchors and then pull back UP off the bottom edge, so a card sits as close to its span as it can without overlapping or falling out of view.
- **Card model** (`ui/editor/margin-model.ts`): what a card says and which affordance it offers. Resolved comments leave the margin (the store keeps them), orphans go into one collapsed group at the top WITH their quote, bodies truncate with an in-place expansion, and Retry is offered only where `retryCommentJob` would accept it.
- **DOM** (`ui/editor/margin-column.ts`): Obsidian-free, popout-safe, no `innerHTML`. Render, measure and position are three phases because a card's height is only knowable once rendered and its position depends on every other card's. `marginModelKey` deliberately excludes anchor positions AND the elapsed timer, so neither a scroll frame nor a running job's once-a-second tick rebuilds the column and destroys focus and expanded answers; the timer and the card's announced sentence are the only live text, and the column writes them in place.
- **Coexistence with the editor width, decided**: with **Readable line length** on (Obsidian's default) the column drops into the empty right margin and the note's layout does not move at all (`overlay`). With it off the text runs the full pane width, so the column reserves its space by padding the scroller (`reserve`) — floating cards over prose would hide the sentences they comment on. The reflow happens when the first comment appears on a note and when the last one goes, both explicit user actions; scrolling never changes it, because the column stays mounted while the note has any comment even when none is currently in view. The free-margin measurement subtracts the reserve it applied (halved under readable line length, where padding moves a centered block by `P/2`), or the placement would oscillate. Below ~700px of pane there is no column at all and the side panel is the surface.
- **Cost of asking**: re-anchoring runs `matchQuote` over the whole note once per comment, and the refresh cycle fires on every edit batch and every scroll frame — so the result is memoized against the CM document's identity (immutable, so a new object IS a changed document) and the stored comments' revisions, and group heights are re-measured only when the DOM or the column width actually changed.
- **Entry point**: `ReviewController.openCommentModal` from the editor context menu, the `Ask for comments` command and the panel button. A selection is required — a margin comment is anchored to a span, and a whole-note comment would have no line to sit next to and no quote to re-anchor against. The picker opens on `behavior.defaultCommentEditorId` (plan §4 comment routing) and falls back silently when that editor can no longer run.

## Accessibility contracts

Three rules the UI layer holds itself to, all of them checkable by reading the code rather than by running a screen reader.

- **Nothing is signalled by colour alone** (WCAG 1.4.1). Editors vs panels: `ui/entity-label.ts` — the name says `(panel)`, the ring and the glyph are additions. Findings in the document: the persona tint is joined by a per-editor bottom-edge STYLE (`editor-ai-daemons-finding-edge-<n>`, from the editor's position in settings) and a `title` naming the editor, its panel, the severity and staleness (`ui/editor/finding-identity.ts`, which also records why that name rides a `title` rather than an `aria-label` — a CM6 mark is a `<span>` in contenteditable, i.e. `role=generic`, which ARIA forbids naming). Diffs: the deletion is struck out, so the insertion is underlined. Severity in the side panel: a shaped Lucide glyph, named through `role=img`. The colour swatch: a check glyph plus `aria-pressed`.
- **Every region and every repeated control is named.** Side-panel sections are named for their editor and, when there is one, their panel (`memberSectionName`); scorecard rows are `role=group` carrying a composed sentence; margin cards and comment rows are `role=group` for the same reason; identically-labelled buttons (Retry, Cancel, Resolve, Delete, appearing once per comment) say which comment they act on (WCAG 2.4.6); a control whose visible text is already its name is never overridden by an `aria-label` (WCAG 2.5.3, `MarginColumn.applyHint`).
- **Motion is a reinforcement, never the signal** (WCAG 2.2.2 / 2.3.3). One blanket `prefers-reduced-motion` block at the foot of `styles.src.css`, scoped to the plugin's own class prefix, collapses every animation and transition — an allow-list was tried first and carried its own warning that a new animation would silently escape it. Every animated state is also legible standing still: a pulsing rail dot is dimmed, the review spinner sits beside the word "Reviewing…", the chip-click emphasis keeps its stronger tint.

## Performance contracts

Four properties the code holds, each measured by `src/app/perf/perf.bench.spec.ts` (`bun test perf.bench`) rather than asserted. Numbers are medians on a developer laptop; the suite asserts ceilings well above them, so it catches an accidental O(n²) without failing on slower hardware.

- **Resolving many quotes against one document costs one pass, not n.** `createQuoteMatcher(text)` binds a document and normalizes it at most once, lazily; `matchQuote` is that matcher used once, for genuine one-offs. Run ingestion (`AnchorBase`) and comment re-anchoring (`reanchorComments`) each build one per batch. 500 orphaned comments on a 200 000-character note: **7 231 ms → 29 ms**. This one is not a micro-optimization — that work ran on the refresh cycle, i.e. on every edit batch while the user typed.
- **One view of the vault per RUN, not per editor.** `createCachingVaultReader` (services/context) answers each read / link resolution / metadata lookup / note-type lookup once, and `startReview` wraps the injected reader with it. 8 editors × 20 linked notes: **160 → 20 note reads, 168 → 21 metadata reads**. Deliberately not a vault cache: it is built per run and thrown away with it, so an exclusion the user adds mid-session is never answered from a stale copy (Business Rules #7). Within a run the freeze is the point — every panel member is briefed on the same vault.
- **A large rewrite still gets a word-level diff.** Above `LCS_TOKEN_BUDGET` the region is split on tokens occurring exactly once on each side (patience-diff anchors, longest increasing subsequence to keep them monotone) and each gap is diffed on its own; only a region with no unique common token degrades to one del + one ins. A 30 000-character, 25 % rewrite: **2 → 1 670 changed segments**, 0.9 ms → 8 ms. A 200 000-character rewrite: 47 ms, reconstruction invariants intact.
- **The editing loop is bounded by the document, not by how many editors are enabled.** `MAX_DECORATED_FINDINGS` = 2 000 marks per note (`ui/editor/decoration-budget.ts`), keeping the first 2 000 in document order plus the triage cursor. Every finding stays in the store, in the side-panel list and actionable; the panel states how many are listed but not highlighted.

Measured and deliberately left alone: the decoration set itself (2 000 marks rebuild in ~1.2 ms, remap on a keystroke in ~0.06 ms), the margin column model (500 comments project and key in ~2.4 ms), and exact-pass anchoring (200 verbatim quotes on a 200 000-character note in ~11 ms).

Bounds on untrusted input, verified by spec rather than assumed: a backend result is capped by the operation contract (≤ 200 findings, quote ≤ 2 000 chars, critique/suggestion/reply ≤ 10 000, replacement/insertion ≤ 100 000) — a 10 000-finding or 1 MB response is refused as `invalid-output`; a CLI backend's stdout is capped at 8 MB (`services/backends/cli/capture.ts`); the link graph is depth 1, capped by `maxLinkedNotes` (≤ 20) and `FOLLOWED_LINKS_CAP` (20 per referenced note), with `contextBudgetChars` bounding what is actually sent.
