# Architecture

High-level structure of the AI Editor plugin. See `Domain Model.md` for entities, `Business Rules.md` for invariants, and `plans/ai-editor-v1-implementation-plan.md` for the vision, the locked product decisions and the risk register.

## Layers

```
src/app/
├── types/        # Settings interfaces, branded IDs
├── domain/       # Pure logic: operation contract (Zod), anchoring engine, snapshots
│                 # No Obsidian imports — fully unit-testable under bun test
├── services/     # Backends (API providers, CLI agents), context assembly,
│                 # run orchestration, persistence (sidecar repository)
├── commands/     # Obsidian command registrations (review, triage, actions)
├── ui/           # CM6 integration (decorations, rail, cards, diffs), side panel,
│                 # settings tab, wizard, modals
└── settings/     # Settings tab + components
```

Dependency direction: `ui`/`commands` → `services` → `domain` → `types`. The domain layer never imports from Obsidian or CM6 — editor-position mapping is abstracted behind `TextChange` (adapted from CM6 `ChangeDesc` at the ui boundary).

### Ambient seams (window, timers, transport)

The service layer is Obsidian-free and its specs run headless under `bun test`, where there is no `window` at all. Three tiny modules own every place that tension shows up, so nothing else in the codebase reaches for an ambient global (catalog review 2026-08-04; BR #20):

- `utils/timers.ts` — `setTimer` / `clearTimer` / `sleep`. Production schedules off `window`; headless falls back to `node:timers`, an **import** rather than a global. Deliberately does NOT prefer `activeWindow`: `obsidianmd/prefer-window-timers` wants `window` for timers specifically and reports `activeWindow` just as loudly.
- `services/backends/resolve-fetch.ts` — the one default `fetch`, and the `FetchFn` type every backend input uses instead of `typeof fetch` (which resolves through whatever ambient types happen to be installed). Prefers `activeWindow` — unlike timers, a popout must dispatch through its own context. Resolution is **lazy**: every service resolves its transport at the top of a function whose next act may be a refusal (excluded note, missing executable, withheld consent), and a path that never dispatches must not require a transport to exist.
- `obsidian-window.d.ts` — declares `createEl` / `createDiv` / `createSpan` on `Window`. Obsidian installs them as globals and separately puts `win: Window` on `Node`, but never joins the two, so `doc.win.createDiv()` — the popout-correct spelling its own lint rule demands — does not otherwise compile. The UI layer builds every element through it; the alternatives are the bare global (binds to the MAIN document) or `createElement` (rejected by the rule).

## Core flow (a review run)

1. User triggers Review (command/rail). The active note is snapshotted (`DocumentSnapshot`: text + hash + id).
2. Binding rules are consulted (`domain/rules/`): a kill-switch rule refuses the run with its own typed status (distinct from a privacy exclusion) and suppresses every surface for that note; an assign rule supplies the default participant pool. An explicit ask/bound action, and a daemon re-dispatch, both override the rule's pool.
3. Context is assembled per editor through the ONE prompt-build entry point, `buildEditorPrompt` (`services/review-service.ts`): system prompt (voice profile + persona prompt text + memory), then the vault notes that ride along — prompt note refs, wikilinks in the prompt text, links followed from prompt notes, and the reviewed note's own links when the editor opts in — all after privacy exclusions and under the character budget whose policy lives in `services/context/context-budget.ts`. The system prompt and the reviewed note are never truncated; attachments are spent in that order and the last ones are dropped first, with every candidate reported. Transforms, push-back threads and the "what will be sent" preview call the SAME function, so the preview cannot drift from the request.
    - A bound ACTION resolves its verb before that step (`resolveActionVerb`): built-in verbs come from the registry, a custom action supplies its own label, class and vault-resolved instruction. The class then picks the pipeline — `transform-selection`, `insert-at`, or the review pipeline with the instruction augmented onto the system prompt — identically for built-in and custom actions.
4. Each enabled editor's backend runs an `Operation` (see contract in `src/app/domain/operations/`). Backends emit `OperationEvent`s: findings (as they complete, when streaming is verified for the provider), progress, exactly one terminal event (result/error), all tagged with the run id.
5. Findings are anchored against the snapshot (exact → normalized → contextual; ambiguous/fuzzy = display-only) and projected into CM6 decorations. User edits remap positions via change-mapping; edits intersecting a finding's range mark it stale. Stream-vs-result duplicates collapse on a key that includes `occurrence`/`prefix`/`suffix`, not just the text — two legitimate findings on different occurrences of the same repeated string are exactly what the prompt asks for, and a text-only key silently dropped the second.
6. Triage: cards, diffs, threads, keyboard commands, bulk operations. Accept re-verifies the precondition text, applies as a single undoable transaction.
7. Panel runs add an aggregation operation over member results, producing a typed `PanelResult` scorecard. Members are ORDINARY editor streams — same anchoring, same finding store, same plugin-wide permit — so they cannot starve another note's run and their findings keep their per-member identity; they are never merged or re-attributed to the panel. The charter is the panel's shared brief in BOTH roles: `augmentPanelCharter` appends it inside `buildEditorPrompt` after the persona and before any per-run instruction (a panel that homogenized its members would be N copies of one editor), and it is also the aggregation system prompt. **Partial failure is decided**: the panel completes with the members that succeeded, a failed member is reported as failed and stays individually retryable inside the run, and it travels to the chairperson flagged so the scorecard states what it did not see; aggregation runs when at least one member succeeded, else it is `skipped`. All-or-nothing was rejected — one member timing out on a laptop model is common, and three honest reviews plus a named gap beats a refusal. The aggregation input is compacted (anchoring aids, evidence, confidence and rationale dropped — the chairperson weighs, it never anchors) and fitted **round-robin** to half the context budget so one verbose member cannot leave the last member unheard, with every omission counted; quotes are never truncated, because a top fix resolves back to its member finding BY QUOTE. A run is "busy" until BOTH its editors and its aggregation settle (`RunHandle.isBusy()`; `isSettled()` is editor-only and gates the aggregation itself). The scorecard is model-authored text, so both renderers (side panel, CLI) reconcile it through `domain/panels/scorecard-model.ts` — member names against the run's roster, a top fix's credit against the finding it actually resolves to.

## Run lifecycle beyond the first pass

A run does not end when its editors settle. Three paths re-open it, and each one is shaped by what the previous pass already produced.

- **Run replacement carries findings over** (issue #19, Business Rule #17). `RunController.startRun` on a file with an existing run cancels it, captures its findings (post-cancel, so in-flight thread turns are already settled as failed; `superseded` records stay behind) and seeds the new `ReviewRunHandle` with them — but only for editors participating in the new run. Carried findings re-anchor against the new snapshot through the normal matcher ladder (one shared `QuoteMatcher`), keep their id/status/thread, enter the per-editor `findingIds`, and render dimmed (`carryover` flag → `editor-ai-daemons-finding-carryover` / panel `is-carryover`) while staying fully actionable. Reconciliation is incremental at ingest: an arriving finding first tries a strict observation match (`observationIdentity` in `domain/operations/cross-run.ts`: quote + hints + critique, proposal excluded per contract v2 §9) against the editor's pending carryover — hit → `FindingStore.adoptCarryover` (id/status/thread kept, anchoring + proposal refreshed; an ACCEPTED match just drops the repeat) — then a loose pass for dismissed/rejected only (same editor, overlapping span via `anchorsOverlap`), so a reworded critique cannot resurrect a judged objection. At the editor's terminal edge (`resolveCarryoverAtTerminal`): `done` drops unmatched in-scope carryover (out of a selection-scoped run's range → kept, un-dimmed), `error`/`cancelled` keeps everything un-dimmed — a failed refresh no longer wipes the triage. `retryEditor` re-dims carried findings (tracked in `carryoverOrigin`) instead of removing them. The triage cursor store re-binds to the replacement run instead of evicting, since finding ids now survive replacement.

- **Retry one editor** (`RunHandle.retryEditor`) re-runs a single `error`/`cancelled` editor INSIDE the existing run. It **replaces** that editor's findings — they came from a failed or partial attempt — and leaves every other editor alone. The retried request sends the CURRENT buffer text, captured synchronously at retry time, and anchors against it: the applied-change history is therefore per EDITOR, not per run, stops at that editor's terminal state and restarts from the retry snapshot, so Business Rules #3/#4 hold across retries. A fresh per-editor run id and a per-retry `AbortController` make retry-after-cancel work (the shared run signal stays aborted) and make a still-draining stream harmless. `isSettled()` is DERIVED from live editor state, so an active retry flips the run back to in-progress on every surface, while the `settled` promise keeps first-settle semantics (that is what the CLI awaits). The concurrency permit is taken exactly like a first attempt. Retry is a UI affordance only — the CLI has none.
- **Generate more** (`RunHandle.continueEditor`) is the mirror image: findings are KEPT and appended, and only a `done` editor is continuable. Non-repetition is handled twice, because either half alone is weak — the request carries `alreadyReported` (quote + clipped critique, ABSENT rather than empty on a first pass so a backend can tell "nothing yet" from "found nothing") and whatever slips through still hits the editor's dedupe keys. **A failed or cancelled continuation does NOT mark the editor `error`** — it restores `done` and records `continuationError` separately, because a failed editor offers Retry, and Retry replaces findings: one click after a timed-out second pass would destroy the first pass's work mid-triage. The offered count is what the section shows and is deliberately NOT severity-filtered (the lens hides findings, it does not un-report them).
- **Daemon mode** (`services/daemon/daemon-scheduler.ts`, pure; `ui/daemon-controller.ts`, glue) is the Business Rule #1 carve-out. **Per-note runtime state (2026-08-06):** the controller holds a per-path override map over the `behavior.daemonAlwaysOn` default (off by default) — every note starts from the default when it opens, the rail toggle and the `Toggle daemon mode for the current note` palette command flip the CURRENT note only (`ReviewController.toggleDaemonModeFor` → `DaemonController.setEnabledFor`, Notice included), nothing is persisted, and `fileClosed` drops the choice so a reopened note starts from the default again. A vault RENAME is NOT a close (adversarial review 2026-08-06): the views follow the file, so `filesRenamedUnder` REMAPS every per-note daemon state — override, pending arm, once-per-file oversized log marker, real timer — to the new path (deleting the override silently flipped an explicitly disabled note back to the always-on default, and an enabled one back off); the `paused` marker alone is dropped, because the rename hook also drops `hiddenFindings` (the run is cancelled) and a remapped pause would have no findings-shown gesture left to lift it. Only a vault DELETE goes through `filesClosedUnder`. The scheduler stays global-flagged ("could ANY note refresh?"); per-note gating happens at the controller's entry points (`recordEdit`/`recordEditorActivity`/`syncRunState`/fire), so a disabled note's events never reach it, and turning a note off drops its arm and timer (per-note cost kill-switch). Flipping `daemonAlwaysOn` clears every per-note session choice — the setting is the authoritative cost decision. The retired persisted global `daemonMode` flag maps to `daemonAlwaysOn` at load (`normalizeLegacyDaemonMode`, pre-parse like the starter flag): a user who had the global mode ON keeps automatic refreshes via always-on. One `window.setTimeout` per file PATH — splits and popouts share a schedule — armed from the existing canonical-view update listener, so there is no second CM6 listener. Two distinct signals (issue #20), and two activity TIERS (2026-08-06): only an EDIT arms a refresh (the changed-hash gate). EDITOR-tier activity postpones a pending refresh — cursor/selection movement (same CM6 listener, `selectionSet`) and the ask/comment/preview modals, via `noteDaemonEditorActivity` → `DaemonScheduler.recordEditorActivity`. TRIAGE-tier activity deliberately does NOT postpone — accept/dismiss single + bulk, `revealFinding`, severity cycling, acknowledgements, push-back, reference adds, regeneration, panel scrolling via the binding's `noteActivity` — all funnel through `noteDaemonTriageActivity` → `DaemonScheduler.recordTriageActivity` (a spec-pinned no-op): triaging findings is working WITH the review, and postponing for it delayed the re-review by the whole triage session. Triage actions that CHANGE the document — accepting a proposal (card, command, bulk), adding references — reach the canonical view's update listener like any edit, so their dispatches carry `triageEditAnnotation` (`ui/editor/triage-edit.ts`) and route to `DaemonScheduler.recordTriageEdit`: an armed window keeps its deadline (accepting at the end of a quiet window must not postpone the refresh by the full delay), an UNARMED note arms like an edit (the accepted text is new text), and a mid-run triage edit coalesces into the settle re-arm. One unannotated doc change in the batch keeps keystroke semantics (`isTriageOnlyEdit`); undo of a triage edit carries no annotation and reads as an edit; transform accepts are deliberately NOT triage — they are authoring. The window therefore measures "has the user paused EDITING?" — a refresh may land mid-triage, which the in-flight UI already handles — and activity of either tier can never trigger a review of unchanged text. Hiding a note's findings (issue #29, per-note session-only view state in `ReviewController.hiddenFindings`) pauses the scheduler for that path (`pause`/`resume`): nothing is due and a stray fire skips WITHOUT consuming the arm, while edits keep arming silently — so un-hiding re-derives the window from resume time and the changed-hash gate decides whether a refresh actually fires. Revealing a finding or summoning a review un-hides first. It re-dispatches only when the note actually changed since its last run (content hash, so undo-back-to-the-same-text does not fire), never while a run or retry is unsettled (re-armed at settle), through the SAME `startReview` pipeline, which means exclusions, kill switches, the size guard and the concurrency budget all apply. Every refusal is silent — an oversized note is skipped with one log line rather than a modal, because a dialog the user did not ask for on a timer is worse than no review. The re-dispatch reuses the note's current run's editor set (all enabled review-capable editors if it was never reviewed). An `abortWhen` guard is checked synchronously right before `startRun` and aborts on a run already in flight, on disposal, and on the note's daemon having been switched off mid-await (per-note state consulted live), so a dispatch that was assembling context can never bill a backend after the cost kill-switch was flipped, and never cancels a user's summon. **Summon, cancel and retry always win.**

## History (issue #21)

The archive behind #19's live view: `domain/history/history-entry.ts` (clipped entry model + retention policy, pure), `services/history/history-service.ts` (session store; privacy gate consulted per record; verbatim-repeat skip keyed on #19's `observationIdentity`), `services/history/history-repository.ts` (opt-in durable sidecar `history.json` — the comment store's write discipline in simplified form: debounced single-flight staged writes, temp recovery, corrupt-store backup; deliberately NO cross-device merge, last-writer-wins, because history is advisory), `services/history/history-recorder.ts` (maps `RunObserver` outcomes to records). The `RunObserver` seam on `RunController` fires on editor `done` (fresh findings only — continuations report additions), on landed thread turns, and on produced scorecards; every call is try/caught — an archive must never break a run (Business Rule #19). UI: a Review | History tab bar in the side panel (`history-tab.ts` holds the pure grouping/filter model). Transforms are recorded at DECISION time (issue #43, deferred from #21): accepting or rejecting a transform/generate preview archives the outcome through the same service and record-time gate — `transformHistoryRecord` (pure, in `history-recorder.ts`) maps the targeted span to the quote, the proposed text to one `replace`/`insert` edit, verb label + rationale to the text, and the verdict (`accepted`/`rejected`) to the label. An outcome the user never ruled on (cancelled, superseded, discarded as stale) is not recorded — the decision is the archive-worthy event, and a decided run is discarded on the spot, so no observation identity is needed. Margin comments are already durable in their own store.

## Memory distillation (issue #4)

The write half of per-editor learning memory. Capture: `FindingStore` takes an optional `onDecided` constructor callback — the store is the one choke point every triage surface (card, keyboard, bulk, panel) transitions through, so accept / reject / dismiss / actually-dismissing concede / held push-back turns (the editor kept its position — non-terminal, a later accept/reject reports again, but a push-back-only session must still reach the journal) report structurally; `ReviewRunHandle` forwards them as the optional `RunObserver.findingDecided` event, and `plugin.ts` composes the history recorder and a `MemoryJournal` adapter into the one observer object (`services/memory/memory-journal.ts` — session-RAM only, clipped, 200-event FIFO ring per editor, seq-stamped for identity-based clearing, event paths remapped on vault rename via `remapPathUnder` so consume-time exclusion checks see CURRENT paths, BR #22). The adapter records only for editors whose memory is ON — `docs/editors.md` promises Off means "nothing recorded", so decisions for opted-out editors never accumulate note quotes in RAM. Distillation: the `Distill editor learnings` command (`commands/memory-commands.ts`, gated by the pure `distillableEditorIds`; `FuzzySuggestModal` picker when several editors qualify) calls `services/memory/memory-distiller.ts` — an Obsidian-free service in the `thread-service.ts` mold: typed refusals reusing the `EditorSkip` vocabulary, the editor's own backend via `resolveEditorBackend`, one `distill-memory` operation through `createBackendExecutor` (both families for free; real timeout; auto-retry applies — invalid-output gets its 1 retry, and the >50k memory ceiling is a hard contract reject), acquiring `RunController.requestGate` directly as foreground work (BR #15). Exclusions are enforced at consume time: excluded/rule-disabled notes' events are dropped, and an excluded memory NOTE refuses the run because its body rides along as `currentMemory` (BR #7). An ABSENT memory note (the create-on-save flow) is checked with empty metadata — it factually has no tags/frontmatter, so folder exclusions still apply to the would-be path while the fail-closed null-metadata branch stays reserved for cold caches on EXISTING notes (otherwise the default `respectFrontmatterOptOut` made the first distillation unreachable). **System prompt is deliberately the distiller preamble + the editor's direct persona text only** — not `buildEditorPrompt` (note-centric: needs a review target, attaches context notes this operation has none of) and not the voice profile (irrelevant to "what did the author accept", and it costs tokens); the persona text is what makes the rewritten rules address the right "you". Save: `ui/memory-review-modal.ts` (BR #2 — editable textarea, previous memory collapsed alongside) routes to a narrow `saveEditorMemory` seam injected from `plugin.ts` (the `setDaemonAlwaysOn` precedent) for settings mode, or to a `Vault.process`/`Vault.create` write of the designated note through the pure `replaceMemoryBody` (`services/memory/memory-note.ts` — frontmatter preserved even when the closing fence lacks a trailing newline, body replaced wholesale; replacement IS the rotation mechanism). The user-typed note path goes through ONE normalizer, `normalizeMemoryNotePath` (trim, fold `\` to `/`, append `.md` when missing; REFUSES absolute paths and `.`/`..`/empty segments by returning `''` — the `normalizeExportPath` precedent, so no traversal input ever reaches a vault read or `createFolder`/`create`; the distiller names the refusal `invalid-memory-note-path`), shared by the distiller's gate/read, the note write and `context-assembler`'s prompt-ref attach — so the read and write sides can never disagree about which note holds the memory. Both current-memory derivations (`clipMemory`, `deriveNoteMemory`) are shared too: the save path re-reads the destination through the SAME functions and refuses the save when it no longer matches `previousMemory` (the proposal's base) — a Notice surfaces the conflict, the modal stays open, and edits made while the request or modal was pending are never silently overwritten. Guards around the flow: the command hides an editor whose distillation is in flight (request running or modal pending — a second invoke would double the paid request and stack overwriting modals), and the modal releases that guard only AFTER an in-flight save settles (`notifyAfterSettled` — Escape/Cancel during a slow write must not let a second distillation launch over a still-populated journal); the modal rejects an amended memory past `MEMORY_TEXT_MAX` with a Notice naming the limit (the settings-schema rejection it prevents is opaque); abort wiring is one session-long `plugin.register` over a set of active controllers, not one registration per invocation (Obsidian has no unregister). The journal clears per editor only after that save succeeds — and only up to the snapshot's seq high-water mark (`snapshotSeq`, identity not count: a full ring evicting a snapshotted event under a mid-flight decision must not let the clear eat that decision), so decisions recorded mid-flight survive for the next run.

## Backends

Two families behind one adapter contract (per-instance capability negotiation: streaming?, JSON schema?, usage?):

- Both families are turned into something runnable by ONE factory, `services/backends/backend-executor.ts`. No dispatch surface (reviews, panel aggregation, transforms, threads, health checks, preview) branches on `family`, so supporting one family and not the other is not expressible. The factory decides the three things that legitimately differ: which executor, the timeout (a CLI backend carries its own per-backend budget instead of borrowing `requestTimeoutSeconds`), and redaction (a CLI backend holds no key of ours, so it is identity — the executor's status-only messages are what contain tool output).
- **Payload recovery and truncation classification** (issue #18): `extractJsonPayload` tolerates a model wrapping its JSON in prose or any code fence — it recovers the first balanced `{…}` that parses (string/escape-aware scan) and strict Zod validation still runs on the recovery, so an object the model clearly meant to send is never thrown away over its envelope. A payload that ends INSIDE an unfinished object, or any parse failure while the provider reported a length-type finish reason (`finish_reason: 'length'` / `stop_reason: 'max_tokens'` / `done_reason: 'length'`, read per adapter and preserved through the streaming accumulators' reassembled envelopes), is the typed error `truncated` with an actionable message ("try a shorter selection…") — never a bare "not valid JSON". Unrecoverable failures log a diagnostic (payload length, first/last 100 chars, unclosed-object flag) behind the log util. `quota` is the other new error code: credits/billing exhausted, distinct from `rate-limit` because one clears with time and the other needs the user to pay (issue #23).
- **Automatic retry + circuit breaker** (issue #23, Business Rule #18): `withAutoRetry` wraps BOTH families at the `createBackendExecutor` seam (the health probe opts out via `autoRetry: false` — a check reports one attempt). The policy is pure (`retry-policy.ts`): bounded retries for `network` (backoff + jitter), one immediate retry for `timeout`/`invalid-output`, one `Retry-After`-honouring retry for `rate-limit` (capped 30 s — the wait holds the concurrency permit), never for `auth`/`quota`/`truncated`/`cancelled`. Only the FINAL outcome reaches the orchestrator (exactly-one-terminal-event preserved; the message counts attempts). `backend-health.ts` tracks per-backend consecutive final failures (shared instance; `cancelled` never counts): at 3 the automatic retry budget stops being spent; manual summons always run, and any success / passing Test connection / settings change resets. HTTP classification reads 402 and quota-coded 429 bodies for the `quota` code (classification only — nothing from a body reaches a message, BR #12) and parses `Retry-After` onto the error event. The daemon's own stop is `daemon-failure-tracker.ts` (pure): 3 consecutive automatic refreshes with every editor failed → the port turns the daemon off EVERYWHERE (every per-note session enable dropped; `daemonAlwaysOn` persisted off when it was on) with a sticky Notice naming the last failure; all-cancelled refreshes neither count nor reset, and re-enabling (per note or via the setting) resets the streak. `DaemonController.disableAllNotes` additionally latches an in-memory `suspended` flag (consulted by `isEnabledFor`, so timers, fresh edits, queued fires and the dispatch's `abortWhen` all read disabled synchronously): with `daemonAlwaysOn` ON the default would otherwise read enabled again during — or forever after, if the settings write fails — the async persist, and the broken backend would keep billing. The latch is lifted by the explicit try-again gestures only: a per-note enable or the `daemonAlwaysOn` flip observed in `settingsChanged`.
- **API providers** (v1 core): Anthropic, OpenAI, OpenRouter, OpenAI-compatible (custom base URL), Azure OpenAI (deployment-based), Ollama. A backend's "Test connection" (`services/backends/health-check.ts`) accepts both families and runs one probe operation through the SAME executor a review uses, so a pass means reviews will work rather than "the endpoint answers"; a reachable endpoint whose model ignores the required structure is reported as its own outcome. Buffered structured output is the baseline; per-provider streaming decoders only where verified. Findings arrive when an editor FINISHES — incremental extraction from a partial stream is explicitly out of scope, and the streaming path emits `progress` only. Transport constraint: Obsidian's `requestUrl` does not stream; renderer `fetch` is used where CORS permits, `requestUrl` as buffered fallback.
    - **Reasoning/thinking is per BACKEND, with no global default** (`thinking`, `thinkingBudgetTokens`, `reasoningEffort`, and an advanced `extraBodyJson` for openai-compatible). Default `off` everywhere: silent minutes-long reasoning reads as a hang. Anthropic `on` sends **adaptive** thinking (`{type:'adaptive'}`) and keeps forced tool use — manual `budget_tokens` is deprecated on Claude 4.6 and HTTP-400-rejected on 4.7+, and adaptive is the mode that supports a forced tool. The legacy manual mode survives as a third value `budget` for Claude ≤4.5, with the budget clamped strictly below `max_tokens` (the sum otherwise fails validation at the API). OpenAI/Azure pass `reasoning_effort` (`default` sends nothing); OpenRouter takes it as its unified `reasoning: { effort }`; openai-compatible merges `extraBodyJson`, extras winning. Streaming accumulators count `thinking_delta` and the openai-compatible `delta.reasoning_content` / `delta.reasoning` conventions as PROGRESS and drop thinking blocks at finalize, so a thinking model does not read as a hang.
    - **OpenRouter is its own kind** even though it is OpenAI-compatible underneath: a preset base URL, the recommended attribution headers and the unified reasoning field are worth more than one fewer adapter branch, because the alternative is every user re-deriving the same three settings.
    - The whole-operation timeout is the user's `behavior.requestTimeoutSeconds` (30-3600, default 600 — laptop-realistic for local models), and the timeout message names that setting. Health checks deliberately do NOT use it (see `Configuration.md` § Setup wizard).
- **CLI agents** (opt-in, desktop-only): Claude Code, Codex — headless spawns behind the security boundary defined in Business Rules #9. The boundary is `services/backends/cli/` and it is the ONE place in the plugin that starts a local process: `spawnCliProcess` re-validates the user's absolute executable path (never PATH), builds the child environment from an empty object, creates and removes the throwaway working directory itself (a caller cannot name one, so an agent's files can never land in the vault), sends note content over stdin only, caps both output streams, refuses to create a process at all for an already-aborted signal, and ends EVERY run — a clean `exit 0` included — with a verified process-tree kill (an agent that exits successfully can leave a background helper holding the note text; a run whose tree could not be killed is reported as failed rather than as a success). `createCliChild` (in `cli/node-process.ts`) is the only import of `node:child_process` in the codebase and its options type has no shell field, so `shell: false` is the only reachable state. stderr is returned as `StderrDiagnostics` whose `toString`/`toJSON` are status-only (BR #12). The captured streams additionally ride failure events as `error.diagnostics` (issue #39): the `summary` is status-only and safe anywhere, while the content sits behind an explicit `reveal()` that the UI renders ONLY on a deliberate user gesture — the "Show details" modal, caveat attached — never in a Notice, message, or anything serialized. This is the designed exception to status-only messaging, not a breach of BR #12: the rule redacts what is shown or logged unprompted, and a user reading their own tool's output on their own machine after an explicit click is the Terminal experience, gated. Issue #42 extends the same seam to the three surfaces that used to collapse to string-only errors: **panel aggregation** (`PanelRunState.errorDiagnostics`, cleared whenever `reopenPanel` re-opens the step → the scorecard's failed status renders Show details), **transform runs** (`TransformRunHandle` keeps `error.diagnostics`; the one-shot failure Notice carries the Show details button and stays up until dismissed — the content itself still renders only in the modal), and **margin comments** (`CommentRunHandle` keeps `error.diagnostics`; `CommentJobRegistry.diagnosticsFor` holds the capture session-side keyed by comment id — never persisted, `reveal()` is a closure that cannot survive a restart — cleared on retry/resolve/delete/note-delete, and surfaced as Show details on the side-panel comment row and the margin card). Per-tool adapters build argv and interpret the JSON-document / JSONL output; they get no say in how the process is created or stopped. Node access is confined to `cli/node-fs.ts` and `cli/node-process.ts`.
    - The adapters live in `cli/tools/` (one per tool, registered in `cli/tools/index.ts` exhaustively over `cliBackendSchema`'s kind vocabulary — the settings schema is the authority on which tools exist). Each is pure: `buildInvocation` returns argv + stdin + which protocol its stdout speaks, `parseEnvelope` returns the model's final message or a typed failure, `capabilities` reports what has actually been verified. Session persistence is off for both tools, so a reviewed note never leaves a verbatim copy outside the vault (BR #7, #12). Tool/research consent is per tool and stated honestly: Claude Code has a real off switch (`canGrantTools: true`), Codex does not — it cannot run without its tools, so its adapter reports `canGrantTools: false` and its argv does not vary with the backend's tool consent, which the settings UI states plainly instead of showing a toggle that would do nothing. Nothing an adapter reads out of a payload reaches a user-visible message: only a shape-checked status token and a reported HTTP status get through.
    - **The invocation contracts were read off the binaries and exercised end to end**, success and failure paths, with the exact argv the code emits — no flag is inferred, so a future version that drops one fails loudly with the unknown option named on stderr. Claude Code: `--print --output-format json --no-session-persistence --strict-mcp-config --permission-mode manual [--model M] [--tools '']`. Codex: `exec --json --color never --skip-git-repo-check --ephemeral --sandbox read-only [--model M] -`. `--dangerously-*`, `workspace-write`, `danger-full-access`, `--add-dir`, `-C/--cd`, `--mcp-config` and `--settings` are emitted by no code path, in either consent state. Envelope parsing is defensive about what was OBSERVED rather than what is documented: Claude Code sets `subtype: "success"` and exits 0 on a failed run, so `is_error` is the authoritative flag; Codex emits non-terminal `error` items (a model-metadata warning on a run that then succeeds) and top-level `{"type":"error"}` reconnection lines, and `turn.failed` outranks anything that preceded it — it too exits 0. Neither tool exposes a usable forced-schema mechanism (`--json-schema` / `--output-schema` need argv space the 4096-char cap denies, or a file the run may not own), which is why prompt delivery reuses the API path's `'json-object'` style.
    - **Open item — `--setting-sources`.** Two sentences the docs used to carry ("no inherited MCP servers or plugins") were false for both tools: Codex reads `~/.codex/config.toml`, where `[mcp_servers.*]` lives, and Claude Code loads plugins, hooks, skills, `CLAUDE.md` and the user's own `permissions.allow`. The docs now state what the plugin does NOT bound instead. `--setting-sources` would plausibly make those sentences true again and the binary accepts an empty list, but what it actually drops could not be demonstrated from outside (the help text is silent on plugins and hooks, and prompt caching confounds a token-count comparison), so it was deliberately NOT shipped: a flag adopted as a security control on the strength of its name is exactly how the false guarantee got written. It needs an experiment before it becomes a claim.
    - One deliberate deviation from the fail-loudly rule, documented at the seam: a stdout overflow FAILS the run (a truncated JSON document is corrupt, not smaller) while a stderr overflow truncates and flags it — memory is bounded either way, and a chatty tool should not lose its result over its own logging.
    - `cli/cli-editor-backend.ts` bridges an adapter to the `RunController`'s injected `execute`, deliberately indistinguishable from `createApiEditorExecutor`: same signature, same exactly-one-terminal-event protocol, same error vocabulary, and the SAME `extractJsonPayload` + `validateOperationResult` as the provider adapters — a result from a local pipe is not more trusted than one from HTTPS. Prompt delivery goes through `buildUserMessage` (`'json-object'` style) so both families answer to one output contract; the persona rides on stdin because every system-prompt flag is argv-bound and argv is world-readable. Model resolution is per-editor override → backend default → the tool's own default, where empty is a valid answer.
    - **Consent** (`domain/settings/cli-consent.ts`) is stored as the executable path each of the two permissions was granted for, never as a boolean: `data.json` syncs (BR #12), so an edited, imported or sync-merged path stops matching and the backend reads as not-consented. `hasToolsConsent` requires launch consent, so tool mode cannot outlive permission to start the process. `resolveBackendRef` is the enforcement point — an enabled CLI backend without matching launch consent is the typed skip `cli-consent-required`. The dialog wording lives in `settings/cli-consent-copy.ts` and is spec-pinned, because consent only means something if the user was told what they agreed to. `settings/tabs/cli-backend-modal.ts` hosts the fields, the two consent rows and Test connection (which asks for launch consent first — the test IS a launch); `cli/detect.ts` fills the path from a curated location list and never executes anything and never reads `PATH`.

## UI integration points

- CM6 `StateField` for finding decorations (mapped through transactions), single active tooltip per view for cards, view-owned panel element for the persona rail, `ItemView` workspace leaf for the side panel (a header bound to the note — name + Review button — over the findings list, scorecards and comments), status-bar item (finding count / gate verdict).
- Every surface that gates on "can a review start here" asks ONE function, `reviewGate` (`services/reviewability.ts`), which returns the reason (`excluded` / `rule-disabled` with the rule label / `no-editor` / `ok`); `isReviewable` and `isPluginEnabledForNote` are projections of it. Surfaces that must SAY WHY (the panel's Review button) read the gate itself, so an explanation cannot drift from the decision it explains.
- The panel's Review button dispatches the shared whole-note review path and REFUSES while a run or retry is in flight (same `canCancelRun` predicate the Cancel command uses) — `RunController.startRun` cancel-replaces an existing run, and silently abandoning a run mid-request (paid for, findings still streaming) is never what a click meant. Cancelling stays on the rail and the palette.
- Multiple leaves/popouts: a file-level run controller with per-view projections; all DOM created via the owning view's document.
- **One canonical view per file forwards edits.** Anchor remapping is not keyed on which view has focus: exactly one view per path forwards every doc-changing transaction to the domain (`applyTextChanges`), so a search-replace-all, a programmatic edit, an undo from the menu and an Accept applied from another pane all remap anchors exactly once. Accept's own edit flows through the same path rather than mutating the store directly; card-originated transactions are recognized by their effect and skipped by the listener to avoid a double-apply. A finding whose span an edit intersects goes **stale** on the spot — the refresh path diffs the store's stale set before and after each forwarded batch and dispatches `markStaleEffect` for exactly the findings that transitioned (on a microtask; CM6 forbids dispatching inside an update listener), with the full decoration rebuild left as the eventual-consistency backstop.
- **The kill switch hides, but a surface the user opened explains itself.** A rule-disabled note gets no rail, no menu items, no commands and no dispatch — except that the side panel's Review button renders DISABLED and names the rule. The panel is a leaf the user deliberately opened, a disabled button dispatches nothing, and refusing to explain an emptied panel is not what the kill switch promises. An existing run stays BOUND while hidden so its anchors keep remapping and removing the rule restores a coherent run.

### Triage surfaces

Triage is a keyboard-first flow over one per-file cursor, with the same stepping engine behind every entry point.

- **One stepping engine.** `triageStep` (memory-based next/prev with wrap, falling back to position-based eviction when the remembered finding is gone) serves the `next-finding`/`prev-finding` commands, the rail chip cycle and the auto-advance after accept/dismiss — the auto-advance IS the eviction fallback, which is why it needs no rules of its own. The per-file `TriageCursorStore` is validated by run token (a replaced run evicts on first contact) and cleared on Escape, rename, delete and dispose; the cursor is rebased onto LIVE anchors, never a stored offset.
- **The current finding is ringed by the decoration spec**, not by a one-shot effect, so the ring survives a decoration rebuild; a finding going stale drops it. Stepping reveals through the side-panel reveal path and opens the finding card at the target (card-on-jump).
- **Escape precedence**: an open card consumes Escape (the card closes, the cursor survives); with no card open, a non-consuming highest-precedence keydown observer clears the file's cursor, i.e. leaves triage.
- **Chip click, decided as a matrix** (`chipClickAction`): a chip with revealable findings reveals the FIRST one and CYCLES on subsequent clicks (anchor order, wrap-around) while briefly emphasizing that editor's live marks (~2 s, never stale marks, reduced-motion aware, auto-cleared); a chip with no revealable findings but a summary or an error opens the side panel scrolled to that editor's section; a chip on a running editor is a no-op, because the row already says so.
- **Bulk accept plans against the live text.** `planBulkAccept` picks every acceptable finding in document order whose FULL edit plan still verifies (contract v2: a proposal is a set of edits, applied all-or-nothing per finding), and when two findings' change sets overlap it keeps the EARLIER one and skips the later WHOLE — composing two rewrites of one span produces nonsense. Adjacent changes do not conflict; two zero-width insertions at one position do (their order would be arbitrary). Every applied change is dispatched as ONE history-isolated transaction, so a single undo restores the batch, and one Notice reports applied plus both skip kinds. `isBulkAcceptable` and `FindingStore.isActionable` are pinned equivalent by spec, so the panel's count and the planner advertise one set; both delegate to `domain/operations/edit-apply.ts`, the single implementation of op semantics (replace / insert-before / insert-after / delete), the conflict rule and the all-or-nothing plan.
- **Dismiss-all is run-scoped as well as per-editor.** `ReviewController.dismissAllFindings(editorId | null)` — `null` = every editor of the run — backs three surfaces on one sweep: the dynamic per-editor commands (`bulk-commands.ts`), the static global `dismiss-all-findings` palette command (registered once by `registerGlobalDismissCommand`, hidden when nothing is dismissable), and the side panel's run-level `Dismiss all findings (n)` row (`globalDismissView` in `bulk-triage.ts` — hidden when a single editor's own row would be the identical control). All obey the severity lens via `bulkCandidates`; dismissing changes no text, so the sweep is one store pass + one decoration dispatch with one Notice — nothing to undo.
- **Undo isolation is explicit everywhere an edit is applied.** Accepts (card, command, bulk) and transform applies carry `isolateHistory.of('full')`: without it CM6 merges the applied edit with adjacent typing in both directions, and one Ctrl+Z reverts the user's keystrokes along with the accept.
- **A failed accept degrades to a Regenerate affordance, never a dead button** (2026-08-06). `FindingStore.accept` folds the two live-text failures (`stale` anchor, `precondition-failed`) into ONE reason, `stale-proposal`; the status stays `open` (BR #16/#17 — degrade visibly, never silently drop). The card's staleness is derived TWO ways in `getCardData`: from the LIVE edit plan (`planEditChanges` against the live buffer failing with `stale`/`precondition-failed` — the common case, where editing inside the span disables Accept before it could ever be clicked) OR from a runtime-only `staleProposalIds` marker set when an `accept` call itself returns `stale-proposal` (precondition drift without remap, e.g. external sync); either way the card renders a "Stale proposal" badge plus a **Regenerate** button instead of a disabled Accept (`acceptControl` in `finding-card.ts`, spec-pinned). Regenerate clears the marker and re-dispatches the note's review through the regular `startReview` pipeline with the run's OWN editor set + panel identity (a single-editor run would kill the other editors' findings — issue #19 carries only participating editors), refusing with a Notice when the finding's editor is `enabled: false` or the note is not open. Carryover findings show the badge only ("Stale (from previous review)") — no Regenerate. The marker self-heals: it is dropped when the full edit plan verifies again against the live text (undo restored it, or carryover adoption re-anchored it) and when the finding disappears.
- **The severity filter is a per-file VIEW lens** (all → warnings and suggestions → warnings only). It governs decorations, the side-panel list, triage stepping, chip cycling and bulk operations — accepting or stepping onto an invisible finding would be a surprise. It deliberately does NOT govern run-report surfaces: rail counts and section statuses keep reporting what the editors found, and a section whose findings are all hidden says so. `visibleFindings` is the single application point.
- **Disabling an editor hides its persona everywhere; nothing is purged** (`ui/editor-visibility.ts`, 2026-08-06). `editor.enabled = false` removes the rail chip (`railEligibleEditors`), the text decorations, panel section, status-bar count and any open card (all through the `disabledEditorIds`/`withoutDisabledEditors`/`panelSectionPlan` lenses — `visibleFindings` applies it before the severity filter), and the panel SCORECARD applies the same lens by NAME (`buildScorecardView` takes the disabled member names, translated from ids through the run's roster): a disabled member's row, dissent positions (entries emptied by the filter are dropped) and top-fix credit disappear while the panel-level verdict/rationale/actions stay, and skip notices for a disabled editor are hidden too (`withoutDisabledEditors` over `binding.skips`), and the daemon resolves its editor set at FIRE time against the live settings, so a disabled editor is never re-dispatched (`daemon-controller.ts` filters the captured set; `resolveReviewParticipants` pool 3 drops disabled editors silently as backstop; an all-disabled set stays `[]`, never `null` — `null` would widen to the default pool). The findings stay in the run's store untouched: re-enabling brings them back without a paid re-review (unless a refresh replaced the run meanwhile — carryover keeps only participating editors, issue #19). A DELETED editor is the opposite contract and keeps its findings visible. The settings observer (`plugin.ts`) calls `requestRefresh()` explicitly so all of this happens on the toggle itself, not on the next interaction.

### Transform preview

A transform or generation never writes into the note on its own (Business Rule #2). The result is ONE CM6 block widget below the line containing the span end or the insertion anchor — a line-start anchor goes after the PREVIOUS line, so a whole-line selection is not covered by its own preview — with the source text left visible and identical behaviour in Live Preview and Source mode. The widget shows a persona-coloured header, the word-level diff (`domain/diff/word-diff.ts`; a generation renders as one insertion block), the rationale, and Accept/Reject; its keys are widget-scoped (Enter accepts, Escape rejects only while focus is inside), never global hotkeys.

The apply precondition is exact text equality against what was dispatched — the selected span at its ORIGINAL offsets for a replacement (so edits strictly after it stay valid), the whole document for an insertion — re-verified in the same synchronous block as the apply, and never fuzzy-relocated (Business Rules #3/#4). An edit that changes the target auto-dismisses the preview with one Notice and discards the run. A note-switch is not a text change: a refresh in the window where Obsidian has assigned `view.file` but has not yet replaced the CM document must not discard a valid transform, so the stale path is non-destructive when the glue has just rebound.

### The persona rail

A card of NAMED rows mounted in the view's `contentEl` (not a CM6 gutter — gutters are left-side, line-oriented strips inside the scroller and would compete with Obsidian's own), showing one row per participating editor, panels owning their members, plus the daemon toggle and the Review/Cancel button.

- **Names, never tooltips.** The persona name is visible text; `narrow` means denser, not icon-only. The model bounds the name in code points as a runaway guard and CSS ellipsis does the everyday shortening, so the accessible name can be built from the VISIBLE text with the full one on the tooltip (WCAG 2.5.3 — a name that omits the `…` the DOM shows is a false claim). The rail is capped as a share of the HOST pane and its row list scrolls.
- **Two nested elements per row**: the outer ring is STATUS (idle/pending/busy/done/error/muted) and the inner core is IDENTITY (filled = editor, hollow = panel), which keeps Business Rule #11 true now that every editor has a ring. The three terminal rings differ by thickness and border style rather than hue, because the persona colour is user-configurable and a red persona would otherwise collapse `done` into `error`.
- **The rail RECONCILES, it does not rebuild.** `render()` is called on every coalesced refresh, i.e. per streamed finding. Replacing the children each time destroyed three things at once: the element holding keyboard focus, the infinite busy-ring sweep (recreated before it could complete a turn), and every one-shot motion cue. The head, the list, the live region and one row per editor id now outlive every render; nodes are only created, removed or moved when the row SET changes, and that path saves the focused control by key and refocuses it with `preventScroll`. Ring classes are re-applied only on a real status change.
- **Motion is diffed, not declared.** `railMotion(previous, viewModel)` compares one render against the last and emits one-shot cues (stagger a new run, bump a changed count, flash a settling row); stylesheet-only entrances would replay on every render. The stagger key is the run's snapshot id, so a retry — which reuses the snapshot — does not re-stagger. Cues are cleared on their own `animationend`, which keeps them CSS-driven and therefore inside the blanket reduced-motion block.
- **Split-control state is stated, not queried.** The two split controls (Review | Selection, and a row's row | retry) used to be styled with `:has()`, which the catalog reviewer flags for selector-invalidation cost on a subtree that re-renders per streamed finding. The rail already knows both conditions, so it sets `-split` and `-hover` classes directly (`syncSelectionSegment`, `syncRetry`). One thing `:has()` gave for free has to be done by hand: a retry button removed while the pointer is over it never fires `mouseleave`, so removal clears the hover class explicitly.
- **Mounts are idempotent ACROSS plugin generations** (`ui/editor/mount-guard.ts`). The keyed glue map only guards within one controller; if a previous generation's `onunload` aborted before `ReviewController.dispose()` (Obsidian catches the throw, logs `Plugin failure`, and still disables), its rail wrapper/margin column stays in the pane's `contentEl` and a fresh controller cannot see it — the next enable would mount a second rail beside the zombie ("double rail", one frozen at its last collapsed state). `createGlue`/`mountMarginColumn` therefore remove any stray `:scope > .editor-ai-daemons-rail-wrapper` / `.editor-ai-daemons-margin` (direct children only — nested views own their own mounts) before mounting. Strays are REMOVED, never adopted: they belong to a dead controller. The leak path is also closed at the source: every `onunload` step in `plugin.ts` and every `destroyGlue` in `dispose()` is exception-isolated, so one throwing step cannot strand the rails.

### Adaptive layout

One pure module owns the rules (`ui/editor/layout-mode.ts`). The pane collapses to the compact rail at **≤500px** and returns to wide only at **≥560px**: the band is hysteresis, because a single threshold would re-render the chrome the user is dragging toward on every observed frame. A non-finite or ≤0 width is not a narrow pane but a pane measured while hidden (collapsed sidebar, deferred leaf, detaching view) and keeps the current mode. `paneCardViewport` insets the pane rect and intersects it with the window box, dropping the pane constraint PER AXIS when it would leave less than a usable card — squeezing a card into a sliver is worse than letting it overlay its neighbour, and horizontal and vertical splits are independent. The glue is one `ResizeObserver` per view, constructed from the VIEW's own window (popouts are observed by their own document's implementation), measured synchronously at creation so an already-narrow pane never flashes the wide rail, and it only stores a changed mode and schedules the normal refresh — no synchronous DOM work inside a resize callback.

## Persistence

- **Every behavior setting has a consumer, and a spec proves it.** `behavior.stripFrontmatter` and `behavior.responseLanguageOverride` both shipped as documented controls that nothing read — a privacy control with no consumer is worse than no control. They are implemented at the one seam each path crosses (`context-assembler` for what is measured and previewed, `backend-executor` for what is sent, `augmentResponseLanguage` for both the editor and the chairperson prompt), and a spec now walks `behaviorSettingsSchema` and fails on any key nothing reads.
- Settings (editors, panels, actions, rules, providers): plugin `data.json`, schema-versioned with migrations, stable UUIDs, referential integrity on delete. Transfer in and out of a vault goes through `domain/settings/settings-transfer.ts` (pure): export strips API keys and declares the fields that can still hold one; import validates per entity, applies section caps BEFORE remapping (so a capped-out entity leaves no dangling reference), regenerates ids, remaps references, brings API backends in disabled, and returns a plan — destinations included — that the user confirms before anything is written.
- Findings/runs: ephemeral (in-memory per session).
- Async margin comments: ONE sidecar file, `<pluginDataDir>/comments.json` (`manifest.dir`, falling back to `Vault.configDir` — the config folder is user-configurable and is never hardcoded), keyed by vault-relative note path, schema-versioned. `domain/comments/` owns the shape, the defensive load and the re-anchoring; `services/comments/comment-repository.ts` owns the location decision, the write discipline and corruption recovery; `ui/comment-store.ts` is the `Vault.adapter` seam plus two vault hooks.
    - **Location, decided**: per-note sidecars next to the notes (or a frontmatter block) were rejected — not polluting the vault is a core promise of this plugin, a conflicted `comments.json` costs plugin state while a conflicted sidecar or frontmatter block conflicts the user's own file, and one file means one code path for rename, corruption and atomic writes. Not `data.json` either: settings hold API keys and are rewritten on every settings change.
    - **Anchoring is never restored, always resolved**: a comment persists `quote` + `prefix`/`suffix`/`occurrence` and deliberately no offsets (the note may have changed while Obsidian was closed), and is re-anchored against the live text through the same `matchQuote` engine findings use. Outcomes: `exact`, `fuzzy` (normalized match, anchored to the SOURCE slice so any precondition compares real text), `orphaned` — kept with its quote, shown as orphaned, never guessed into a position and never deleted.
    - **Rename moves, delete drops**: the repository re-keys the exact path AND any folder prefix, idempotently, so it does not depend on which event Obsidian emitted. A delete drops the entry; a path-keyed tombstone was rejected because a note later created at that path would silently inherit a deleted note's comments.
    - **Corruption**: an unreadable or partially-salvaged store is copied to a timestamped `comments.corrupt-*.json` BEFORE anything writes, the plugin loads with what could be salvaged, and the user is told. If the copy fails, the repository refuses to write for the session.
    - **Writes**: debounced, coalesced (one in flight, at most one queued behind it), staged to `comments.json.tmp` and renamed over the store, with ordered fallbacks for adapters that will not replace an existing file.
    - **Interrupted jobs**: `submitted`/`running` cannot be true in a session that has not started, so they load back as `interrupted` — Retry, never fake resumption. Plugin unload records the same thing from the other side (`CommentJobRegistry.interruptAll()` before the store is flushed), because either path can be the one that runs and they must agree.

## Push-back threads

A thread turn lives on the RUN handle, because the run owns the findings: a replaced or discarded run kills its turns for free, and `cancelRun` aborts them and marks their findings failed immediately, so an abort-ignoring executor cannot leave a card spinning. A turn does not touch `settled`/`isSettled()` — the review is over — and it aborts on its own signal rather than the run's, so pushing back on the findings of a CANCELLED run still works. Dispatch (`services/thread-service.ts`) is shaped like `startReview`: exclusions fail closed first, then the kill switch, then the editor that PRODUCED the finding — only that editor may answer, and a missing / disabled / review-incapable / backend-less one is a typed skip. There is no size guard: a thread turn never carries the note text, and the review that produced the finding already passed it. A turn discusses the LIVE text of an anchored span, else the anchored text, else the raw quote — a stale anchor's offsets are never consulted.

## Background comment jobs

A parked margin comment is the only work in the plugin the user walks away from, so it gets its own orchestration shape (`services/orchestration/comment-run.ts`) — keyed by COMMENT id, not by file, bound to no view, surviving note switches by construction. It is a `review` operation scoped to the span with the question carried as the per-run instruction (`domain/comments/comment-prompt.ts`); no seventh request kind was added, so there is one prompt serializer, one result shape and one set of protocol tests.

- **Admission** (`services/orchestration/background-gate.ts`): background work shares the ONE plugin-wide budget but never queues for it. A job takes a permit only while `queuedCount() === 0` and `activeCount() < cap - 1`. The reserve keeps a slot the foreground can take immediately; the empty-queue clause is what actually prevents starvation, because `Semaphore` is FIFO and a queued background waiter would be admitted ahead of a review queued behind it. The cost falls on the background side (a busy vault can leave a comment waiting indefinitely), which is the right way round. Floors at one permit so `maxConcurrentRequests: 1` does not kill the feature. Preemption was rejected: the request is already paid for at the provider.
- **The registry** (`services/comments/comment-job-registry.ts`) is the ONE join between the durable comment and the live run, so a job can never be `running` on disk with nothing running. It follows the run's own notifications rather than its `settled` promise — `cancel()` terminates a handle synchronously while the aborted stream may still be winding down — and owns the once-a-second ticker that keeps elapsed timers honest, started and stopped with the in-flight set.
- **Dispatch** (`services/comments/comment-job-service.ts`) has the same gate order as `startReview`: exclusions fail closed, the binding-rule kill switch refuses before any dialog, then the size guard (a comment sends the whole note as context, unlike a thread turn), then one named editor resolved fresh, then context assembly, then the durable record, then the request. A rule's `assign` target does not override the comment's editor — a comment names who it asked, like a push-back does.
- **Retry** re-anchors the span against the note as it reads NOW and refuses (`orphaned`) when the quote is gone: re-asking about text that no longer exists would return an answer about something else under the original question. A retry clears the previous error and answer rather than merging with them.
- **Span hints** (`domain/comments/span-hints.ts`) are the inverse of `matchQuote` — a user-created comment derives its own `quote`/`prefix`/`suffix`/`occurrence`, with a spec-pinned round-trip guarantee that hints re-anchor to exactly the span they came from.
- **Surface**: the margin column (below) and the side panel section (`ui/comment-jobs-model.ts` is the pure projection; the `ItemView` only renders it). The status bar was rejected — it is global chrome, and a per-second timer there would animate permanently for a feature the user is deliberately not watching.

## Margin comment column

Comments are rendered beside the lines they were parked on by a positioned overlay owned by the markdown view — deliberately NOT a CM6 gutter, for the same reason the rail is not one: gutters are left-side, line-oriented strips inside the scroller, while this is a right-hand column of prose cards that must coexist with Obsidian's own gutters instead of competing for their slot. Three pure modules decide everything and the glue only measures and applies.

- **Geometry** (`ui/editor/margin-layout.ts`): where a column may exist, which comments share a line, and where each group lands. Groups push each other DOWN from their anchors and then pull back UP off the bottom edge, so a card sits as close to its span as it can without overlapping or falling out of view.
- **Card model** (`ui/editor/margin-model.ts`): what a card says and which affordance it offers. Resolved comments leave the margin (the store keeps them), orphans go into one collapsed group at the top WITH their quote, bodies truncate with an in-place expansion, and Retry is offered only where `retryCommentJob` would accept it.
- **DOM** (`ui/editor/margin-column.ts`): Obsidian-free, popout-safe, no `innerHTML`. Render, measure and position are three phases because a card's height is only knowable once rendered and its position depends on every other card's. `marginModelKey` deliberately excludes anchor positions AND the elapsed timer, so neither a scroll frame nor a running job's once-a-second tick rebuilds the column and destroys focus and expanded answers; the timer and the card's announced sentence are the only live text, and the column writes them in place.
- **Coexistence with the editor width, decided**: with **Readable line length** on (Obsidian's default) the column drops into the empty right margin and the note's layout does not move at all (`overlay`). With it off the text runs the full pane width, so the column reserves its space by padding the scroller (`reserve`) — floating cards over prose would hide the sentences they comment on. The reflow happens when the first comment appears on a note and when the last one goes, both explicit user actions; scrolling never changes it, because the column stays mounted while the note has any comment even when none is currently in view. The free-margin measurement subtracts the reserve it applied (halved under readable line length, where padding moves a centered block by `P/2`), or the placement would oscillate. Below ~700px of pane there is no column at all and the side panel is the surface.
- **Cost of asking**: re-anchoring runs `matchQuote` over the whole note once per comment, and the refresh cycle fires on every edit batch and every scroll frame — so the result is memoized against the CM document's identity (immutable, so a new object IS a changed document) and the stored comments' revisions, and group heights are re-measured only when the DOM or the column width actually changed.
- **Entry point**: `ReviewController.openCommentModal` from the editor context menu, the `Ask for comments` command and the panel button. A selection is required — a margin comment is anchored to a span, and a whole-note comment would have no line to sit next to and no quote to re-anchor against. The picker opens on `behavior.defaultCommentEditorId` (plan §4 comment routing) and falls back silently when that editor can no longer run.

## Accessibility contracts

Three rules the UI layer holds itself to, all of them checkable by reading the code rather than by running a screen reader.

- **Nothing is signalled by colour alone** (WCAG 1.4.1). Editors vs panels: `ui/entity-label.ts` — the name says `(panel)`, the ring and the glyph are additions. Findings in the document: the persona tint is joined by a per-editor bottom-edge STYLE (`editor-ai-daemons-finding-edge-<n>`, from the editor's position in settings) and a `title` naming the editor, its panel, the severity and staleness (`ui/editor/finding-identity.ts`, which also records why that name rides a `title` rather than an `aria-label` — a CM6 mark is a `<span>` in contenteditable, i.e. `role=generic`, which ARIA forbids naming). Diffs: the deletion is struck out, so the insertion is underlined. Severity in the side panel: a shaped Lucide glyph, named through `role=img`. The colour swatch: a check glyph plus `aria-pressed`; when a custom hex is active the native colour input carries the selected ring and names its value (`Custom color, current: #…`), and every choice (swatch or picker) is pushed through a visually-hidden `role=status` live region created OUTSIDE the row the field re-renders (`settings/components.ts` + pure logic in `settings/color-field-model.ts`). The picker seeds from the active preset's computed colour so "start from the current colour and tweak" works; it stays a native `input[type=color]` rather than Obsidian's `ColorComponent` — that is a `Setting`-control wrapper around the same input which would force the custom picker out of the swatch row for zero functional gain.
- **Every region and every repeated control is named.** Side-panel sections are named for their editor and, when there is one, their panel (`memberSectionName`); scorecard rows are `role=group` carrying a composed sentence; margin cards and comment rows are `role=group` for the same reason; identically-labelled buttons (Retry, Cancel, Resolve, Delete, appearing once per comment) say which comment they act on (WCAG 2.4.6); a control whose visible text is already its name is never overridden by an `aria-label` (WCAG 2.5.3, `MarginColumn.applyHint`), and where a name IS composed the visible text is its leading run — the rail's rows build their accessible name from the name they actually SHOW, ellipsis included, and keep the full one on the tooltip (`rail-model.ts`). **Progress is pushed, not only pullable**: the rail owns one visually-hidden `role=status` region, outside anything a render replaces, fed the coarse transitions `railAnnouncement` derives from the motion cues (run started, one editor landed, run finished) — never a per-finding stream. Per-row precision is worthless during a run if reaching it means re-navigating the rail.
- **The persona colour is never consumed raw where it must stay readable** (WCAG 1.4.3 / 1.4.11). The colour is user-configurable (any hex, plus legacy `var(--color-*)` presets), so a near-black on a dark theme — or a pale yellow on light — would composite to an invisible tint/edge at every mix level. The FINDING HIGHLIGHTS block of `styles.src.css` derives `--editor-ai-daemons-finding-display` (and `--editor-ai-daemons-editor-display` for the rail-settle wash and the transform preview's left edge): an OKLCH relative-colour lightness clamp per theme (dark 0.60–0.82, light 0.40–0.62, hue preserved) behind `@supports (color: oklch(from red calc(l) c h))`, with a `color-mix(in oklab, colour 55%, var(--text-normal))` fallback. The `@supports` gate is load-bearing: a two-declaration cascade fallback does not work through `var()` — an unsupported `oklch(from var(...))` only fails at computed-value time and nukes the consumer to transparent. Solid identity chips (rail core, preview dot, swatches) keep the raw colour so they match the settings swatch. Relatedly, stale/carryover marks are dimmed by weaker tints, never by element `opacity` — CM6 renders overlapping marks as NESTED spans, so element opacity compounds multiplicatively (0.55^N) and erases the note text when several findings overlap.
- **Motion is a reinforcement, never the signal** (WCAG 2.2.2 / 2.3.3). One blanket `prefers-reduced-motion` block at the foot of `styles.src.css`, scoped to the plugin's own class prefix, collapses every animation and transition — an allow-list was tried first and carried its own warning that a new animation would silently escape it. Every animated state is also legible standing still, and the standing-still form is written FIRST so the animation is only what is left on top: an armed daemon toggle carries a solid accent border and an accent ring under its pulse, the busy ring is an asymmetric arc that stays asymmetric, the three terminal rings differ by border thickness and style rather than by hue alone (the persona colour is user-configurable and can be red or grey), the review spinner sits beside the word "Reviewing…", the chip-click emphasis keeps its stronger tint. One-shot cues are removed on their own `animationend` rather than on the next render, so a re-render mid-animation cannot abort them — and they stay CSS-driven, which a WAAPI animation would not be (it would escape the blanket block entirely).

## Performance contracts

Four properties the code holds, each measured by `src/app/perf/perf.bench.spec.ts` (`bun test perf.bench`) rather than asserted. Numbers are medians on a developer laptop; the suite asserts ceilings well above them, so it catches an accidental O(n²) without failing on slower hardware.

- **Resolving many quotes against one document costs one pass, not n.** `createQuoteMatcher(text)` binds a document and normalizes it at most once, lazily; `matchQuote` is that matcher used once, for genuine one-offs. Run ingestion (`AnchorBase`) and comment re-anchoring (`reanchorComments`) each build one per batch. 500 orphaned comments on a 200 000-character note: **7 231 ms → 29 ms**. This one is not a micro-optimization — that work ran on the refresh cycle, i.e. on every edit batch while the user typed.
- **One view of the vault per RUN, not per editor.** `createCachingVaultReader` (services/context) answers each read / link resolution / metadata lookup / note-type lookup once, and `startReview` wraps the injected reader with it. 8 editors × 20 linked notes: **160 → 20 note reads, 168 → 21 metadata reads**. Deliberately not a vault cache: it is built per run and thrown away with it, so an exclusion the user adds mid-session is never answered from a stale copy (Business Rules #7). Within a run the freeze is the point — every panel member is briefed on the same vault.
- **A large rewrite still gets a word-level diff.** Above `LCS_TOKEN_BUDGET` the region is split on tokens occurring exactly once on each side (patience-diff anchors, longest increasing subsequence to keep them monotone) and each gap is diffed on its own; only a region with no unique common token degrades to one del + one ins. A 30 000-character, 25 % rewrite: **2 → 1 670 changed segments**, 0.9 ms → 8 ms. A 200 000-character rewrite: 47 ms, reconstruction invariants intact.
- **The editing loop is bounded by the document, not by how many editors are enabled.** `MAX_DECORATED_FINDINGS` = 2 000 marks per note (`ui/editor/decoration-budget.ts`), keeping the first 2 000 in document order plus the triage cursor. Every finding stays in the store, in the side-panel list and actionable; the panel states how many are listed but not highlighted.

Measured and deliberately left alone: the decoration set itself (2 000 marks rebuild in ~1.2 ms, remap on a keystroke in ~0.06 ms), the margin column model (500 comments project and key in ~2.4 ms), and exact-pass anchoring (200 verbatim quotes on a 200 000-character note in ~11 ms).

Bounds on untrusted input, verified by spec rather than assumed: a backend result is capped by the operation contract (≤ 200 findings, ≤ 10 edits per finding, quote ≤ 2 000 chars, critique/edit-text/reply ≤ 10 000, replacement/insertion ≤ 100 000) — a 10 000-finding or 1 MB response is refused as `invalid-output`, while a PER-FINDING violation inside a valid review envelope is salvaged instead (contract v2 design §5: invalid edits strip to display-only with the `invalidProposal` marker, an invalid observation core drops the finding counted; the losses travel on the result event as `salvage` and the side panel reports them); a CLI backend's stdout is capped at 8 MB (`services/backends/cli/capture.ts`); the link graph is depth 1, capped by `maxLinkedNotes` (≤ 20) and `FOLLOWED_LINKS_CAP` (20 per referenced note), with `contextBudgetChars` bounding what is actually sent.
